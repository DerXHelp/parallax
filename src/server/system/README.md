# src/server/system – Desktop-Integration (Windows seit Phase 2, Linux seit WP-106)

Owner: **WP-33**, Einträge einer Installation **WP-86** (Teil 86c), Linux **WP-106** (Welle L2) (außer
`ports.ts`: Koordinator, eingefroren). Aufträge: `docs/wp/WP-33.md`, `docs/wp/WP-86.md` §3,
`docs/wp/WP-106.md`.

Sichtbare Konsole für `claude --resume <id>` (ADR-104), Autostart-Verknüpfung (ADR-110) und der
optionale Protokoll-Handler `parallax:` (ADR-109); seit WP-86 zusätzlich die Startmenü-Verknüpfung
einer Installation. Nur der produktive Server (Standard-Datenordner, SDK-Backend, kein `--dev`;
`--system-integration=on` erzwingt es – `systemIntegrationAvailable` in `config.ts`) ändert HKCU,
den Autostart-Ordner oder das Startmenü – Tests, Dev- und Fake-Server nie.

**Marker (WP-86, `markers.ts`):** Ob ein vorhandener Eintrag (Argumente der Verknüpfung,
`shell\open\command`) „eigen“, „zurückgestellt“ oder „fremd“ ist, entscheidet sein Befehl
(case-insensitiv). Klon/Entwicklung (`installRoot` null): eigen = `launcher\main.ts`, zurückgestellt =
`\start.mjs` (Einträge einer Installation bleiben beim Anlegen und Entfernen unangetastet, ohne Warnung,
Log `info`, kein Launch-URI im Toast). Installation (`installRoot`): eigen = `launcher\main.ts` (wird
umgebogen) oder `<installRoot>\start.mjs`; der Eintrag einer anderen Installation ist fremd. Der
Deinstaller nimmt nur `<installRoot>\start.mjs`. Fremde Einträge werden nie ersetzt oder entfernt.

**Linux (WP-106, WP-100 §5.4/§5.5/§5.8):** dieselben Regeln über freedesktop-Einträge (`xdg.ts`):
Autostart `$XDG_CONFIG_HOME/autostart/parallax.desktop`, Protokoll-Handler
`$XDG_DATA_HOME/applications/parallax-url-handler.desktop` + `xdg-mime default` (ein fremder
Standard bleibt), Programmeintrag `parallax.desktop` mit `<root>/parallax.svg` nur für eine
Installation; eigen/zurückgestellt/fremd nach der `Exec`-Zeile (`launcher/main.ts`, `/start.mjs`). Die
Konsole und das Fenster „Shell im Ordner“ öffnen einen Terminal-Emulator (`terminalEmulator.ts`,
`linuxConsole.ts`), die Prozess-Überwachung läuft über `/proc`. Pfade nur aus der übergebenen
Umgebung (`HOME`, `XDG_*`), nie `os.homedir()`; ein Testlauf schreibt nichts (R6).

**Verdrahtung (WP-40):** `createSystemIntegration({ available: systemIntegrationAvailable(config),
repoRoot, home: config.home })`, `apply(settings)` beim Start und nach jedem `settings.update`,
`warnings()` in `HostState.warnings`, `onChange` → `publishHostState`; Konsole:
`config.backend === 'fake' ? createFakeConsoleLauncher() : createConsoleLauncher()`. Der Toast
(`lib/toast.ts`) bekommt `launchUri: integration.toastLaunchUri(entryId)` und `silent`.

**Verdrahtung (WP-86d, Koordinator):** `createSystemIntegration` bekommt `installRoot` aus der
Konfiguration (`--install-root`); der Installer ruft `ensureStartMenuEntry`, der Deinstaller
`removeInstallationEntries`.

**Verdrahtung (WP-106, offen für den Koordinator):** Konsole über `createPlatformConsoleLauncher({
terminalEmulator: () => settings().console.terminalEmulator })` (Ergebnis kann `null` sein),
`linuxDesktopCapabilities()` in die Host-Fähigkeiten; `createSystemIntegration` braucht nichts Neues.

**Tests:** nur mit injiziertem `run` (Fake) und Temp-`APPDATA` (Linux: `memoryDesktopFs`, Windows-Teile
nur unter Windows); `guard.test.ts` prüft, dass ohne
Injektion nichts gestartet wird (Spawn-Falle, auch Startmenü und Deinstaller) und jeder Test der
Integration sein `run` injiziert. Marker-Matrix (Klon/Installation/Deinstaller × alt/neu/andere
Installation/fremd) in `autostart.test.ts`. Live (sichtbares Fenster, `.lnk`, HKCU, Toast-Klick) prüft
erst WP-41 (L6, L8, L10).
