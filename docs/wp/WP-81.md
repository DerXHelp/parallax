# WP-81 – Benachrichtigungen über Rechner

Auftrag des Koordinators (18.11.2026), Branch `wp/81` von `feature/multi-host` @ `d0112fd`. Normativ: `docs/wp/WP-75.md`
§4.6 (und §4.4 „Welche Einstellungen gelten“), `docs/wp/WP-76.md` (Wächter), ADR-211. Nachtrag des Koordinators aus dem
Security-Review: Ratenbegrenzung der Wächter-Toasts, Einstellungen im Web immer von diesem Rechner.

Besitz: `src/server/sessions/{notifier,manager}.ts` (nur der Benachrichtigungsweg) und deren Tests,
`src/server/sync/hub.ts` (nur Wächter-Zustellung/Presence), `src/server/hosts/**` (ohne `ports.ts`), `src/server/lib/toast.ts`,
`src/server/launcher/{args,cli,launcher}.ts`, `src/web/notifications/**`.

## Aufbau

### Freigebender Server: Routing

- **Der Wächter ist nie Teil der Fenster-Logik.** `chooseChannelWithReason` filtert ihn heraus (`windowClients`), ebenso
  `isViewedByVisibleClient`, `isWatchedByFocusedClient` und `presenceSummary` (dort `relay: boolean`, je Fenster `remote`).
  Ein Wächter, der Fokus oder eine angezeigte Session behauptet, ändert nichts.
- **Fokus-Historie** (`FocusHistory`, `observeFocus`, rein): letzter Fokus eines lokalen und eines Remote-Fensters in
  diesem Serverlauf – auch von inzwischen geschlossenen Fenstern (`presence()` kennt nur offene Verbindungen) – und der
  erste Verbindungszeitpunkt des aktuellen Wächters (gleiche Client-Id nach einem Wiederverbinden behält ihn). Der
  Manager pflegt sie in `onPresenceChanged` und vor jedem Routing.
- **`relayTarget(clients, history)`**: Der Wächter ist Ziel, wenn er verbunden ist und
  - `remote_focus`: das zuletzt fokussierte Fenster kam über den Fernzugang, oder
  - `no_local_focus`: seit der Wächter (erstmals) verbunden ist, war kein eigenes Fenster fokussiert (auch: nie).
  Gleiche Zeitstempel: dieser Rechner gewinnt.
- **`routeNotification(…, history)`**: Ist der Wächter Ziel, gilt der native Kanal als verfügbar (der Toast erscheint auf
  dem steuernden Rechner, auch wenn dieser hier nicht toasten kann). Wählt der Kanal dann einen nativen Toast, wird er zu
  `relayClientId` (+ `relay: RelayReason` in der Route), `native` ist false. Ohne `history` (ältere Aufrufer) nie.
- **Manager**: `notify` an das Fenster wie bisher, zusätzlich `notify{…, delivery:'system'}` an den Wächter; Log-Zeile
  mit `relay` und Kanal `relay`/`relay_in_app`.

Routing-Matrix (native Toasts sind hier verfügbar, Filter dieses Rechners lassen eine OS-Meldung zu):

| Fenster-Lage | Wächter | Nutzer zuletzt | Ergebnis |
| --- | --- | --- | --- |
| Fenster im Blick zeigt die Session | egal | egal | nichts (wie bisher) |
| Fenster im Blick woanders | egal | egal | `in_app` dorthin (wie bisher) |
| Ziel-Fenster kann Web Notifications | egal | egal | `system` an das Fenster, kein Toast (wie bisher) |
| Ziel-Fenster ohne Web Notifications | nein | – | `in_app` + lokaler Toast (wie bisher) |
| Ziel-Fenster ohne Web Notifications | ja | hier | `in_app` + lokaler Toast (wie bisher) |
| Ziel-Fenster ohne Web Notifications | ja | am steuernden Rechner | `in_app` an das Fenster + `system` an den Wächter |
| kein Fenster | nein | – | lokaler Toast (wie bisher) |
| kein Fenster | ja | hier | lokaler Toast |
| kein Fenster | ja | am steuernden Rechner | `system` an den Wächter (auch ohne native Toasts hier) |
| „Nicht stören“/Toast aus (hier) | egal | egal | nur `in_app` an das Fenster, nie an den Wächter |

### Steuernder Server: `hosts/relayToasts.ts`

`createRelayToasts({ hosts, settings, enabled, available?, system?, logger?, … }) → { close, idle }`:

- abonniert `onRelay` und `onChange`; zeigt nur `delivery: 'system'` von Rechnern in `list()`;
- Texte in der Sprache dieses Rechners (`toastText` der Engine-Toasts, zweite Zeile `RELAY_TOAST_BODY` mit dem Namen
  des anderen Rechners);
- Filter dieses Rechners: „Nicht stören“ und `events[kind].toast` → kein Toast, `events[kind].sound` aus → stumm;
- Klick: `parallax://session/<hostId>/<entryId>` nur, wenn `system.toastLaunchUri(entryId)` nicht null ist
  (= `openOnClick` an und Protokoll-Handler registriert, nur produktiver Server);
- Schlüssel `relayToastTag(hostId, entryId)` = `rl_` + 32 Hex von SHA-256(`hostId:entryId`) (≤ 64 Zeichen, nie gleich
  einer Entry-Id dieses Rechners); `clear` entfernt den Toast; verschwindet ein Rechner aus `list()` (entfernt, Rolle
  verlassen), werden alle seine Toasts einzeln entfernt;
- eigene kurze Warteschlange (wie `nativeToasts.ts`: dauerhafter Fehler → aus für diesen Lauf, vorübergehende Fehler →
  Pause mit Backoff), zusätzlich aus, wenn der Engine-Kanal dauerhaft ausfällt (`available`);
- **Security-Review:** je Rechner höchstens `RELAY_TOAST_RATE.max` = 10 Toasts je 60 s (darüber verworfen, Log
  gedrosselt über `shouldLogRepeated`), ein Toast je Rechner und Session (gleicher Schlüssel ersetzt), Titel auf
  `LIMITS.titleChars` gekürzt; Texte nur als Textknoten über `lib/toast.ts` (Umgebungsvariablen, DOM).
- Nie im Log: Titel und Rechnernamen (nur `hostId`, `entryId`, `kind`).

### Protokoll-Link

- `lib/toast.ts` nimmt beide Formen an (`parseHostSessionProtocolUri`, kanonisch neu erzeugt mit
  `hostSessionProtocolUri`); `local` als Rechner und ungültige Rechner-Ids werden verworfen.
- `cli.ts` prüft `--open` mit `parseHostSessionProtocolUri`; Fehlermeldung und `args.ts` (Problemtext, Hilfe) nennen beide
  Formen (`OPEN_LINK_FORMS`). `LauncherOptions.hostId` geht an `appUrlWithCode(origin, code, {entryId, hostId})` – beim
  Neustart und beim laufenden Server gleich (`openWindow` ist für beide Wege derselbe Code; Test für beide).
- Web (`src/web/state/selection.ts`, nur gelesen): `sessionKeyFromHash` nimmt `<hostId>:<entryId>` über `parseSessionKey`
  an. Die Auswahl bleibt stehen, während die Verbindung zum Rechner erst aufgebaut wird; `useSessionSubscription` abonniert
  neu, sobald die Verbindung registriert ist (`registryVersion`). Nur `forgetHost` (Rechner entfernt) leert sie.

### Web

- `delivery.ts` nimmt für jede Meldung `selectSettings(state, LOCAL_HOST_ID)`: Ton, Lautstärke, „Nicht stören“, Toast je
  Ereignis, `focusedElsewhere` dieses Rechners, auch für Sessions anderer Rechner (Sicherheitsfund: sonst umginge ein
  fremder Rechner „Nicht stören“).
- `chooseDeliveryChannel`: ohne `osAllowed` (Filter dieses Rechners) wird auch `system` zum In-App-Hinweis – nötig, weil
  der Server eines anderen Rechners mit seinen eigenen Einstellungen gefiltert hat. Für eigene Sessions ändert das nur
  das Rennen mit einer Einstellungsänderung.

## Entscheidungen

1. **„Zuletzt fokussiert“ über eine Fokus-Historie im Manager** statt nur über `presence()`: Der Normalfall „Fenster am
   steuernden Rechner geschlossen, Nutzer sitzt noch dort“ wäre sonst nicht erkennbar. Der Wächter zählt ab seiner
   ersten Verbindung in diesem Serverlauf (Wiederverbinden nach Netzwackler kippt das Ziel nicht).
2. **Wächter als nativer Kanal, auch ohne native Toasts hier**: Fall 2 aus WP-75 §4.6 (kein Fenster am steuernden
   Rechner) funktioniert so auch, wenn der freigebende Rechner selbst nicht toasten kann.
3. **Klick-Gate über `SystemIntegration.toastLaunchUri(entryId) !== null`** (Port eingefroren): es sagt genau
   „`openOnClick` an + Handler registriert + produktiver Server“; die URI baut `relayToasts` selbst mit dem Rechner.

## Abweichungen und Stolpersteine

- **Doppelter Ton im Randfall:** Bekommt ein Remote-Fenster ohne Web Notifications den In-App-Hinweis und der Wächter den
  Toast, klingen auf dem steuernden Rechner Fenster und Toast (ADR-122 will nur einen Ton). Der steuernde Server weiß
  nicht, ob eines seiner Fenster die Meldung auch bekam; `Notification` hat dafür kein Feld. Selten, weil der Launcher
  Web Notifications für den eigenen Origin vorab erlaubt. Abhilfe nur per Contract (siehe Bericht: optionales Feld,
  z. B. `notification.silent`).
- **Zweite Toast-Warteschlange:** `relayToasts` hat eine eigene Warteschlange neben `nativeToasts.ts` (höchstens zwei
  PowerShells gleichzeitig). `nativeToasts.ts` gehört nicht zu WP-81; ein gemeinsamer Kanal mit freiem Schlüssel wäre
  ein Follow-up.
- **Verpasstes `notify.clear`:** Ist der Wächter getrennt, während auf dem freigebenden Rechner eine Entscheidung
  beantwortet wird, bleibt der Toast stehen, bis er ersetzt, geklickt oder der Rechner entfernt wird (kein Abgleich nach
  dem Wiederverbinden).
- **Abschalten beim Herunterfahren:** `relayToasts.close()` muss vor `hosts.close()` laufen, sonst sieht es die leere
  Liste der Deaktivierung und entfernt beim Beenden alle Toasts (siehe Verdrahtung).
- Ein Link `parallax://session/<hostId>/<id>` eines Rechners, der hier nicht (mehr) in der Liste steht, wählt im Web einen
  Schlüssel ohne Verbindung (Anzeige der Shell nicht geprüft; Shell gehört nicht zu WP-81).

## Verdrahtung (Koordinator, `src/server/app/compose.ts`)

```ts
import { createRelayToasts, type RelayToasts } from '../hosts/relayToasts';

let relayToasts: RelayToasts | null = null;

// nach createNativeToasts (`toasts`), createHostsService (`hosts`) und der Systemintegration (`system`):
relayToasts = createRelayToasts({
  hosts,
  settings: () => stores.settings.get(),
  enabled: config.toasts === 'native',
  available: () => toasts.available(),
  system,
  ...loggerOption,
});

// Shutdown-Schritt 'multiHost' – VOR controlHosts?.close() (sonst entfernt die Deaktivierung alle Toasts):
{
  name: 'multiHost',
  run: async () => {
    await multiHostStart;
    await multiHost?.stop();
    relayToasts?.close();
    await controlHosts?.close();
    await remoteAccess?.close();
  },
},
```

Der Routing-Teil braucht keine Verdrahtung (Manager und Hub sind schon verbunden). `cleanupAfterFailure` läuft über
dieselben Schritte.
