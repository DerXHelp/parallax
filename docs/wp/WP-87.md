# WP-87 – Update in der App: Entwurf und Zuschnitt (Stufe 2: WP-87…89)

Branch `feature/releases`. Grundlage: `docs/wp/WP-83.md` §7–§9, §11, §12, §16 und WP-86 (fertig). **Entwurf zur
Prüfung durch den Koordinator;** erst nach Freigabe arbeiten die Teilpakete aus §2 in Worktrees. Wo Plan und Code sich
widersprechen, gilt der Code (§0.3).

## 0. Ziel, Entscheidungen, Abweichungen

**Ziel:** Parallax prüft selbst auf neue Releases, bereitet ein Update im Hintergrund vor (laden, prüfen, entpacken,
Agent SDK) und schaltet auf Klick um: sichern, neu starten, das offene Fenster verbindet sich neu. Scheitert der Start,
geht es automatisch zurück. Dazu „Zurück zu <vorige>“, „Aus Datei installieren“, „Was ist neu“, Lizenz und Hinweise.

### 0.1 Entscheidungen des Nutzers (17.11.2026, verbindlich)
1. **1.0.0 enthält den Update-Mechanismus** mit den Abhängigkeiten von heute; das folgende Abhängigkeits-Update wird
   1.0.1, das erste Update über den Knopf auf allen Rechnern.
2. Ein Rechner läuft auf der installierten `1.0.0-rc.2` ohne Mechanismus; er kommt per `install.cmd` weiter (§4).
3. Live-Test rc.3 per `install.cmd` → rc.4 „Aus Datei“ → 1.0.0 per Knopf: geprüft und in §4 eingebaut.

### 0.2 Entwurfsentscheidungen
- **E1 Die alte Version orchestriert.** Der Server startet `versions\<alt>\dist\launcher.js --apply-update=<v>` direkt
  (nicht über `start.mjs`), wartet auf den Handschlag „bereit“ und beendet sich erst dann. Ohne Handschlag hinterließe
  ein abgestürzter Orchestrator ein Fenster, das nur noch „startet neu“ zeigt.
- **E2 Der Orchestrator startet die neue Version selbst** (`dist/server.js` über `launchLocked`, die heutige Startlogik
  ohne eigene Sperre). Ein neuer Launcher hinge an der Start-Sperre, die der Orchestrator hält
  (`src/server/launcher/launcher.ts:221`).
- **E3 Ergebnis in `update-result.json`** im Datenordner, in einem über Versionen stabilen Format. Der startende Server
  macht daraus `justUpdated` bzw. `failedUpdate`.
- **E4 Nur Fehlendes wird gebaut.** Die Installationslogik wird geteilt (`stageVersion`, `switchVersion`,
  `verifyVersion`); Signatur, Hashes, `walkPackage`, `provideSdk` und die Sicherung bleiben die vorhandenen Module.
- **E5 Update-Zustand im Speicher.** Auf der Platte nur `update-state.json` (ausgeblendete Version) und der Marker; ein
  Store-Schema ändert sich nur durch `settings.updates`.
- **E6 „Was ist neu“** aus dem signierten `CHANGELOG.md` (§1.6); der Parser zieht nach `src/shared/changelog.ts`.
- **E7 Test-Endpunkte nur im Test-Build** (esbuild-`define` `__PARALLAX_UPDATE_TEST__`); ein Test belegt, dass das
  Release-Bundle sie nicht enthält. `isTestRun` genügt nicht (WP-83 §12).

### 0.3 Abweichungen vom Plan, Widersprüche Plan ↔ Code
1. WP-83 §11/§12 (Knopf erst ab 1.1.0, Live-Test 1.1.0 → 1.1.1) wird durch §0.1 und §4 ersetzt.
2. **§5.1** nennt `start.mjs`/`parallax.cmd` als Vorlagen im Paket; `scripts/release-pack.ts:338-343` legt sie nicht
   hinein. `writeRootFiles` (`src/server/install/install.ts:267`) schreibt die Vorlagen des **laufenden** Codes, nach
   einer Übergabe also die der alten Version. Neu: das Paket trägt `root/start.mjs` und `root/parallax.cmd` (signiert),
   der Umschalter nimmt sie von dort (§1.9).
3. **§7** „`release.json` kann einen Nachfolgeschlüssel tragen“: Das Schema hat kein solches Feld
   (`src/server/launcher/release.ts:35-56`). Es bleibt bei einem zweiten Eintrag in `RELEASE_PUBLIC_KEYS`, ausgeliefert
   in einer Version, die noch mit dem alten Schlüssel signiert ist.
4. **§9.3:** Die Sicherung legt der Orchestrator an, nicht `backupBeforeStart` (`src/server/launcher/backupStep.ts:16`),
   denn er braucht den Ordner für den Rückweg. Wie die neue Version startet, regelt E2.
5. **§9.3 „Reconnect bis zu 2 Minuten“** ist zu knapp. Ungünstigster Fall ≈ 3,5 min: 45 s bis der alte Server endet,
   10 s Kill, 60 s neue Version, 60 s Rückweg. Neu: 5 Minuten.
6. **§9.7:** drei zusätzliche Fehlercodes (§1.5).
7. **Nicht im Plan:** Der Shutdown beendet nach 5 s jeden Kindprozessbaum des Servers
   (`src/server/launcher/shutdown.ts:91`, `:172`), also auch den Orchestrator; er bekommt eine Ausnahme (§2.2, §2.5).
8. **§9.1 (Proxy/TLS)** ist erfüllt: Der Server einer Installation läuft mit `PACKAGE_NODE_FLAGS`
   (`src/server/launcher/launcher.ts:683`).
9. **§9.5:** `latest.json.notes` enthält nur den Abschnitt der neuen Version (`scripts/release/sign.ts:62`); über
   mehrere Versionen zählt das `CHANGELOG.md`-Asset (§1.6).
10. Vorabversionen haben keinen eigenen Changelog-Abschnitt und nehmen „Unveröffentlicht“
    (`scripts/release/changelog.ts:159`); „Was ist neu“ macht es ebenso.
11. **GitHub `latest` liefert nur Vollversionen** (geprüft 17.11.2026): `releases/latest/download/latest.json` → 404,
    solange es nur Pre-releases gibt; `…/download/v1.0.0-rc.2/latest.json` → 302 auf
    `release-assets.githubusercontent.com`. 404 heißt „kein Update“, nicht Fehler. `compareVersions`
    (`src/shared/version.ts:44`) ordnet bereits `1.0.0 > 1.0.0-rc.4`.

### 1.5 Fehlercodes (`src/shared/errors.ts`)
| Code | Kategorie, HTTP, Schwere | Parameter |
|---|---|---|
| `UPDATE_CHECK_FAILED` | internal, 502, warning, retry | `reason`: network, timeout, http, too_large, schema, url |
| `UPDATE_DOWNLOAD_FAILED` | internal, 502, error, retry | `reason`: network, timeout, http, size, hash, disk |
| `UPDATE_INVALID_SIGNATURE` | validation, 400, error | `file`: `latest.json` \| `release.json` |
| `UPDATE_INVALID_PACKAGE` | validation, 400, error | `reason`: zip, layout, files, version, same_version, too_large |
| `UPDATE_SDK_FAILED` | internal, 502, error, retry | – |
| `UPDATE_NOT_PACKAGED` | conflict, 409, warning | – (Klon, `pnpm dev`) |
| `UPDATE_BUSY` | conflict, 409, warning, retry | `status` |
| **neu** `UPDATE_NODE_TOO_OLD` | conflict, 409, error | `required`, `actual` |
| **neu** `UPDATE_DOWNGRADE_BLOCKED` | conflict, 409, error | `version` |
| **neu** `UPDATE_RESTART_FAILED` | internal, 500, error, retry | `version`, `reason` |

- `CHECK_FAILED`/`DOWNLOAD_FAILED` tragen bei `reason: 'http'` zusätzlich `status`.
- `UPDATE_NODE_TOO_OLD`: Der Rat „Node aktualisieren“ unterscheidet sich vom kaputten Paket. Nicht Kategorie `setup`,
  die schaltet den Setup-Bildschirm (`isSetupError`); das gilt für alle Update-Codes.
- `UPDATE_DOWNGRADE_BLOCKED`: ältere Version aus einer Datei, andere Schema-Hashes, keine passende Sicherung – die alte
  Version würde Store-Dateien in Quarantäne schieben (WP-83 §1).
- `UPDATE_RESTART_FAILED.reason` ∈ `UPDATE_RESTART_FAILED_REASONS` = spawn, handshake, lock, package, backup, port,
  timeout, exited, store_too_new. Gilt für das Ack von apply/rollback, `failedUpdate.error` und den Client nach Ablauf
  der Neustart-Frist (§2.4).

### 1.6 „Was ist neu“: Woher die Notizen kommen
- **Vor dem Update, Quelle `github`:** `update.check` lädt bei einer neueren Version das Asset
  `…/releases/download/v<v>/CHANGELOG.md` (≤ 2 MiB) und prüft dessen SHA-256 gegen `changelogSha256` im signierten
  `latest.json` (`scripts/release/sign.ts:61`); die Datei bleibt im Speicher. Scheitert das, gilt `latest.notes` als
  einziger Abschnitt. **Quelle `file`:** das `CHANGELOG.md` des Pakets (in `release.json` gehasht, also signiert).
- **Installierte Version:** `<repoRoot>\CHANGELOG.md` (im Paket gelistet, im Klon die Datei des Repos).
- **Auswahl:** `sectionsBetween(changelog, from, to)` aus `src/shared/changelog.ts` liefert die freigegebenen Abschnitte
  mit `from < v ≤ to`; ist das leer und `to` eine Vorabversion, kommt „Unveröffentlicht“. `for=available`: `from` =
  laufende Version (bei einem Downgrade nur der eigene Abschnitt). `for=installed`: mit `since` die Abschnitte danach,
  sonst `releaseSection(laufend)`. Gerendert über den `Markdown`-Slot, ohne Raw-HTML.

1. **Sperren** `launch` (Datenordner) und `install` (Stammordner), je ≤ `lockMs`.
2. **Prüfen vor dem Handschlag:** `server.lock.json` nennt `waitPid` und die Build-ID der eigenen `release.json`; Ziel:

4. **Warten**, bis die Home-Sperre frei ist (versuchen, sofort freigeben) und `waitPid` nicht mehr lebt, ≤

   belegt: Marker `failed (lock)`, Benachrichtigung, Ende ohne Umschalten.
5. **Volle Prüfung** `verifyVersion(root, v, releaseKeys())`; scheitert sie, kein Umschalten, die alte Version startet
   wieder (Schritt 10) mit Marker `failed (package)`.
6. **Sicherung** `createBackup(home, {from: readLastBuildId ?? eigene, to: ziel})`; im Restore-Modus danach

   verloren. Dann `writeLastBuildId(home, ziel)`, `pruneBackups`. Fehler → alte Version mit Marker `failed (backup)`.
7. **Marker `pending`** mit `backupDir`, dann `switchVersion(root, v, {previous: eigene})`; `before` merken.
8. **Start** per `launchLocked({home, port, serverArgs, build: true, printUrl: false, openWindow: false,

9. **Erfolg:** `cleanupVersions(root, [v, eigene])`, Sperren frei, Exit 0.
10. **Rückweg:** Baum der neuen Version beenden, ≤ `killGraceMs` auf die Home-Sperre warten; `restoreBackup(home,
    backupDir)`, `writeLastBuildId(home, eigene)`, `restoreCurrent(root, before)`; Marker `failed {error:
    UPDATE_RESTART_FAILED {version, reason}, log}`; eigene Version per `launchLocked` starten. `reason` aus
    `LauncherError.reason`: server_timeout → timeout, server_exited → exited, store_too_new → store_too_new,
    `port_*` → port, package_damaged → package.
11. **Scheitert auch der Rückweg:** Benachrichtigung über `lib/toast.ts` mit dem Log-Pfad (deutsch oder englisch nach
    `settings.json`, zwei feste Texte im Modul); Marker bleibt `failed`, Sperren frei, Exit 1.

## 3. Risiken und offene Fragen
1. **Fenster beim Neustart:** Neu verbinden geht nur mit demselben Port; der Orchestrator übergibt die Server-Argumente
   der alten Version, ein geänderter `settings.port` wirkt erst beim nächsten Start von Hand. Wurde Chrome geschlossen,
   gibt es danach kein Fenster (gewollt). Ein Neuladen mitten im Neustart landet im normalen Reconnect.
2. **Autostart, Benachrichtigungs-Klick oder `parallax:`-Link während des Wechsels:** Der Launcher wartet auf die
   Start-Sperre (bis 25 min, `launcher.ts:201`) und öffnet dann ein Fenster der laufenden Version. `install.cmd` trifft
   auf die `install`-Sperre und bricht mit Hinweis ab.
3. **Orchestrator stirbt nach `READY`:** Kein Server läuft; das Fenster zeigt nach 5 min „Server beendet“. Ein Start
   über das Startmenü klappt (`current.json` gültig, Sicherung vorhanden); ein verbliebener Marker `pending` zeigt nur
   harmlos `justUpdated`.
4. **Virenscanner:** Entpacken und Kopieren von ≈ 6 500 Dateien und der erste Start dauern länger. Fortschritt bleibt
   sichtbar, die Frist lässt sich per `PARALLAX_UPDATE_READY_TIMEOUT_S` verlängern, der Rückweg ist sicher.
5. **Proxy:** PAC- oder reine NTLM-Proxys werden nicht unterstützt, dann bleibt „Aus Datei“. Das SDK kommt bei gleicher
   Version aus `<root>\cache`, ohne Registry.
6. **Rechte und Sperren:** alles je Nutzer, ohne Admin. Ein noch gesperrter Versionsordner bleibt stehen;
   `cleanupVersions` meldet ihn als `problems`, der nächste Lauf räumt ihn.
7. **rc.2 ohne Mechanismus:** nur `install.cmd`; dessen Übergabe schreibt die Stammdateien von rc.2, bis ein Update aus
   rc.3+ sie aus `root/` setzt.
8. **Schema-Hash-Drift:** Ein zod-Update kann die Ausgabe von `z.toJSONSchema` ändern (etwa 1.0.0 → 1.0.1). Dann gilt
   `needsRestore`, obwohl die Daten passen; der Rückweg geht nur mit Sicherung und Warnung. Hingenommen,
   Normalisierung später.
9. **Zweiter Server aus der Installation auf einem anderen Datenordner:** Ein Update startet nur den eigenen neu; das
   Aufräumen schützt nur den Server des Standard-Datenordners (wie WP-86).
10. **Job-Objekte:** Läuft der Server in einem Job mit „kill on close“, stirbt der Orchestrator womöglich mit. Dasselbe
    Risiko trägt heute schon der Serverstart des Launchers; die Live-Prüfung zeigt es.
11. **Fehler in der Orchestrierung einer Version** lassen sich nur per `install.cmd` umgehen, denn immer orchestriert
    die alte Version. Deshalb ändert sich zwischen rc.4 und 1.0.0 nichts an `applyUpdate.ts`, `launchLocked`,
    `handoff.ts` – sonst vorher rc.5 (§4).
12. **Folgearbeit:** `minNode` in `latest.json`, damit `UPDATE_NODE_TOO_OLD` schon vor dem Download auffällt; für
    1.0.x bleibt `minNode` gleich.

**FRAGE an den Nutzer:** Soll der automatische Rückweg auch live mit einem absichtlich kaputten Vorab-Release geprüft
werden? Vorschlag: nein – E2E prüft ihn mit B-kaputt, live wird „Zurück zu …“ in beide Richtungen geprüft.

## 3a. Security-Review (WP-89, 17.11.2026)
Unabhängiges Review (Subagent, nur lesend) des Mechanismus auf `feature/releases`: **kein kritischer und kein hoher
Fund.** Geprüft und in Ordnung: Test-Schalter (Zweig fehlt in allen Bundles), `latest.json` (Signatur vor dem Parsen,
exakte URL, kein Pre-Release, nur höhere Versionen, Weiterleitungen nur https), Zip (bsdtar schreibt höchstens die
deklarierte Größe, widersprüchliche Header scheitern schon beim Listen; der Walk fängt Links, ADS, Hardlinks,
Zusatzdateien), Orchestrator (PID und Build-ID gegen das Lockfile, Voll-Check unter Sperre), SDK (sha512 aus der
signierten `release.json`, Auth nur für denselben Host), Spawn, HTTP-Klassen, Marker und Zustandsdateien per zod.

**Behoben (89):**
- Zip-Listing: Namen aus `tar -t -v` müssen zeilenweise dem schlichten `tar -t` gleichen – ein Name mit
  „ parallax-“ darin kann keinen zweiten Wurzelordner vortäuschen (`update/zip.ts`).
- `comparePackageFiles`: `Object.hasOwn` statt `in` (Namen wie `toString` galten als gelistet).
- Orchestrator: Startzeit des alten Servers direkt vor `TerminateProcess` erneut prüfen (PID-Wiederverwendung während
  der Kind-Abfrage).
- Server-Start: `WS_NO_BUFFER_UTIL=1`, `WS_NO_UTF_8_VALIDATE=1` (`launcher/serverProcess.ts`) – `ws` sucht sonst ohne
  eingebaute Varianten optionale Add-ons bis hinauf nach `C:\node_modules`.

**Offen (Follow-ups, mittel/niedrig):**
- **Rechte eines eigenen Installationsordners** (`--dir`, mittel): Erbt ein eigener Root Schreibrechte für andere
  lokale Nutzer, können sie Dateien zwischen Prüfung und Start tauschen. Der Standardordner
  `%LOCALAPPDATA%\Programs\Parallax` ist nicht betroffen. Vorschlag: DACL beim Installieren und vor
  Vorbereiten/Anwenden prüfen (analog `lib/homeAccess.ts`) und ablehnen oder einschränken.
- **SDK-Ordner nach dem Staging** (niedrig): wird nur über `package.json` wiedererkannt, nicht neu gehasht.
  Voraussetzung: Schreibzugriff auf den Root.
- **Frische von `latest.json`** (niedrig): kein Ablaufdatum, keine signierte Mindestversion – ein MITM mit
  System-CA kann Updates einfrieren (alte signierte Datei oder 404); „Aus Datei“ nimmt ältere signierte Versionen an
  (bewusst, Rückweg).
