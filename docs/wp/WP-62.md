# WP-62 – `claude`-Updates: Hinweis, Kurz-Check mit Profil, Routine

- **Auftraggeber:** Koordinator, 12.11.2026, nach Abstimmung mit dem Nutzer („Parallax muss immer aktuell
  gehalten werden“).
- **Branch:** `wp/62` von `feature/cli-update` (von `main` @ `040e447`), Worktree `.worktrees/wp-62`.
- **Nutzer-Freigaben (12.11.2026, dauerhaft):**
  1. Kurz-Check bei jedem `claude`-Update ohne Rückfrage: Live mit Haiku über das Abo (kein API-Key),
     höchstens **0,05 USD je Check**.
  2. Nach grünem Check darf der Koordinator nach `main` mergen und pushen, wenn nur das Profil oder kleine
     Anpassungen betroffen sind; größere Fixes vorher dem Nutzer zeigen.
  3. `claude` aktualisiert sich weiter automatisch.

## 1. Auftrag

### Ziel
`claude` erscheint oft mehrmals pro Woche neu und aktualisiert sich selbst. Parallax soll das **merken**,
mit **einem Befehl billig prüfen** lassen, ob sich etwas Relevantes geändert hat, und der Ablauf soll als
**Projekt-Skill** in jeder Session gleich laufen. Der große Ablauf `docs/sdk-upgrade.md` (SDK anheben, alle
Fixtures neu aufzeichnen) bleibt für echte SDK-Upgrades (Stufe 2).

Anlass: Die Änderungen der CLI 2.1.322 (Aufgabenliste nicht angeboten, `task_progress.description` als
Tätigkeit, `@`-Expansion) fielen erst in der großen Live-Abnahme WP-61 auf, nicht im Live-Smoke.

### Pflichtlektüre
`CLAUDE.md`; `docs/sdk-upgrade.md` (ganz); `docs/sdk-findings.md` (Nachträge 11.11. und 12.11.2026);
`docs/wp/WP-61.md` §2.5/§2.9; ADR-011 (Live-Guards), ADR-070 (Versionsregel C.7), ADR-154 (Ressourcen),
ADR-155/156; `e2e/live/**` (Live-Smoke, `liveCostUsd`, `unknown-counts.json`); `scripts/record.ts` +
`scripts/record/**` (Guards: Abo-Login, `apiKeySource: none`, Budget); `src/server/claude/{resolveClaude,
integration,preflight}.ts`; `src/shared/version.ts`.

### Teil A – Profil (eine Quelle im Repo)
- Eine Datei im Repo hält das **CLI-Profil** der zuletzt geprüften Version: `cliVersion`, `sdkVersion`,
  Datum, und alles, was der Check vergleicht (Teil B). Ort und Format wählst du (z. B.
  `src/server/claude/cli-profile.json` + kleines Lese-Modul); Bedingung: der Server liest daraus
  `testedVersion`, `pnpm cli-check --accept` schreibt sie, sie ist menschenlesbar und diff-freundlich
  (sortierte Listen).
- Erstes Profil: per Check gegen die installierte CLI 2.1.322 erzeugen (Teil B, live).

### Teil B – `pnpm cli-check` (neu, `scripts/cli-check.ts` + ggf. `scripts/cli-check/**`)
1. **Vorprüfung ohne Kosten:** `claude --version`, Auth (`auth status`: Abo, kein API-Key, keine
   `ANTHROPIC_API_KEY`/`_AUTH_TOKEN`/`_BASE_URL`), SDK-Mindestversion (C.7). Fehlschlag → Abbruch vor jedem
   Live-Aufruf.
2. **Probe (live, Haiku, sehr kleiner Prompt):** eine SDK-Session in einem Temp-Scratch-Ordner mit
   Temp-Home, die einsammelt: `system/init` (Schlüssel, `tools` inkl. deferred, Slash-Commands, Agents,
   Capabilities, Modell, `permissionMode`), `initializationResult()`, `supportedModels()`, die
   Kategorie-`id`s von `getContextUsage()`. Guards wie beim Recorder (ADR-011).
3. **Live-Smoke:** `e2e/live` (bestehend) laufen lassen; `unknown-counts.json`, Kosten und
   Validierungs-Drops einsammeln.
4. **Vergleich mit dem Profil**, strukturiert: neue/verschwundene Werkzeuge (besonders `TodoWrite`/
   `TaskCreate`, ADR-156), Init-Schlüssel, Capabilities, Modelle, Kontext-Kategorien; `unknownCounts`
   nicht leer, Validierungs-Drops > 0, Smoke-Fehler.
5. **Ergebnis:** Bericht (Markdown) unter `test-results/cli-check/` und kurze Konsolen-Zusammenfassung;
   Exit 0 = grün (keine Abweichung), 1 = Abweichungen (Bericht listet sie mit Hinweis, welche Stelle in
   Parallax betroffen sein könnte), 2 = Fehler/Abbruch. `--accept` schreibt nach grünem oder bewusst
   akzeptiertem Lauf das neue Profil und hängt eine Zeile an ein Protokoll (z. B. `docs/cli-updates.md`:
   Datum, alte → neue Version, Ergebnis, Kosten).
6. **Budget-Guard:** Summe aus Probe und Smoke höchstens 0,05 USD (abbrechen, sobald überschritten);
   Kosten im Bericht.
7. **Rückbau automatisch,** nur nachweislich eigene Daten: Scratch-/Temp-Home-Ordner, CLI-Transkriptordner
   unter `~/.claude/projects/` der eigenen Scratch-`cwd`s, CLI-Task-Ordner unter `%TEMP%\claude\<hash>\
   <session-id>` der eigenen Session-IDs; Plan-Dateien/`~/.claude.json` nur melden.
8. **Ressourcen (ADR-154):** der Check ist ein schwerer Lauf (Playwright) – mit niedriger Priorität
   (`lowerProcessPriority`), nie parallel zu anderen schweren Läufen.
- `package.json`: Skript-Eintrag `"cli-check"` ist vom Koordinator freigegeben (keine neue Abhängigkeit).

### Teil C – Hinweis in Parallax
- Contract (vom Koordinator freigegeben, Eintrag im Contract-Changelog durch den Koordinator):
  `claudeInstallStatusSchema` bekommt `testedVersion: z.string().nullable()` **mit Default `null`**; der
  Server füllt es aus dem Profil. Sonst keine Contract-Änderung.
- Web: Ist die installierte Version neuer als `testedVersion` (`compareVersions`), zeigt Parallax einen
  dezenten Hinweis dort, wo heute „zu alt“ erscheint (`HostFacts`, Profil-/Neue-Session-Status):
  „claude <v> ist neuer als die mit Parallax geprüfte Version <t>“ (en/de, kein Fehlerton). FakeBackend:
  gleiche Version → kein Hinweis.
- `pnpm preflight`: Zeile `claude <v> (tested <t>)`, bei neuer Version `WARN … newer than tested`.

### Teil D – Projekt-Skill `/claude-update`
`.claude/skills/claude-update/SKILL.md` (Deutsch, für den Koordinator), Ablauf:
1. `claude --version` mit dem Profil vergleichen; gleich → fertig.
2. `pnpm cli-check` allein und mit niedriger Priorität (Dauerfreigabe 1).
3. **Grün:** Branch `fix/cli-<version>` von `main`, `pnpm cli-check --accept`, `pnpm check` + `pnpm build`,
   Merge nach `main` (`--no-ff`), Push (Dauerfreigabe 2), danach `main` in laufende Feature-Branches.
4. **Abweichungen:** einordnen. Klein (tolerantes Parsen, Profil, Doku, Option zurücknehmen) → Fix mit
   Test → wie 3. Größer (neue Funktion, Verhalten/UX, Contract) → dem Nutzer zeigen, nichts nach `main`.
5. Stufe 2 (`docs/sdk-upgrade.md`) vorschlagen, wenn der Check echte Änderungen zeigt oder das letzte
   SDK-Upgrade älter als etwa einen Monat ist.
6. Kurzbericht an den Nutzer: Version alt → neu, Ergebnis, Kosten, was gemergt wurde, ob `git pull` in der
   produktiven Instanz nötig ist.

### Rahmen
- **Live:** nur `pnpm cli-check` bzw. seine Teile (Probe, `e2e/live`), höchstens **drei Läufe** in diesem
  WP, je ≤ 0,05 USD (Dauerfreigabe 1). Kein `record`, kein `dev:live`, keine anderen Live-Läufe.
- **Ressourcen (ADR-154):** du bist der einzige Agent; schwere Läufe (`pnpm check`/`build`/`e2e`,
  `cli-check`) nacheinander, nie zwei gleichzeitig, PowerShell mit
  `(Get-Process -Id $PID).PriorityClass = 'BelowNormal'` davor.
- Nie `%LOCALAPPDATA%\Parallax`, kein `pnpm start`/`parallax.cmd` ohne eigenes Home, keine Desktop-Bedienung.
- Tabu außer den Freigaben oben: `src/shared/**` (nur `testedVersion`), Ports, Lockfile,
  `pnpm-workspace.yaml`, neue Abhängigkeiten.
- Tests: Profil-Vergleich und Bericht als Unit-Tests mit festen Profilen (kein Live in `pnpm test`);
  Hinweis-Anzeige als Web-Test; `pnpm check`, `pnpm build`, `pnpm e2e` grün.

### Abnahme
- `pnpm cli-check` gegen 2.1.322: grün nach `--accept` (erstes Profil), Bericht und Protokollzeile da,
  Rückbau nachgewiesen, Kosten ≤ 0,05 USD.
- Gegenprobe ohne Live: ein manipuliertes Profil (z. B. Werkzeug `TodoWrite` „vorhanden“, ältere
  Version) → Vergleich meldet Abweichung, Exit 1; Hinweis erscheint bei `testedVersion` < installiert.
- `pnpm check`, `pnpm build`, `pnpm e2e` grün.
