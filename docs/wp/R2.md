## Gesamturteil

Die Engine ist in der Substanz **korrekt und gut geschnitten**: Options-Abbildung, Spawn-Wrapper,
Event-Reihenfolge (`exit` zuletzt), Broker-Regeln (ADR-012, C.4), erster Klick gewinnt, ein Op-Pfad
(Publish → Log → Mirror → `lastOrder`), `/clear` mit Session-ID aus dem nächsten `init`,
Auto-Retry nach ADR-025, Neustart mit `expired`/`needs-resume` und der Shutdown ohne Abbruch offener
Entscheidungen entsprechen Plan, Findings und Design. `buildEnv` wird für SDK-Spawn, Git und
Verlaufs-Worker konsequent genutzt, gespawnt wird nur das aufgelöste `claude.exe`. Die Testsuite
deckt alle 12 Fixtures, die synthetischen Szenarien und die Befehlstabelle ab.

Schwächen liegen an den **Rändern zum Betriebssystem**: die Waisen-Bereinigung liest „Abfrage
gescheitert/zu langsam“ als „Prozess weg“ und blockiert dabei den Start bis zu ≈ 40 s (R2-02), der
Kinder-Pfad ist nicht gegen PID-Wiederverwendung geschützt (R2-03), die Bereitschaft hängt an einem
15-s-Timeout ohne zweiten Versuch (R2-04), und es gibt keinen exklusiven Schutz gegen zwei Server
auf demselben `PARALLAX_HOME` (R2-05). Dazu ein echter Flake im Launcher-Integrationstest (R2-01),
der `pnpm check` sporadisch rot macht.

**Anzahl:** 1 × BLOCKER, 4 × SOLLTE, 11 × NIT.

### BLOCKER vor WP-20c/WP-22

#### R2-01 [BLOCKER vor WP-20c/WP-22] Launcher-Integrationstest: Fake-Server stirbt am `EPERM` seines Lockfile-Renames
- **Fundstelle:** `src/server/launcher/launcher.integration.test.ts:58-60` (Fake-Server:
  `writeFileSync` + nacktes `renameSync`), Gegenspieler `src/server/launcher/launcher.ts:246-264`
  (`waitForServer` liest das Lockfile alle 150 ms, `:112`).
- **Befund:** Im dritten Schritt des Tests („stale lock after a crash → new server“) liegt das alte
  Lockfile noch da; der Launcher liest es in Schleife, während der neue Fake-Server es per
  `renameSync` ersetzt. Unter Windows scheitert ein Rename über eine gerade geöffnete Datei mit
  `EPERM` (Probe: 483 von 608 Versuchen) – die unbehandelte Exception beendet den Fake-Server mit
  Code 1 („Server output: Node.js v26.4.0“). Genau so im Lauf 1 dieses Reviews rot. Ein Virenscanner
  auf der frisch geschriebenen `.tmp`-Datei hat dieselbe Wirkung. Der Produktivcode ist nicht
  betroffen (`writeServerLock` → `writeFileAtomic` mit Retry), aber `pnpm check` wird sporadisch rot
  – die Abnahmen von WP-20a/b/c verlangen „2× grün“. Die Datei lag außerhalb der FLAKES-Besitzpfade.
- **Fix (Owner WP-21, nur Test):** im Fake-Server den Rename bei `EPERM`/`EBUSY`/`EACCES` mit
  kurzem Backoff wiederholen (synchron z. B. `Atomics.wait` 10…400 ms, ≈ 1,6 s gesamt wie
  `DEFAULT_RETRY_DELAYS_MS`) und erst danach `listening` melden; Gegenprobe: Datei 10× unter Last
  (L1 aus FLAKES.md) grün.

### SOLLTE (vor WP-22)

#### R2-02 [SOLLTE] Waisen-Bereinigung: „Abfrage gescheitert/zu langsam“ gilt als „Prozess weg“ – und blockiert den Start bis ≈ 40 s
- **Fundstelle:** `src/server/lib/process.ts:305-339` (`processInfo`: Timeout 20 s, `exitCode ≠ 0`,
  leere/ungültige Ausgabe → `null`), `:361-395` (`childProcesses` → `[]`),
  `src/server/sessions/recovery.ts:82-98`, `src/server/sessions/manager.ts:390-396` (Record wird
  **immer** entfernt), `src/server/sessions/runtime.ts:460-463` (`await s.orphanCleanup` im
  Lifecycle-Lock, vor `process_starting`).
- **Befund:** `null` steht sowohl für „gibt es nicht“ als auch für „PowerShell lief in den Timeout /
  ist per Policy gesperrt (AppLocker, Constrained Language Mode auf dem Firmenrechner) / Ausgabe
  unlesbar“. Im zweiten Fall wird ein noch laufender `claude.exe` als `gone` verbucht, nach leerem
  Kinder-Ergebnis der Record gelöscht – die Waise wird nie mehr gefunden (B „Waisen … beim Start
  aufgeräumt“, C.8). FLAKES.md hat unter Last bis ≈ 23 s je Aufruf gemessen (Default 20 s). Zugleich
  wartet ein `session.resume`/`sendPrompt` direkt nach dem Serverstart auf beide Abfragen (bis ≈ 2 ×
  20 s), ohne dass die UI etwas sieht (keine Fakten-Änderung vor dem Warten). Je Record laufen zwei
  PowerShell-Prozesse, alle Records parallel – eine CPU-Spitze genau beim Start (Edge-Fenster, Hub).
- **Fix (Owner WP-11 für `lib/process.ts`, WP-13b für `recovery.ts`/`manager.ts`/`runtime.ts`):**
  1. Ergebnis dreiwertig: `{kind:'found', info} | {kind:'missing'} | {kind:'unknown', reason}`
     (Timeout, Exit ≠ 0, Parse-Fehler); bei `unknown` Record **behalten**, `warn` loggen (optional
     Host-Warnung), beim nächsten Start erneut prüfen.
  2. Vorfilter `isProcessAlive(pid)` (sofort): tot → nur Kinder-Pfad; lebt → Identität prüfen.
  3. **Eine** gebündelte CIM-Abfrage für alle Records (`ProcessId = a OR … OR ParentProcessId = a OR
     …`, Probe ≈ 2,8 s statt 2 × 2,4 s je Record), Timeout beim Start großzügig (60 s, läuft im
     Hintergrund).
  4. Den wartenden Start sichtbar machen (`process_starting` vor `await orphanCleanup`) oder das
     Warten auf die Bereinigung nur für Einträge mit eigenem Record (ist schon so) und mit Obergrenze.
  Tests: Timeout/Fehler → Record bleibt, `unknown` wird geloggt; ein Aufruf für mehrere Records.

#### R2-03 [SOLLTE] Kinder-Pfad der Waisen-Bereinigung ist nicht gegen PID-Wiederverwendung geschützt
- **Fundstelle:** `src/server/sessions/recovery.ts:93-106` (Fenster `[recordedAt − 5 s,
  serverStartedAt]`), Kommentar `:80` („A PID reused by another program is never touched“).
- **Befund:** Ist der aufgezeichnete `claude.exe` tot, werden alle Prozesse mit `ParentProcessId =
  pid` beendet (`taskkill /T /F`), die nach dem alten Start und vor diesem Server starteten. Das
  Fenster ist nach oben offen bis zum Neustart – nach einem Absturz am Freitag und Start am Montag
  kann die PID dazwischen von einem fremden Prozess benutzt worden sein, der Kinder startete und
  selbst endete; dessen Kinder (Build, Editor-Helfer …) würden samt Baum getötet. Der Kommentar gilt
  nur für den Hauptpfad. WP-13 §7 wollte genau diese Heuristik „nach WP-22 entscheiden“; 13b hat sie
  per R1-Hinweis schon aktiviert. WP-22 prüft die Waisen-Bereinigung live auf dem Nutzerrechner.
- **Fix (Owner WP-13b, Entscheidung Koordinator):** Obergrenze = letzter Zeitpunkt, an dem der alte
  Server sicher lebte: Herzschlag in `processes.json` (z. B. `aliveAt` je Record, alle 60 s und bei
  jedem `add` geschrieben; Feld mit Default, kein Versionssprung) oder ersatzweise mtime von
  `sessions.json`/`processes.json` + 60 s Toleranz; Kinder nur, wenn `child.startedAt ≤ aliveAt +
  Toleranz`. Bis dahin `childProcesses` im Manager-Default abschalten (`proc.childProcesses`
  undefined) und den Kommentar korrigieren. Test: Kind nach `aliveAt` → nicht beendet.

#### R2-04 [SOLLTE] Bereitschaft hängt an einem 15-s-Timeout ohne zweiten Versuch – Session bleibt `starting`
- **Fundstelle:** `src/server/backend/sdkBackend.ts:521-523` (`supportedModels` mit `controlMs`
  15 s), `:314-324` (`applyAfterReady` mit demselben Timeout), `src/server/sessions/runtime.ts:425-438`
  (Fehler nur geloggt, kein synthetisches `idle`, kein erneuter Versuch).
- **Befund:** `supportedModels()` wartet im SDK auf den `initialize`-Handshake (`sdk.mjs`:
  `(await this.initialization).models`) und ist das einzige Signal, mit dem ein **ohne Prompt**
  gestarteter Prozess (`session.resume`, Auto-Retry) `starting` verlässt (§2.3 Nr. 6). Ein Kaltstart
  (erster Start nach dem Booten, Virenscanner auf der großen `claude.exe`, langsame Plugins) kann
  15 s überschreiten; danach bleibt die Session dauerhaft `starting` (Spinner), bis der Nutzer
  zufällig einen Prompt sendet; `autoCompactWindow` bei Settings-Datei wird dann nie gesetzt (C.1).
  Der Pfad ist ungetestet (kein Test zu einem abgelehnten `supportedModels` in `src/server/sessions`).
- **Fix (Owner WP-13c für den Timeout, WP-13b für `ready()`):** eigenes Bereitschafts-Timeout
  (z. B. `readyMs: 60_000`, wie `contextFullMs`) für `supportedModels`/`applyAfterReady`; in
  `ready()` bei `TimeoutError` einmal erneut versuchen und, falls der Prozess lebt und noch kein
  `session_state` kam, nach dem zweiten Fehlschlag `idle` setzen oder die Session mit
  `CLAUDE_CONTROL_FAILED` in `error` schicken (nicht still in `starting` lassen). Test mit
  Fake-Session, deren `supportedModels` ablehnt bzw. erst nach `advance()` antwortet.

#### R2-05 [SOLLTE] Kein exklusiver Schutz gegen zwei Server auf demselben `PARALLAX_HOME`
- **Fundstelle:** `docs/wp/WP-21.md:118-119` („optional vor dem Öffnen der Stores“),
  `docs/wp/WP-13b.md:157` (`manager.start()` vor `listen`), `src/server/launcher/launcher.ts:127-152`.
- **Befund:** Starten zwei Launcher gleichzeitig (Doppelklick), sehen beide kein Lockfile und starten
  je einen Server. Beide öffnen die Stores und laufen durch `manager.start()` – Recovery schreibt
  `sessions.json`, hängt Korrektur-Zeilen an Transkripte, die Waisen-Bereinigung ändert
  `processes.json` und beendet Prozesse –, **bevor** der Verlierer am `listen` mit `EADDRINUSE`
  scheitert. Ein von Hand gestarteter zweiter Server mit anderem `--port` (oder `pnpm dev:live` mit
  `--home` auf das echte Home) läuft sogar dauerhaft als zweiter Writer (JsonStore: „ein Writer“, B
  „Persistenz“; Plan „nie zwei Writer“). Das Lockfile schützt nur den Launcher-Pfad und erst nach
  `listen`.
- **Fix (Owner WP-20 `main.ts`, Helfer WP-21 `launcher/`):** vor dem Öffnen des ersten Stores einen
  **exklusiven Mutex je Home** nehmen: Named Pipe `\\.\pipe\parallax-<sha256(windowsPathKey(home))
  .slice(0,16)>` per `net.createServer().listen(pipe)` (Probe: zweites `listen` → `EADDRINUSE`, wird
  beim Prozessende automatisch frei – kein Stale-Zustand). `EADDRINUSE` → Meldung + Exit 5
  (`SERVER_EXIT_CODES.alreadyRunning`); der Launcher behandelt 5 schon (`launcher.ts:294-310`).
  Helfer z. B. `acquireHomeLock(home): Promise<{release()} | null>` in `launcher/homeLock.ts` mit Test
  (zwei Prozesse, gleiche/andere Schreibweise des Pfads).

### NIT

#### R2-06 [NIT] Shutdown-Zusammenspiel WP-21 ↔ WP-13b: doppeltes `dispose`, serielle Kills
- **Fundstelle:** `docs/wp/WP-21.md:133` (Schritt `backend.dispose()`), `src/server/sessions/manager.ts:437-444`
  (hängende PIDs nacheinander, je `taskkill` bis 15 s), `:457` (`backend.dispose()` im Manager).
- **Befund:** Das Beispiel in WP-21 ruft `backend.dispose()` als eigenen Schritt, der Manager tut es
  bereits (harmlos, aber zwei Besitzer einer Aufgabe). Die Kills nach dem 15-s-Deckel laufen seriell;
  mit mehreren hängenden Sessions kann `manager.shutdown()` die 20 s von `sessionsTimeoutMs`
  überschreiten, dann laufen die WP-21-Schritte (Stores schließen) parallel zum Rest des Managers.
- **Fix:** WP-20 verdrahtet `dispose` nur einmal (Manager), WP-21.md-Beispiel anpassen; Kills im
  Manager parallel (`Promise.allSettled`). Owner WP-20/WP-13b.

#### R2-07 [NIT] `sendPrompt` nach einem synchronen Spawn-Fehler meldet `SESSION_NOT_RUNNING` statt `CLAUDE_SPAWN_FAILED`
- **Fundstelle:** `src/server/sessions/runtime.ts:592-598`, `src/server/backend/sdkBackend.ts:279-287`.
- **Befund:** Scheitert der Spawn synchron (z. B. `expectedCommand`), ist die Session schon beendet,
  wenn `deliverPrompt` direkt nach `startRuntime` sendet; der Befehl scheitert mit
  `SESSION_NOT_RUNNING {reason:'closed'}`, der eigentliche Code erscheint erst im Status. §3.5.6
  verlangt „Fehler → Befehlsfehler“.
- **Fix:** nach `backend.start()` prüfen, ob die Session bereits endete (`agent.pid === null` und
  `send` wirft) und dann `CLAUDE_SPAWN_FAILED` werfen (Grund aus dem `error`-Event). Owner WP-13b.

#### R2-08 [NIT] Ruhendes `session.rename` wartet nicht auf die Waisen-Bereinigung
- **Fundstelle:** `src/server/sessions/commands.ts:292-306`.
- **Befund:** `renameSession` schreibt ins Claude-JSONL (C.6). Direkt nach einem Serverstart kann
  dort noch ein verwaister `claude.exe` laufen – der Start wartet deshalb auf `orphanCleanup`

### Verdrahtung für WP-20c (`src/server/main.ts`)

```ts
import { SERVER_EXIT_CODES } from './launcher/exitCodes';
import { logHomeAccess } from './lib/homeAccess';
import { acquireHomeLock, type HomeLockResult } from './lib/homeLock';

const config = loadConfig();
// 1. VOR initLogging und vor dem ersten Store (Registry, Settings, Auth-Secret, processes.json …):
let homeLock: HomeLockResult;
try {
  homeLock = await acquireHomeLock(config.home);   // legt das Home an
} catch (error) {                                  // unsicherer Pfad / unerwarteter Pipe-Fehler
  process.stderr.write(`Parallax: the data folder ${config.home} cannot be locked: ${String(error)}\n`);
  process.exit(SERVER_EXIT_CODES.failure);
}
if (homeLock.kind === 'busy') {
  // Ein anderer Server nutzt dieses Home (anderer Port, Doppelklick, dev:live). Der Launcher sucht
  // nach Exit 5 den Gewinner und öffnet dort ein Fenster.
  process.stderr.write(`Parallax: another Parallax server already uses ${config.home}.\n`);
  process.exit(SERVER_EXIT_CODES.alreadyRunning);  // 5
}
// 2. initLogging, Stores, openProcessStore, Manager, manager.start() (Waisen laufen im Hintergrund),
//    listen, writeServerLock – wie in WP-13b.md/WP-21.md.
// 3. Nach listen, im Hintergrund (≈ 2 s PowerShell, wirft nie):
void logHomeAccess(config.home);
// 4. Shutdown-Schritte: … 'stores' → 'lock' (lock.release()) → 'homeLock' (homeLock.lock.release())
//    → 'logging'. KEIN eigener Schritt backend.dispose() – das macht manager.shutdown() (R2-06).
```

- Ein Prozessende (auch Absturz/`taskkill`) gibt den Home-Lock frei; `release()` ist idempotent.
- `pnpm dev` (`--home=.parallax-dev`) bekommt den Lock ebenfalls: ein zweites `pnpm dev` im selben
  Checkout endet mit 5; Worktrees haben eigene `.parallax-dev`-Ordner. E2E mit Temp-Homes ist frei.
- Sonst nichts zu verdrahten: Waisen-Prüfung, Bereitschaft und Code-Retry stecken in Manager,
  Backend bzw. Launcher.
