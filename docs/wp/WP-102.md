## 102a – Pfad-Regelsätze (fertig)
- `PathFlavor = 'win32' | 'posix'`, `pathFlavorOf(platform)` (`win32` → `win32`, alles andere → `posix`).
- `PathRules` mit `flavor`, `separator`, `maxLength`, `issue`, `isSafe`, `nameIssue`, `key`, `equal`, `isInside`,
  `resolve`, `baseName`, `extension`, `join`, `isAbsolute`; Instanzen `WIN32_PATHS` (delegiert an die unveränderten
  `windows*`-Funktionen) und `POSIX_PATHS`; `pathRules(flavor)`.
- POSIX-Funktionen: `posixPathIssue`, `isSafePosixPath`, `posixNameIssue`, `posixPathKey`, `posixPathsEqual`,
  `isPosixPathInside`, `resolvePosixPath`, `posixBaseName`, `posixPathExtension`; `POSIX_PATH_MAX_BYTES` (4095),
  `POSIX_NAME_MAX_BYTES` (255).
- **POSIX-Regeln** (Präzisierung von WP-100 E6): absolut (`/…`), keine Steuerzeichen, keine `.`/`..`-Segmente, Länge in
  UTF-8-Bytes (Pfad ≤ 4095, Segment ≤ 255), **groß/klein unterscheidend**; erlaubt sind `:` `?` `*` `"` `<` `>` `|`,
  Punkt oder Leerzeichen am Ende und Namen wie `CON`. Neuer Grund **`pseudo_fs`** in `PATH_ISSUES` für `/proc`, `/sys`,
  `/dev` und darunter. `/run` bleibt erlaubt (dort liegen u. a. Mounts des Benutzers); Sockets, FIFOs und Geräte fängt
  die Regel „nur reguläre Dateien lesen“ in `lib/paths.ts` ab (WP-103).
- Der Schlüssel fasst `/` zusammen und entfernt den Schluss-`/` außer bei `/`; `//server/share` ist unter Linux ein
  gewöhnlicher Pfad (`/server/share`).

## 102b – Schemas, Shells, Plattform und Fähigkeiten
- **Editor** (`model.ts`): `editorExecutableIssue(executable, rules = WIN32_PATHS)` – unter Windows wie heute (absolute
  `.exe`, Sperrliste); unter POSIX absolut und sicher, Sperrliste nach Basisname (Shells, Interpreter, Terminal-
  Emulatoren). `editorSettingsSchema` prüft im Schema nur noch Länge und Steuerzeichen; die plattformgenaue Prüfung
  macht der Server beim Speichern (`settings.update`) und die UI mit den Regeln des Hosts.
  `isDefaultProgramAllowed(path, rules = WIN32_PATHS)`.
- **Konsole** (`model.ts`): `consoleSettingsSchema.gitDir` wie Editor (Schema: Länge/Steuerzeichen, Server prüft;
  unter Linux immer `null`).
- **Shells:** `SHELL_KINDS` um `login`, `bash`, `zsh`, `fish`, `pwsh` erweitert. `shell.detect` liefert zusätzlich
  `shells: ShellKind[]` (auf diesem Host verfügbar, Reihenfolge = Anzeige). Der Server ersetzt beim Laden eine
  `defaultShell`, die es auf dem Host nicht gibt, durch den Standard der Plattform (Windows `cmd`, Linux `login`).
- **Host-Fähigkeiten** (`hostStateSchema`): neues Feld `capabilities` mit Default für ältere Server (die alle Windows
  sind): `{desktop, externalConsole, shellWindow, editor, fileManager, autostart, protocolHandler}` – Linux im
  Server-Modus meldet alles außer den Session-Features als `false`; die UI blendet danach aus (ersetzt die
  Plattformprüfung im Web).
- **`PROTOCOL_VERSION` 6 → 7:** Neue Enum-Werte (`ShellKind`) gehen über den Draht; ältere Parser würden sie
  verwerfen. Gekoppelte Rechner müssen ohnehin dieselbe App-Version haben (`hosts/link.ts:550`,
  `remote/headers.ts:25`); der Sprung schränkt also nichts zusätzlich ein.

## 102c – „Verwalten“, Terminal über den Vermittler, Launcher-Endpunkte
- **Stufe je Kopplung** (`model.ts`): `REMOTE_PEER_LEVELS = ['control', 'manage']`; `remotePeerSchema.level` mit Default
  `'control'` (persistiert, `schemaVersion` bleibt 1, Default nach CLAUDE.md).
- **Freigaben** (`protocol.ts`):
  - `REMOTE_MANAGE_COMMANDS`: `settings.update`, `server.shutdown`, `profile.*`, `update.*`, `multiHost.configure`,
    `remoteAccess.*` (Kopplung, Schlüssel, Ereignisse). `isRemoteAllowedCommand(name, level = 'control')`.
  - Weiter immer gesperrt: `session.openExternal`, `session.consoleCommand`, `file.open`, `editor.detect`,
    `link.open`, `session.openShell`, `hosts.*`.
  - `shell.detect` wird für jede Stufe erlaubt (E3).
  - Neu `remoteAccess.setPeerLevel {peerId, level}` (lokal oder mit `manage`; die eigene Kopplung herabzustufen fragt
    die UI nach).
  - `remoteAccess.pair` bekommt `level` (Default `'control'`): Der Code des Kopplungsfensters bindet die Stufe.
- **Was der steuernde Rechner sieht:** Die Begrüßung der Fernverbindung meldet `access: 'control' | 'manage'`; die UI
  zeigt Einstellungen, Profile und Updates eines anderen Rechners nur bei `manage`.
- **Terminal über den Vermittler** (`http.ts`): `HOST_API_PATHS.terminalWs = '/api/hosts/:hostId/terminal/ws'`,
  `hostTerminalWsPath(hostId)`; die Route des freigebenden Rechners nimmt Verbindungen gekoppelter Rechner an (jede
  Stufe, E3). `session.openShell` (sichtbares Fenster) bleibt gesperrt.
- **Launcher-Endpunkte für die Kommandozeile** (`http.ts`, Bearer-Launcher-Token wie `launcherCode`, ohne Origin):
  `POST /api/launcher/remote` mit `{action: 'status' | 'enable' | 'disable' | 'pair' | 'unpair', level?, peerId?, all?}`.
  Die Antwort auf `pair` enthält den formatierten Code nur für das aufrufende Terminal.
  `parallax service …` (systemd) braucht keinen Server und keinen Contract.
- **Ereignisprotokoll** (`remote/eventLog.ts`, Typen in `model.ts`): neue Ereignisse `level_changed`, `manage_command`
  (Name des Befehls, nie Inhalte).
- **Ergänzung der Sicherheitsspezifikation:** neuer Abschnitt `docs/wp/WP-76.md` §B.13 „Stufen und Terminal (WP-102)“
  vor der Umsetzung: Schutzgüter, was `manage` freigibt, Bindung an den Kopplungscode, Ereignisse, Terminal über den
  Vermittler (Wächter, Grenzen, keine Eingaben im Log), Restrisiko „übernommener steuernder Rechner“.
