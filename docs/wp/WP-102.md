## 102a – Pfad-Regelsätze (fertig)
- `PathFlavor = 'win32' | 'posix'`, `pathFlavorOf(platform)` (`win32` → `win32`, alles andere → `posix`).
- `PathRules` mit `flavor`, `separator`, `maxLength`, `issue`, `isSafe`, `nameIssue`, `key`, `equal`, `isInside`,
  `resolve`, `baseName`, `extension`, `join`, `isAbsolute`; Instanzen `WIN32_PATHS` (delegiert an die unveränderten
  `windows*`-Funktionen) und `POSIX_PATHS`; `pathRules(flavor)`.
- POSIX-Funktionen: `posixPathIssue`, `isSafePosixPath`, `posixNameIssue`, `posixPathKey`, `posixPathsEqual`,
  `isPosixPathInside`, `resolvePosixPath`, `posixBaseName`, `posixPathExtension`; `POSIX_PATH_MAX_BYTES` (4095),
  `POSIX_NAME_MAX_BYTES` (255).
- **POSIX-Regeln** (Präzisierung von WP-100 E6): absolut (`/…`), keine Steuerzeichen, keine `.`/`..`-Segmente, Länge in
  UTF-8-Bytes (Pfad ≤ 4095, Segment ≤ 255), **groß/klein unterscheidend**; erlaubt sind `:` `?` `*` `"` `<` `>` `|`,
  Punkt oder Leerzeichen am Ende und Namen wie `CON`. Neuer Grund **`pseudo_fs`** in `PATH_ISSUES` für `/proc`, `/sys`,
  `/dev` und darunter. `/run` bleibt erlaubt (dort liegen u. a. Mounts des Benutzers); Sockets, FIFOs und Geräte fängt
  die Regel „nur reguläre Dateien lesen“ in `lib/paths.ts` ab (WP-103).
- Der Schlüssel fasst `/` zusammen und entfernt den Schluss-`/` außer bei `/`; `//server/share` ist unter Linux ein
  gewöhnlicher Pfad (`/server/share`).

## 102b – Schemas, Shells, Plattform und Fähigkeiten (fertig)
- **Editor** (`model.ts`): `editorExecutableIssue(executable, rules = WIN32_PATHS)` – unter Windows wie heute (absolute
  `.exe`, Sperrliste); unter POSIX absolut und sicher, Sperrliste nach Basisname (Shells, Interpreter, Terminal-
  Emulatoren). `editorSettingsSchema` prüft im Schema nur noch Länge und Steuerzeichen; die plattformgenaue Prüfung
  macht der Server beim Speichern (`settings.update`) und die UI mit den Regeln des Hosts.
  `isDefaultProgramAllowed(path, rules = WIN32_PATHS)`.
- **Konsole** (`model.ts`): `consoleSettingsSchema.gitDir` wie Editor (Schema: Länge/Steuerzeichen, Server prüft;
  unter Linux immer `null`).
- **Shells:** `SHELL_KINDS` um `login`, `bash`, `zsh`, `fish`, `pwsh` erweitert. `shell.detect` liefert zusätzlich
  `shells: ShellKind[]` (auf diesem Host verfügbar, Reihenfolge = Anzeige). Der Server ersetzt beim Laden eine
  `defaultShell`, die es auf dem Host nicht gibt, durch den Standard der Plattform (Windows `cmd`, Linux `login`).
- **Host-Fähigkeiten** (`hostStateSchema`): neues Feld `capabilities` mit Default für ältere Server (die alle Windows
  sind): `{desktop, externalConsole, shellWindow, editor, fileManager, autostart, protocolHandler}` – Linux im
  Server-Modus meldet alles außer den Session-Features als `false`; die UI blendet danach aus (ersetzt die
  Plattformprüfung im Web).
- **`PROTOCOL_VERSION` 6 → 7:** Neue Enum-Werte (`ShellKind`) gehen über den Draht; ältere Parser würden sie
  verwerfen. Gekoppelte Rechner müssen ohnehin dieselbe App-Version haben (`hosts/link.ts:550`,
  `remote/headers.ts:25`); der Sprung schränkt also nichts zusätzlich ein.

### Ergebnis 102b (20.11.2026)
Umgesetzt wie oben, mit diesen Präzisierungen:
- **Editor-Schema nach Pfadform statt nur Länge:** `editorSettingsSchema` prüft den Pfad mit den Regeln seiner eigenen
  Form (`pathFlavorOfShape` in `@shared/paths`: `/…` = POSIX, sonst Windows). Ein Windows-Pfad wird damit im Schema
  genauso streng geprüft wie bisher; ein POSIX-Pfad nach den POSIX-Regeln. Die Host-Prüfung kommt zusätzlich:
  `assertHostSettings` in `sessions/commands.ts` (vor `settings.update`, `HOST_PATH_RULES` aus `server/lib/paths.ts`)
  → `VALIDATION_FAILED {field: 'editor.executable', reason}`; `editorIssues(draft, rules = WIN32_PATHS)` im Web (die
  Regeln des bearbeiteten Hosts reicht WP-104 durch). Beim Start prüft `files/editors.ts` weiter mit den
  Windows-Regeln (WP-106 stellt auf die Host-Regeln um).
- **POSIX-Sperrliste** `EDITOR_BLOCKED_POSIX_EXECUTABLES`: Shells, Interpreter, Programme, die ein anderes Programm
  starten (`env`, `sudo`, `setsid`, `flatpak` …), Terminal-Emulatoren, Öffner (`xdg-open`, `gio` …). Vergleich
  ohne Groß-/Kleinschreibung, eine Versionsendung wie `python3.12` zählt nicht.
- **`gitDir` bleibt Windows-streng** (Abweichung vom Plan): Das Feld meint nur den Ordner von Git for Windows; ein
  Linux-Host lässt es `null`, die UI blendet es dort aus (WP-104).
- **Shells:** `WINDOWS_SHELL_KINDS`, `POSIX_SHELL_KINDS`, `shellKindsFor(flavor)`, `defaultShellFor(flavor)`.
  `shell.detect.shells` ist im Schema mit den drei Windows-Shells vorbelegt. Die UI (Kopfzeile, Session-Menü, leeres
  Terminal, Einstellungen) zeigt bis WP-104/105 weiter die drei Windows-Shells. Alle Wörterbücher kennen die neuen
  Namen. Unter Windows lehnt `resolveShellLaunch` die Linux-Shells mit `SHELL_NOT_FOUND` ab; das Ersetzen einer
  fremden `defaultShell` beim Laden kommt mit WP-105.
- **Fähigkeiten:** `hostCapabilitiesSchema`, `HostCapabilities`, `WINDOWS_HOST_CAPABILITIES` (alles `true`).
  `SessionManager` meldet `deps.host.capabilities ?? WINDOWS_HOST_CAPABILITIES`; die Linux-Werte ermittelt WP-103 in
  `server/lib`, die Komposition (`app/compose.ts`) reicht sie durch.

## 102c – „Verwalten“, Terminal über den Vermittler, Launcher-Endpunkte (fertig)
Normativ ist `docs/wp/WP-76.md` §B.13 (Stufen und Terminal) und §B.14 (Schlüsselspeicher unter Linux), beide am
20.11.2026 vor der Umsetzung geschrieben. Präzisiert gegenüber dem ersten Entwurf: Ein freigebender Rechner hat genau
**eine** Kopplung (`remotePeerFileSchema.peer`), also kein `peerId`; `remoteAccess.pair` bleibt auch mit `manage`
lokal (§B.2 Nr. 7: der Code nie an ein Fenster über den Fernzugang).
- **Stufe der Kopplung** (`model.ts`): `REMOTE_PEER_LEVELS = ['control', 'manage']`, `remotePeerLevelSchema`;
  `remotePeerRecordSchema.level` mit Default `'control'` (persistiert, `schemaVersion` bleibt 1) und
  `remotePeerSchema.level` (Anzeige; Default `'control'`).
- **Freigaben** (`protocol.ts`):
  - `REMOTE_MANAGE_COMMANDS`: `settings.update`, `server.shutdown`, `profile.*`, `update.*`, `multiHost.configure`,
    `remoteAccess.unpair`, `remoteAccess.renewKey`, `remoteAccess.check`, `remoteAccess.events`,
    `remoteAccess.eventsSeen`, `remoteAccess.setPeerLevel`. `isRemoteAllowedCommand(name, level = 'control')`.
  - Weiter immer gesperrt: `remoteAccess.pair`, `remoteAccess.cancelPairing`, `session.openExternal`,
    `session.openShell`, `session.consoleCommand`, `file.open`, `editor.detect`, `link.open`, `hosts.*`.
  - `shell.detect` wird für jede Stufe erlaubt (E3, braucht das Terminal).
  - Neu `remoteAccess.setPeerLevel {level}` (lokal in beide Richtungen; aus der Ferne nur mit `manage` und nur herab;
    die Regel prüft der Server, der Contract erlaubt den Befehl für `manage`).
  - `remoteAccess.pair` bekommt `level` (Default `'control'`).
- **Begrüßung** (`protocol.ts`): `helloSchema.access: 'local' | 'control' | 'manage'` (Default `'local'`).
- **Terminal über den Vermittler** (`http.ts`): `HOST_API_PATHS.terminalWs = '/api/hosts/:hostId/terminal/ws'`,
  `hostTerminalWsPath(hostId)`, `REMOTE_PATHS.terminalWs = '/remote/v1/terminal/ws'`. Der Kommentar bei
  `API_PATHS.terminalWs` („nie in `HOST_API_PATHS`“) wird ersetzt.
- **Launcher-Endpunkt für die Kommandozeile** (`http.ts`): `API_PATHS.launcherRemote = '/api/launcher/remote'`,
  `launcherRemoteRequestSchema` = `{action: 'status'}` | `{action: 'enable'}` | `{action: 'disable'}` |
  `{action: 'pair', level}` | `{action: 'cancel'}` | `{action: 'unpair'}` | `{action: 'level', level}`;
  `launcherRemoteResponseSchema` = `{remoteAccess: RemoteAccessState | null, code: string | null}` (`code` nur bei
  `pair`). `parallax service …` (systemd) braucht keinen Server und keinen Contract.
- **Ereignisprotokoll** (`model.ts`): `REMOTE_EVENT_KINDS` um `level_changed`, `manage_command`, `terminal_opened`;
  `remoteEventSchema` bekommt `detail: string | null` (Default `null`; Befehlsname bzw. `control→manage`, nie Inhalte).

### Ergebnis 102c (20.11.2026)
Umgesetzt wie oben, mit diesen Präzisierungen:
- **Drei Listen:** `REMOTE_ALLOWED_COMMANDS` (jede Stufe, neu mit `shell.detect`), `REMOTE_MANAGE_COMMANDS`,
  `REMOTE_DENIED_COMMANDS`; jeder Befehl steht in genau einer (Test). `isRemoteAllowedCommand(name, level =
  'control')`; Hub und Web rufen es noch ohne Stufe auf, also unverändert `control`.
- **`remoteAccess.pair.level` ist optional** (fehlt = `control`) statt mit Default: Bestehende Aufrufer bleiben gültig.
- **`connectionAccessSchema`** (`CONNECTION_ACCESS = ['local', 'control', 'manage']`) für `hello.access`; der Hub
  meldet heute `local` bzw. für Fernverbindungen `control`.
- **`launcherRemoteResponseSchema`** hat zusätzlich `expiresAt` (Ende des Kopplungsfensters, nur bei `pair`).
- **`remoteAccess.setPeerLevel`** ohne Kopplung → `VALIDATION_FAILED {reason:'not_paired'}`, gleiche Stufe → nichts;
  der Server-Handler kommt mit WP-107 (bis dahin `NOT_IMPLEMENTED`), der Fake-Host (`fake-multi-host.ts`) kann ihn.
- Vorläufige Werte bis WP-107: Der Peer-Eintrag einer neuen Kopplung bekommt `level: 'control'`, Ereignisse
  `detail: null`. Texte der neuen Ereignisse im Verbindungsprotokoll (de/en).
