### Anforderungen (normativ)
1. **Ordner-Browser (ADR-119, §4.12):** `path === null` → Wurzeln: Laufwerke `A:`…`Z:` (je `stat` von
   `X:\` mit `driveTimeoutMs` 1500, langsame/fehlende überspringen), dazu `kind:'home'` =
   `os.homedir()`. Sonst: `windowsPathIssue` → `PATH_REJECTED{reason}`; `assertNoUnsafeLink`
   (jedes Segment `lstat`; Link → `readlink`, Ziel mit `windowsPathIssue` → `PATH_REJECTED{reason:
   'link_target'}`); `readdir(withFileTypes)`; nur Ordner und Links auf Ordner (Link-Ziel ebenso
   geprüft, unsichere Links weglassen); `hidden` = Punkt-Name oder `$Recycle.Bin`, `System Volume
   Information`, `$WinREAgent`, `Recovery`, `Config.Msi`; ohne `showHidden` weggelassen; sortiert
   case-insensitiv; > `LIMITS.fsListMax` → `truncated`. `parent` = übergeordneter Ordner bzw. null an der
   Laufwerkswurzel. Fehler: ENOENT → `CWD_NOT_FOUND`, kein Ordner → `CWD_NOT_DIRECTORY`,
   EACCES/EPERM → `FOLDER_NOT_READABLE`. Pfade exakt aus Eingabe + Name (kein `realpath`).
   `checkCwd`/`resolveAllowedPath` nutzen `assertNoUnsafeLink` ebenfalls (R1-17 erledigt).
2. **Upload (ADR-103):** Route `POST /api/attachments` (Klasse „mutation“, Guard unverändert):
   Content-Type-Parser nur für `ATTACHMENT_MEDIA_TYPES` (Buffer, `bodyLimit = LIMITS.imageBytes`),
   anderer Typ → 415 `UNSUPPORTED_MEDIA_TYPE`, zu groß → 413 `PAYLOAD_TOO_LARGE`, Query per
   `attachmentUploadQuerySchema` (400 `VALIDATION_FAILED`), Magic-Bytes (PNG `89 50 4E 47`, JPEG
   `FF D8 FF`, GIF `GIF87a/GIF89a`, WebP `RIFF….WEBP`) passend zum Content-Type, sonst 415.
   `blobs.put(data, mediaType, name ?? null, size)` → 200 `attachmentUploadResponseSchema`.
   `BlobStore.put` speichert `width`/`height` in der Meta-Datei.
3. **Port (ADR-111):** `loadConfig` liest `<home>/settings.json` nur lesend (`settingsFileSchema`;
   neuere Version/ungültig → ignorieren, Hinweis über ein neues Feld `ServerConfig.notes: string[]`,
   das `main.ts` (WP-40) und der Launcher loggen); Rangfolge wie oben; Launcher und Server identisch
   (Test). Neu außerdem `ServerConfig.systemIntegration: 'auto' | 'on' | 'off'` (Flag
   `--system-integration`, Env `PARALLAX_SYSTEM_INTEGRATION`, Default `auto`; unter Vitest bzw.
   `NODE_ENV=test` immer `off`, auch wenn `on` verlangt ist – `ConfigError` bei `on` im Test), vom
   Launcher an den Server durchgereicht (`serverArgsFor`).
4. **Konsole (ADR-104):** `createConsoleLauncher().open(spec)`: `runFile(systemTool(
   'WindowsPowerShell\\v1.0\\powershell.exe'), ['-NoProfile','-NonInteractive','-ExecutionPolicy',
   'Bypass','-EncodedCommand', <konstantes Skript>], { env: {...spec.env, PARALLAX_CONSOLE_EXE,
   PARALLAX_CONSOLE_ARGS: windowsCommandLine(spec.args), PARALLAX_CONSOLE_CWD}, timeoutMs: 30_000 })`.
   Skript: Werte lesen, die drei Variablen aus der eigenen Umgebung entfernen, `Start-Process
   -FilePath $exe -ArgumentList $line -WorkingDirectory $cwd -PassThru` (ohne `-ArgumentList`, wenn
   leer), Ausgabe `pid=<n>;start=<ISO>`; Fehler → Exit 3 mit Grund → `{kind:'failed', reason}`.
   `state(proc)`: `isProcessAlive(pid)` (tot → `ended`), bei bekannter Startzeit Vergleich mit
   `processStartTime` (± 5 s, sonst `ended`), Abfragefehler → `unknown`. Kein `cmd`, keine Shell.
   `windowsCommandLine` tabellengetestet (Leerzeichen, `"`, Backslashes vor `"`, leere Args, Umlaute).
5. **Fake-Konsole:** `createFakeConsoleLauncher`: `open` liefert eine synthetische PID (≥ 50 000) und
   ruft `onRun(spec)`; `state` = `running` bis `runMs` vergangen, dann `ended`.
6. **Autostart (ADR-110):** Verknüpfung `Parallax.lnk` in `<APPDATA>\Microsoft\Windows\Start
   Menu\Programs\Startup` (Pfad aus `env.APPDATA`, im Test ein Temp-Ordner), erzeugt/entfernt per
   PowerShell + `WScript.Shell` (Skript konstant, Daten per Env), `TargetPath` = `node`,
   `Arguments` = `windowsCommandLine(args)`, `WorkingDirectory` = Repo, `WindowStyle` 7.
   `launcherCommand(repoRoot, ['--autostart'])` = `realpath(process.execPath)` + `[<repo>\node_modules\
   tsx\dist\cli.mjs, '--tsconfig', <repo>\src\server\tsconfig.json, <repo>\src\server\launcher\main.ts,
   …extra]`; läuft der Server nicht auf dem Standard-Datenordner (nur mit `--system-integration=on`),
   kommt `--home=<home>` dazu (Autostart und Protokoll-Handler).
7. **Protokoll-Handler (ADR-109):** `HKCU\Software\Classes\parallax` (Default `URL:Parallax`, Wert
   `URL Protocol` leer, `shell\open\command` = `"<node>" <args…> --open "%1"`) über `reg.exe`
   (`lib/registry.ts` additiv `regAddValue`/`regDeleteKey`, `runFile`, System32-Pfad) – entfernen beim
   Abschalten. Nur eigener Schlüssel; vorhandener fremder Schlüssel `parallax` (anderer Befehl) wird
   überschrieben nur, wenn sein Befehl `launcher\main.ts` enthält, sonst `PROTOCOL_HANDLER_FAILED
   {reason:'foreign'}`.
8. **`createSystemIntegration`:** `available === false` → `apply` tut nichts, `toastLaunchUri` = null,
   keine Prozesse. Sonst `apply(settings)` gleicht Autostart (`settings.autostart.enabled`) und
   Protokoll-Handler (`settings.notifications.openOnClick`) ab (nacheinander, nie parallel, nie
   werfend); Fehler → Warnungen `AUTOSTART_FAILED`/`PROTOCOL_HANDLER_FAILED` (`hostWarningSchema`,
   ID `system:autostart` bzw. `system:protocol`), `onChange` danach. `toastLaunchUri(entryId)` =
   `sessionProtocolUri(entryId)`, wenn der Handler zuletzt erfolgreich registriert wurde.
9. **Toast:** `ToastRequest.launchUri` (nur wenn `parseSessionProtocolUri` sie akzeptiert, sonst
   ignoriert) → `<toast activationType="protocol" launch="…">` (per DOM, Daten über Env wie bisher);
   `silent` → `<audio silent="true"/>`.
10. **Launcher:** `--open <uri>`/`--open=<uri>`: `parseSessionProtocolUri`, ungültig → Exit 2 mit
    Meldung, nichts gestartet; sonst normaler Ablauf und Fenster-URL `appUrlWithCode(origin, code,
    {entryId})`. `--autostart`: Server starten (Build-Prüfung wie bisher); Fenster nur, wenn
    `settings.autostart.openWindow` (Settings nur lesend). Usage-Text und `parallax.cmd/.ps1`-Kopf
    nennen die Flags.

### Entscheidungen

- **`--open` muss das letzte Argument sein** (R5): Windows setzt `%1` roh ein; ein Link mit
  `" --home=… "` könnte sonst Optionen anhängen. Alles nach dem Link → Exit 2, nichts gestartet.
- **Zwei Schutzschichten gegen echte Systemänderungen in Tests (R6):** `loadConfig` → `off`;
  zusätzlich `system/run.ts`: ohne injiziertes `run`/`env` verweigert ein Testlauf jeden Aufruf vor
  dem Spawn (leere Umgebung → kein echtes `APPDATA`). `guard.test.ts` prüft das mit einer
  Spawn-Falle (`vi.mock('node:child_process')`) und statisch, dass jeder Test der Integration `run`
  injiziert und niemand `process.env.APPDATA` liest. `readSettingsFile` liest unter Vitest nie im
  echten Datenordner (auch nicht über ein handgebautes `env` – bestehende Launcher-Tests rufen
  `loadConfig` mit `env: {}`).
- **Laufwerke (R8):** höchstens ein `stat` je Laufwerk gleichzeitig; hängt es noch, bekommt der
  nächste Aufruf keinen zweiten (libuv-Threadpool hat 4 Threads).
- Ein Port aus `settings.json` zählt im Launcher als „ausdrücklich“ für den Port-Hinweis (V2-13).
