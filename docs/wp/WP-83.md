# WP-83 – Releases: öffentliches Repo, Versionen, Changelog, Installation und Update (Plan)

Branch `feature/releases` von `main` (`3ce6b12`). **Nur Plan, nichts umgesetzt.** Die Umsetzung beginnt erst nach
Freigabe durch den Nutzer. Grundlage sind zwei Gespräche mit dem Nutzer am 17.11.2026.

## 0. Ausgangslage und Anforderungen

**Heute:** Jede produktive Instanz ist ein Klon von `origin/main`. Zum Aktualisieren beendet der Nutzer den Server,
führt `git pull` und `pnpm install --frozen-lockfile` aus und startet `parallax.cmd`; der Launcher baut `dist/` beim
Start neu. Dafür braucht jeder Rechner git, pnpm und die Dev-Abhängigkeiten, und jeder Rechner baut selbst. Der Nutzer
findet das „irgendwie unschön“.

**Aussagen des Nutzers (17.11.2026)**
- Das Repo `DerXHelp/parallax` ist öffentlich (per `gh repo view` geprüft).
- Node darf auf allen Zielrechnern vorausgesetzt werden (drei Windows-Rechner: privat, Firmenrechner, VM).
- Released wird bewusst über Tags und gern gebündelt; nicht jede Änderung ist ein eigenes Release wert.
- Es braucht Changelogs.
- Entschieden im zweiten Gespräch:
  - Die erste Version ist **1.0.0**.
  - Das Netz sollte auf allen Rechnern durchgehen.
  - Source-Maps kommen mit ins Paket.
  - Die Trennung der Abhängigkeiten in `package.json`/Lockfile ist freigegeben.
  - `CLAUDE.md` wird angepasst.
- **Vor dem ersten Release** prüft der Koordinator das ganze Repo auf private Angaben (Pfade, Namen, womöglich
  Firmennamen) und entfernt sie. Das Repo ist öffentlich und muss „sauber und neutral“ sein. Dieser Schritt gehört zum
  Release-Paket.
- Zur Lizenz wünscht der Nutzer eine Empfehlung mit Recherche (§3.5).

**Anforderungen**

| # | Anforderung |
|---|---|
| R1 | Die Zielrechner brauchen weder git noch pnpm noch einen Build; Node 24 (LTS) oder neuer genügt (§13). |

**Nicht in v1**
- Ein Installer als `.exe`/MSI, winget, eine Authenticode-Signatur.
- Node mitliefern (Single Executable Application). Auf verwalteten Rechnern drohen bei einer unsignierten `.exe`
  SmartScreen- und AppLocker-Probleme.
- Vorabversionen über den Update-Knopf. Vorab-Tags werden gebaut, lassen sich aber nur per Datei installieren
  (§9.6).
- Delta-Updates, macOS/Linux, Updates entfernter Hosts (Multi-Host, WP-75).
- Installieren ohne Klick.

## 1. Bestand und Lücken (Stand `main` `3ce6b12`)
- **Versionen:** `package.json` hat `version` `0.0.0`. Es gibt keinen Tag, kein `CHANGELOG.md`, kein `.github/` und
  keine `LICENSE`.
- **Build-ID:** `<version>+<commit>[.dirty-…]` kommt aus `repo.config.ts` `resolveBuildId` (git, letzter Commit der
  Build-Eingaben). Der Launcher vergleicht sie mit `dist/` und baut bei einer Abweichung neu. Einem Paket fehlen git
  und `repo.config.ts`; die erwartete ID wäre unbekannt, und der Launcher würde bauen wollen.
- **Launcher:** Er läuft per tsx aus `src/server/launcher/main.ts`, und tsx ist eine Dev-Abhängigkeit.
- **`repoRoot`:** Server und Launcher leiten ihn aus der Lage von `dist/` ab (`main.ts`). In einer Installation wäre das
  der Versionsordner: Autostart und Protokoll bekämen dessen Pfad, und Server wie Chrome erbten ihn als
  Arbeitsverzeichnis (`chromeWindow.ts` startet Chrome ohne eigenes `cwd`). Ein offenes Chrome sperrt den Ordner dann
  gegen das Löschen.
- **Server-Bundle:** `dist/server.js` ist mit `packages: 'external'` gebündelt. Zur Laufzeit braucht es aus
  `node_modules`:

  | Paket | Lizenz |
  |---|---|
  | `fastify`, `@fastify/static`, `@fastify/websocket`, `pino`, `pino-roll`, `zod` | MIT |
  | `diff` | BSD-3-Clause |
  | `@anthropic-ai/sdk` (Peer des Agent SDK) | Apache-2.0 |
  | `@modelcontextprotocol/sdk` (Peer des Agent SDK) samt ≈ 17 eigenen Abhängigkeiten | MIT (je Paket in WP-85 prüfen) |
  | `@anthropic-ai/claude-agent-sdk` | **proprietär:** `LICENSE.md` = „© Anthropic PBC. All rights reserved. Use is subject to the Legal Agreements …“ |

  - Das Agent SDK (≈ 5 MB, nur Peer-Abhängigkeiten) importiert beim Laden statisch `@modelcontextprotocol/sdk` und
    `zod/v4`. Das MCP-SDK steht nicht in `package.json`; pnpm installiert es nur als automatischen Peer.
  - `logger.ts` lädt `pino-roll` über eine Variable und `pino-pretty` (Dev-Abhängigkeit) nur im Dev-Modus. Die
    Metadatei von esbuild sieht das erste nicht und meldet das zweite fälschlich.

- **Abhängigkeiten:** `dependencies` enthält auch reine Web-Pakete (React, Radix, shiki, streamdown, lucide …), die
  Vite ohnehin in `dist/web` bündelt. Ein Produktions-Install würde sie unnötig mitnehmen. Das Web-Bundle enthält
  Code und Schriften (Inter, JetBrains Mono: SIL OFL) unter MIT, ISC, Apache und OFL; deren Hinweise fehlen bisher.
- **Autostart und Protokoll-Handler** (`system/autostart.ts`, `system/protocol.ts`) starten
  `node <repo>\node_modules\tsx\dist\cli.mjs --tsconfig … launcher\main.ts`.
  - Als „eigener Eintrag“ gilt, was `launcher\main.ts` enthält (`LAUNCHER_MARKER`, `OWN_COMMAND_MARKER`).
  - Nur eigene Einträge werden ersetzt.
- **Stores:** Sie migrieren nur vorwärts. Eine neuere `schemaVersion` bricht den Start mit Exit 3 ab
  (`STORE_VERSION_TOO_NEW`), eine ältere Version startet also nicht auf migrierten Daten.
  - Gleiche `schemaVersion` heißt aber nicht gleiches Schema, denn neue Felder kommen ohne Versionssprung. Eine Datei,
    die am zod-Schema scheitert, verschiebt `JsonStore` nach `<datei>.corrupt-<zeit>` und nimmt `.bak` oder die
    Defaults. Unbekannte Felder fallen beim nächsten Schreiben weg (`store/jsonStore.ts`).
  - Im Datenordner liegen oben `sessions.json`, `profiles.json`, `settings.json`, `processes.json`, Registry,
    Modellkataloge, Kontolimits und `auth-secret.json`. Je Eintrag liegen unter `entries/<id>/` u. a.
    `decisions.json`, `commands.json`, Anhänge und die Transkripte `*.transcript.jsonl` (nur angehängt, ohne
    `schemaVersion`). Dazu kommen `blobs/`, `ui/`, `chrome/`, `logs/` und `login/`.
  - Die Meldung zu `STORE_VERSION_TOO_NEW` empfiehlt heute „git pull, pnpm install“ (`launcher.ts`).
- **Anmeldung:** Das Gerätecookie ist mit dem gespeicherten `auth-secret.json` signiert und überlebt einen
  Server-Neustart. Der Client lädt bei einer neuen Build-ID neu (A.2).
- **Fenster beim Neustart:** Ein geordneter Stopp schließt die WebSocket mit `4503` (`SERVER_SHUTDOWN`). Der Client
  geht dann in den Endzustand `server-stopped` und verbindet sich nicht neu (`state/connection.ts`,
  `shell/HostGate.tsx`). Der Update-Neustart braucht deshalb einen eigenen Zustand (§9.3, §9.7).
- **„Server beenden“** zeigt, was ein Stopp abbricht (`shell/server-shutdown/impact.ts`). Das passt auch für den
  Update-Neustart.
- **Bordmittel:**
  - Windows bringt `C:\Windows\System32\tar.exe` (bsdtar) mit, das Zip und `.tgz` entpackt; `systemTool()` findet
    es schon heute.
  - Node hat Ed25519 und SHA-512 in `node:crypto`.
  - Neben `node.exe` liegt in der Regel npm (`node_modules\npm\bin\npm-cli.js`).
  - Paket und Prüfung brauchen deshalb keine neue Abhängigkeit.
  - Node 26 bringt kein Corepack mehr mit.
- **Private Angaben:** Der Vorab-Scan fand welche im Repo (§3.1).

### 3.3 Prüfung gegen Rückfälle
- `scripts/public-check.ts` mit einem Test daneben, der über alle Dateien von `git ls-files` läuft. Damit gehört die
  Prüfung zu `pnpm test` und `pnpm check`, ohne neues Skript in `package.json`.
- **Allgemeine Regeln** (im Repo):
  - Benutzerpfade ohne Platzhalter (erfundene Testnamen wie `C:\Users\Max` stehen in der Allowlist);
  - E-Mail-Adressen außer `example.*`, `noreply` und Anbieter-Adressen in Lizenztexten;
  - claude.ai-Session-Links;
  - Schlüsselmuster (`sk-ant-`, PEM-Blöcke `PRIVATE KEY`).
- **Verlauf und Metadaten:** Ein Test über `git ls-files` sieht weder Commit-Messages noch Branch-Namen noch
  Autor-Adressen. Deshalb gibt es zusätzlich `public-check --refs <bereich>`:
  - Es prüft Messages, Autor- und Committer-Adressen, Branch-, Tag- und Dateinamen der Commits im Bereich.
  - Der Koordinator ruft es vor jedem Push mit der lokalen Liste auf (z. B. `origin/main..HEAD`).
- **Bilder** prüft kein Textscan. Neue Screenshots entstehen nur aus dem Playground-Showcase mit erfundenen Daten.
- **Private Begriffe** (Namen, Firmen, Hosts) stehen heute in `.public-check.local` im Wurzelordner des
  Entwicklungs-Repos.
  - Die Datei ist nur lokal ausgeschlossen (`.git/info/exclude`), nicht über `.gitignore`. So steht nicht einmal ein
    Hinweis auf die Liste im Repo.
  - **Entschieden (§13):** In WP-84 zieht die Liste nach `.git/public-check.local` um, also in das gemeinsame
    git-Verzeichnis (`git rev-parse --git-common-dir`). Dort lässt sie sich nicht committen, `git clean -x` löscht sie
    nicht, Worktrees finden sie, und es braucht keinen Eintrag in `.git/info/exclude`.
  - Ein neuer Klon hat die Liste nicht (auch nicht `.git/info/exclude`). Sie wird beim Umschreiben (§3.4) von Hand
    übernommen.
  - Weder die Begriffe noch eine Regel, die sie nennt, dürfen ins Repo: nicht in Code, Doku, Pläne, Testdaten,
    Commit-Messages oder Branch-Namen.
  - Der Test schlägt fehl, wenn die Datei versioniert ist.
  - Verglichen werden ganze Wörter, ohne Rücksicht auf Groß- und Kleinschreibung. Teiltreffer in Bezeichnern zählen
    nicht. Der Test nennt bei einem Fund nur Datei und Zeile, nie den Begriff.
  - In der CI und in Subagenten-Worktrees fehlt die Liste; dort greifen nur die allgemeinen Regeln. Die volle
    Prüfung läuft beim Koordinator vor jedem Merge nach `main` und vor jedem Release.
- Ausnahmen (z. B. die Repo-URL `github.com/DerXHelp/parallax`, die der Updater braucht) stehen in einer kleinen
  Allowlist im Skript.
- Neue `CLAUDE.md`-Regel: „Öffentliches Repo: keine privaten Pfade, Namen, Firmen- oder Netzdetails in Code, Doku und
  Testdaten; Scratch-Pfade nie in Berichte.“

### 3.4 Git-Verlauf und Commit-Metadaten: einmal umschreiben (Nutzer, 17.11.2026)
Der Nutzer erlaubt **einen einmaligen Force-Push** mit aufgeräumtem Verlauf. Er findet am Ende von WP-84 statt, nach
den Bereinigungs-Commits und vor dem ersten Release. Danach gibt es noch keinen Tag, der umgeschrieben werden müsste.

**Stand (17.11.2026)**
- Forks: 0, Issues und PRs: keine, Wiki aus. Keine Tags, kein Stash, keine Notes, ein Worktree.
- Branches auf `origin`: `main`, `feature/phase-3`, `feature/question-tabs`. Die beiden Feature-Branches sind in
  `main` enthalten (geprüft).
- Lokal 16 Branches: 14 davon sind in `main` enthalten (`feature/*` abgeschlossener Vorhaben, `wp/62`…`wp/67`). Nicht
  enthalten sind nur `feature/multi-host` und `feature/releases`.
- `git filter-repo` ist noch nicht installiert; Python 3.13 ist vorhanden.

**Ablauf**
1. **Vorbereiten:**
   - Alle Worktrees sind entfernt, kein anderer Lauf pusht.
   - Lokale Branches, die in `main` enthalten sind, werden gelöscht (`git branch --merged main`). Es bleiben `main`,
     `feature/multi-host` und `feature/releases`.
   - Die alten SHAs der drei Branches auf `origin` werden notiert (für den Lease in Schritt 6).
   - `git status --ignored` wird gesichtet: Was im Entwicklungs-Repo nicht versioniert ist, aber bleiben muss (lokale
     Liste, `.claude/settings.local.json` o. Ä.), wird notiert.
   - Eine Sicherung des alten Verlaufs entsteht per `git clone --mirror` in einen Ordner außerhalb des Repos (lokal;
     wird nach erfolgreicher Prüfung gelöscht).
2. **Werkzeug:** `git filter-repo`, eine einzelne Python-Datei. Als neues Werkzeug braucht es eine Version älter als
   14 Tage. Die Freigabe gilt mit der von WP-84.
3. **Umschreiben in einem frischen Klon** (`git clone --no-local` in den Scratch-Ordner, dort die drei Branches lokal
   angelegt). `filter-repo` verlangt einen frischen Klon und entfernt danach das Remote `origin`. Das
   Entwicklungs-Repo selbst wird nicht umgeschrieben. Alle Refs in einem Lauf:
   - `--replace-text`: Regeln für Pfade, Benutzernamen und private Begriffe gelten für alle Dateien in allen Commits.
   - `--replace-message`: dieselben Regeln für Commit-Messages. Dazu entfallen die Zeilen
     `Co-Authored-By: Claude …` und `Claude-Session: …` samt der Leerzeile davor (434 bzw. 400 Zeilen, Stand
     17.11.2026).
   - `--mailmap`: Die E-Mail-Adresse von Autor und Committer in allen Commits des Nutzers wird zur `noreply`-Adresse
     (§13). Der Name bleibt der Klarname.
   - `--prune-empty never` und `--prune-degenerate never`: Kein Commit fällt weg, die Commit-Map ist vollständig.
   - Die Regel-Dateien enthalten die privaten Angaben selbst und liegen deshalb nur im Scratch-Ordner. Sie werden
     danach gelöscht.
4. **Commit-Verweise:**
   - `filter-repo` passt abgekürzte Hashes in Commit-Messages selbst an, in Dateien aber nicht.
   - Danach ersetzt ein Skript anhand von `.git/filter-repo/commit-map` die alten Hashes in der aktuellen Doku
     (`progress.md`, WP-Berichte) in **einem** Folge-Commit. Es erkennt 7-, 12- und 40-stellige Formen (die Build-ID
     nutzt 12 Stellen).
5. **Prüfen:**
   - Der Scan des neuen Verlaufs findet nichts mehr: allgemeine Regeln und lokale Liste über alle Blobs aller Refs,
     dazu `public-check --refs --all` (Messages, Adressen, Branch- und Dateinamen).
   - Commit-Anzahl und Baum von `HEAD` entsprechen dem Stand vor dem Umschreiben, bis auf die ersetzten Stellen.
   - `pnpm check` und `pnpm build` sind grün (im frischen Klon, nach `pnpm install --frozen-lockfile`).
6. **Force-Push aus dem frischen Klon:**
   - Remote neu anlegen, dann `git push --force-with-lease=main:<alte SHA> origin main`. Ein bloßes
     `--force-with-lease` hätte ohne Remote-Tracking-Ref nichts zum Vergleichen.
   - `feature/phase-3` und `feature/question-tabs` werden auf `origin` gelöscht (beide sind in `main` enthalten).
   - Die Plan-Branches (`feature/multi-host`, `feature/releases`) werden mit umgeschrieben, aber nicht gepusht.
7. **Entwicklungs-Repo ersetzen:**
   - Sein `.git` enthält den alten Verlauf weiter (Reflogs, `ORIG_HEAD`, alte Packs).
   - Deshalb wird der Ordner beiseitegelegt und am **gleichen Pfad** neu geklont. Der Pfad bleibt gleich, damit das
     projektbezogene Gedächtnis von Claude Code passt. Die Plan-Branches kommen aus dem umgeschriebenen Klon.
   - Danach werden die lokale Liste und die notierten ignorierten Dateien übernommen und
     `pnpm install --frozen-lockfile` ausgeführt.
   - Erst nach erfolgreicher Prüfung werden der alte Ordner, der frische Klon und die Mirror-Sicherung gelöscht.
8. **Nacharbeit:**
   - GitHub hält alte Commits über ihre SHA erreichbar, und die Ansicht „Activity“ zeigt die Force-Pushes mit den
     alten SHAs. Der Nutzer bittet deshalb den GitHub-Support, die alten Commits und gecachten Ansichten zu entfernen.
   - **Alte Klone:** Die produktiven Klone auf den drei Rechnern werden neu geklont oder gelöscht, nicht nur
     zurückgesetzt. Aus einem alten Klon wird nie gepusht, sonst käme der alte Verlauf zurück. Mit WP-86 wechseln sie
     ohnehin auf die Installation.
   - Auf jedem Rechner, auf dem der Nutzer committet, wird `user.email` auf die `noreply`-Adresse gesetzt. Das passiert
     **vor** dem Einschalten der Push-Sperre, sonst lehnt GitHub neue Commits ab. Bis zum Umschreiben pusht der
     Koordinator keine Commits mit der alten Adresse, die noch nicht auf `origin` liegen.
   - In GitHub schaltet der Nutzer „Keep my email addresses private“ und „Block command line pushes that expose my
     email“ ein.

### 3.5 Lizenz (Empfehlung: MIT)
**Recherche (17.11.2026)**
- **Ohne Lizenz** gilt das Urheberrecht: Andere dürfen den Code ansehen (und auf GitHub forken), aber nicht verwenden.
  Ein öffentliches Release wäre für andere rechtlich nicht nutzbar.
- **Copyleft (GPL/AGPL)** passt nicht: Parallax baut auf dem proprietären Agent SDK auf. Eine GPL-Software, die eine
  proprietäre Bibliothek voraussetzt, braucht eine Ausnahmeklausel, und das wird schnell unklar.
- **Apache-2.0** bietet eine ausdrückliche Patentlizenz und Regeln für Beiträge. Das lohnt sich bei Projekten mit
  Firmenbeiträgen. Es bringt aber Pflichten mit (NOTICE-Datei, Änderungen kennzeichnen), die hier nichts bringen.
- **Source-available** (PolyForm Noncommercial, BSL) schützt ein Geschäftsmodell, das es hier nicht gibt, und
  schreckt Nutzer ab.
- **MIT** ist kurz und am weitesten verbreitet; einzige Pflicht ist, den Hinweis zu behalten. Das passt zu den
  Laufzeit-Abhängigkeiten (MIT, BSD, Apache) und zu einem persönlichen Werkzeug.

**Entscheidung (Nutzer, 17.11.2026): MIT**
- `LICENSE` mit MIT. Rechteinhaber ist der Nutzer mit Klarnamen.
- README-Abschnitt „Rechtliches“:
  - Parallax ist ein unabhängiges Projekt und nicht mit Anthropic verbunden. „Claude“ und „Claude Code“ sind Marken
    von Anthropic.
  - Parallax steuert das vom Nutzer installierte, **unveränderte** Claude Code. Die Anmeldung erledigt Claude Code
    selbst; Parallax sieht, speichert und vermittelt keine Zugangsdaten.
  - Es gelten die Bedingungen von Anthropic für Claude Code und das Agent SDK.
  - Das deckt sich mit Anthropics Seite „Legal and compliance“:

## 4. Versionen und Changelog

### 4.1 Versionsschema
- SemVer `MAJOR.MINOR.PATCH`, Tag `vX.Y.Z`. Maßgeblich ist `package.json` `version`; sie fließt schon heute in die
  Build-ID.
- **PATCH:** nur Fehlerbehebungen, ein neues CLI-Profil (`/claude-update`) oder Doku.
- **MINOR:** neue Funktionen, auch mit Datenmigration.
- **MAJOR:** Neuinstallation oder Handarbeit nötig, etwa eine höhere Node-Mindestversion oder ein neuer
  Installationsordner.
- Vorabversionen heißen `vX.Y.Z-rc.N` und werden ein GitHub-„Pre-release“. Der Update-Knopf bietet sie nicht an
  (§9.6).
- Die erste Version ist **1.0.0** (Nutzer, 17.11.2026).
- Davon unabhängig bleiben das Protokoll (`PROTOCOL_VERSION`) und die `schemaVersion` der Stores.

### 4.2 `CHANGELOG.md`
Die Datei liegt im Wurzelordner des Repos, ist deutsch und folgt dem Aufbau von „Keep a Changelog“. Beispiel:

```markdown
# Changelog

Alle nennenswerten Änderungen an Parallax. Versionen nach SemVer, neueste zuerst.

## [Unveröffentlicht]

### Neu
- „Verlauf“ an Agent-Zeilen im Aufgaben-Panel öffnet das Transkript des Subagenten (WP-74).

### Geändert
- Das Modell steht dezent in der Fußzeile eines Turns statt als Badge an jeder Antwort (WP-74).

## [1.0.0] – 2026-11-28

Erstes Release. …

### Hinweise zum Update
- Einmaliger Umstieg vom Git-Klon: siehe README „Installieren“.
```

- **Gruppen** stehen in fester Reihenfolge, leere entfallen:
  - **Neu**, **Geändert**, **Behoben**, **Entfernt**, **Sicherheit**;
  - **Hinweise zum Update**: Datenmigration, „Rückkehr nur mit Sicherung“, neue Voraussetzungen.
- **Ein Eintrag** beschreibt in einem Satz die Wirkung für den Nutzer, nicht die Umsetzung. Das WP steht in Klammern
  dahinter.
- **Einzige Quelle:** Release-Seite, `latest.json` und App nehmen ihre Texte aus dieser Datei. Aus Commits wird nichts
  generiert, denn die Commit-Messages sind WP-Protokolle und keine Texte für Nutzer.
- **Sprache:** nur Deutsch. Die UI ist zweisprachig, der Nutzer liest Deutsch.

### 4.3 Pflege
- **Merge nach `main`** (Dauerfreigabe vom 16.11.2026): Der Koordinator ergänzt im selben Merge-Commit die Einträge
  unter „Unveröffentlicht“. Beim Release liegt so schon alles bereit, und der Release-Schritt ist nur noch ein
  Umbenennen.
- **`fix/<name>` nach `main`:** ein Eintrag unter „Behoben“.
- **`/claude-update`** (Profil nach `main`):
  - Eintrag „Geprüft mit Claude Code X.Y.Z“ unter „Geändert“.
  - Am Ende fragt der Skill, ob ein Patch-Release folgen soll. Ohne Release zeigt die produktive Instanz den Hinweis
    „neuer als geprüft“ bis zum nächsten Release.
- **Interne Arbeiten** ohne Wirkung für den Nutzer (Tests, Refactoring, Doku-Pflege) bekommen keinen Eintrag.

### 4.4 Release-Ablauf („mach ein Release“)
1. **Voraussetzungen:** Der Koordinator ist auf `main`, der Stand ist sauber und gleich `origin/main`, und
   „Unveröffentlicht“ ist nicht leer.
2. **Vorschlag:** Er schlägt die Version nach §4.1 vor und zeigt die Notizen. Es geht weiter nach dem OK des Nutzers,
   oder sofort, wenn der Nutzer die Version selbst nennt („mach Release 1.4.0“).
3. **Changelog:** „Unveröffentlicht“ wird zu `## [1.4.0] – <Datum>`, darüber entsteht ein neues, leeres
   „Unveröffentlicht“. `package.json` `version` wird gesetzt.
4. **Commit und Tag:** Der Commit „Release 1.4.0“ geht direkt auf `main` (wie die Koordinator-Nachträge). Dazu kommt
   der annotierte Tag `v1.4.0`, dann der Push von `main` und Tag.
5. **CI:** Er beobachtet die CI (`gh run watch`) und meldet dem Nutzer den Link zum Release.
6. **Fehlschlag:** Schlägt die CI fehl, wird nichts veröffentlicht. Der Tag wird lokal und auf `origin` gelöscht,
   der Fehler behoben und dieselbe Version neu getaggt; sie war nie öffentlich.

Neue Dauerfreigabe in `CLAUDE.md`: „mach ein Release“ des Nutzers erlaubt Release-Commit, Tag und Push.

### 4.5 Prüfungen
- **`scripts/release-notes.ts`** (ohne Abhängigkeit) parst `CHANGELOG.md`:
  - `--check` prüft das Format: Überschriften, Gruppen, Datumsformat, keine doppelte Version.
  - `--extract <version>` liefert den Abschnitt als Markdown für die Release-Seite und `latest.json`.
- **Test** neben dem Skript: Er liest das echte `CHANGELOG.md`, damit Formatfehler schon in `pnpm check` auffallen.
- **CI:** Der Tag muss `v` + `package.json` `version` sein, und der Abschnitt dieser Version muss existieren und
  darf nicht leer sein.

### 5.2 Bau
- **Abhängigkeiten trennen** (freigegeben 17.11.2026): Die reinen Web-Pakete wandern nach `devDependencies`, und
  `dependencies` ist dann die Laufzeit des Servers. `@modelcontextprotocol/sdk` kommt ausdrücklich in

  Lockfile ändert sich. Eine neue Version kommt nicht hinzu, die 14-Tage-Regel greift also nicht.
- **Wächter:** Die Metadatei von esbuild genügt nicht (§1). `release-pack` löst deshalb jeden nackten Import auf,
  statisch und als `import('…')` mit festem Text, und zwar gegen das Staging-`node_modules` (mit vorübergehend
  vorhandenem SDK):
  - aus `dist/server.js` und `dist/launcher.js`;
  - aus allen `.mjs`/`.js` des Agent SDK.
  - Eine kleine Liste im Skript nennt Importe über Variablen (`pino-roll`) und reine Dev-Importe (`pino-pretty`).
  - Fehlt ein Paket, bricht das Release ab und nicht erst der Server beim Nutzer. Der Smoke-Start (§6) ist die zweite
    Sicherung.
- **Launcher bündeln:** `scripts/build-launcher.ts` erzeugt `dist/launcher.js`. `main.ts` bestimmt `repoRoot` wie der
  Server (`dist` → `..`).
- **Paket-Modus:** Liegt `release.json` neben `dist/`, prüft der Launcher keinen Build (kein git, kein
  `repo.config.ts`) und nimmt die Build-ID aus `release.json`. Ohne `release.json` bleibt alles wie heute
  (Entwicklungs-Repo, Klon).
  - `start.mjs` übergibt den Stammordner der Installation ausdrücklich (`--install-root`). Launcher und Server nutzen
    ihn statt `repoRoot` für Autostart, Protokoll und Startmenü.
  - Arbeitsverzeichnis von Server und Chrome ist der Stammordner, nie ein Versionsordner (§8.1, Aufräumen).
  - Die Meldung zu `STORE_VERSION_TOO_NEW` nennt im Paket-Modus „Parallax aktualisieren oder Sicherung einspielen“
    statt „git pull“.
- **`scripts/release-pack.ts`** (ohne Signatur; die macht ein eigener CI-Job, §6):
  1. In einem frischen Staging-Ordner liegen `package.json`, Lockfile und `pnpm-workspace.yaml`; darin läuft
     `pnpm install --prod --frozen-lockfile --config.node-linker=hoisted`.
  2. Wächter (oben), danach wird das Agent SDK aus dem Staging entfernt. Version und `integrity` aus dem Lockfile
     wandern in `release.json`; der Lockfile kennt keine Tarball-URL (§8.2).
  3. Dazu kommen `dist/` (ohne Metadateien), die Vorlagen, `parallax.ico`, `CHANGELOG.md`, `LICENSE` und die
     erzeugte `THIRD_PARTY_NOTICES.md`.
  4. Das Staging enthält nur normale Dateien: keine Links, keine Junctions, keine Namen, die sich nur in Groß- und
     Kleinschreibung unterscheiden.
  5. `release.json` wird erzeugt, noch unsigniert. Ergebnis ist der Staging-Ordner als CI-Artefakt.
- **Build-ID:** Sie kommt weiter aus `resolveBuildId` (in der CI mit vollem Klon, `fetch-depth: 0`) und lautet z. B.
  `1.4.0+3ce6b12`.

## 6. CI: `.github/workflows/release.yml`
- **Auslöser:** Push eines Tags `v*`.
- **Umgebung:**
  - Läufer `windows-latest` (für öffentliche Repos kostenlos), Node 26 über `actions/setup-node`.
  - pnpm über `pnpm/action-setup` in der Version aus `packageManager`; Node 26 hat kein Corepack mehr.
  - Checkout mit `persist-credentials: false`. Die Standardrechte des `GITHUB_TOKEN` stehen in den Repo-Einstellungen
    auf „read“.
- **Jobs** (je ein eigener Läufer, nacheinander):
  1. **build** (`contents: read`, kein Secret):
     - Checkout mit vollem Verlauf, dann `pnpm install --frozen-lockfile` (in der CI ist das SDK normal installiert,
       das ist keine Weitergabe).
     - Tag, Version und Changelog prüfen (§4.5).
     - `pnpm check` (enthält die Neutralitätsprüfung, §3.3), `pnpm build`.
     - `pnpm e2e`: Chrome ist auf dem Läufer installiert; es läuft das FakeBackend, kein `claude`.
     - `release-pack`; der Staging-Ordner wird als Artefakt hochgeladen.
  2. **sign** (Umgebung `release`, `contents: write`):
     - Er installiert nichts und führt außer einem kleinen Signierskript (nur `node:crypto`, aus dem Checkout) keinen
       Projektcode aus.
     - `release.json` signieren, dann mit `tar.exe -a -c` zippen. So liegt `release.json.sig` im Zip.
     - SHA-256 des Zips, `latest.json` erzeugen und signieren.
     - Hochladen als **Entwurf**: `gh release create vX.Y.Z --draft --notes-file <abschnitt> <zip> latest.json
       latest.json.sig CHANGELOG.md`, bei `-rc.N` mit `--prerelease`.
  3. **smoke** (`contents: read`): Er prüft das fertige Zip unter **Node 24** (Mindestversion, §13) und Node 26:
     - mit dem echten `install.js` in einen Temp-Stammordner installieren, SDK aus der Registry;
     - dasselbe Zip ein zweites Mal installieren;
     - Start über `start.mjs` mit FakeBackend und Temp-Home, Health, `--print-url`;
     - `--uninstall`.
     - In WP-85 gibt es `install.js` noch nicht. Dort startet der Smoke das Paket mit dem SDK aus dem
       Build-Arbeitsbereich.
  4. **publish** (`contents: write`): Der Entwurf wird veröffentlicht (`gh release edit --draft=false`).
- **Reihenfolge:** Veröffentlichen ist der letzte Schritt. Ein Fehlschlag hinterlässt höchstens einen Entwurf, den der
  Koordinator löscht.
- **Sicherheit der Pipeline:**
  - Eine Umgebung gilt für einen ganzen Job, nicht für einen Schritt. Deshalb sind Bau und Signatur getrennte Jobs.
    Im Bau-Job laufen fremde Install-Skripte (z. B. esbuild) ohne Schlüssel und ohne Schreibrecht.
  - Actions sind per Commit-SHA gepinnt, mit der Version als Kommentar. Neue Versionen kommen nur, wenn sie älter als
    14 Tage sind (wie bei npm).
  - Der Signaturschlüssel liegt als Secret in der Umgebung `release`, die nur Tags `v*` nutzen dürfen
    (Deployment-Regel).
  - Keine Workflows mit Secrets auf `pull_request` von Forks.
- **Später möglich:** `ci.yml` mit `pnpm check` bei jedem Push nach `main`. Das kostet nichts, wäre aber doppelt zu den
  lokalen Checks vor dem Merge.

### 6.1 Abhängigkeiten: Sicherheitslücken und Updates (Nutzer, 17.11.2026)
**Eingeschaltet am 17.11.2026** (Einstellungen des Repos, per `gh api`):
- Dependabot alerts (Warnungen aus der GitHub Advisory Database);
- Secret scanning mit Push protection (GitHub lehnt Pushes mit erkannten Schlüsseln ab; ergänzt `public-check`);
- Private vulnerability reporting (vertrauliche Meldungen von außen).
- Nicht eingeschaltet: Dependabot security updates. Ihre PRs kämen ohne Wartezeit; über Sicherheits-Fixes wird im
  Einzelfall entschieden (unten).
- Erster Stand: 0 offene Dependabot-Alerts, 0 Secret-Scanning-Alerts.

**Lücke bei pnpm 12:** pnpm 12 schreibt `pnpm-lock.yaml` als zwei YAML-Dokumente (bei Parallax der Fall). Laut
GitHub-Doku übersieht der Dependency Graph dann Abhängigkeiten aus dieser Datei, und Dependabot erzeugt für sie keine
Alerts. Die Alerts sind deshalb nur ein Zusatz.

**CVE-Prüfung mit `pnpm audit`** (WP-85), denn pnpm liest den eigenen Lockfile vollständig:
- `.github/workflows/audit.yml`, wöchentlich per Zeitplan und von Hand startbar: `pnpm audit` über alle Pakete
  (Laufzeit und Entwicklung). Bei einem Fund schlägt der Lauf fehl, und GitHub schickt dem Nutzer eine Mail.
- Im Build-Job des Releases (§6): `pnpm audit --prod --audit-level high`. Eine bekannte hohe oder kritische Lücke in
  einem Laufzeit-Paket bricht das Release ab, bis entschieden ist (unten).
- Nicht in `pnpm check`, denn `pnpm audit` braucht das Netz. Der Koordinator ruft es vor „mach ein Release“ auch lokal
  auf.
- Rechte: `contents: read`, kein Secret.

**Updates mit Dependabot version updates** (WP-85, `.github/dependabot.yml`):
- Ökosystem `npm` (pnpm), Ziel `main`, einmal im Monat, alle Updates gebündelt in **einem** PR (`groups`).
- `cooldown: default-days: 14` entspricht der 14-Tage-Regel.
- `ignore: @anthropic-ai/claude-agent-sdk`; dafür gilt `/claude-update` (`docs/sdk-upgrade.md`).
- Ökosystem `github-actions` mit derselben Wartezeit: Es hält die per SHA gepinnten Actions der Release-CI aktuell.
- **Übernahme:**
  - Dependabot-PRs werden auf GitHub nie gemergt. Der Koordinator holt sie in einen Feature-Branch
    (`feature/deps-update`) und läuft den üblichen Weg: Checks, Build, E2E, Merge nach `main`.
  - Vorher prüft er jeden Eintrag unter `packages:` im Lockfile gegen die Registry-Zeit, wie in
    `docs/wp/DEPS-2026-11.md`. Der Cooldown gilt nur für die direkt aktualisierten Pakete, transitive Pakete können
    jünger sein.
- **Falls Dependabot mit pnpm 12 nicht zurechtkommt** (der erste PR zeigt es): Ersatz ist ein eigener monatlicher
  Workflow, der das bisherige Verfahren ausführt (`pnpm update` mit `minimumReleaseAge=20160`, Agent SDK
  ausgenommen) und einen PR öffnet. `dependabot.yml` behält dann nur `github-actions`.

**Sicherheits-Fixes und die 14-Tage-Regel** (Nutzer, 17.11.2026): Ein Fix für eine Lücke ist zwangsläufig eine frische
Version.
- Bei einer CVE mit Schwere **hoch oder kritisch** entscheidet der Nutzer im Einzelfall, ob der Fix vor Ablauf der
  14 Tage kommt. Der Koordinator legt dazu Paket, Schwere, betroffene Pfade (Laufzeit oder nur Entwicklung) und das
  Alter des Fixes vor.
- Sonst wartet der Fix, bis er 14 Tage alt ist.
- `CLAUDE.md` bekommt die 14-Tage-Regel samt dieser Ausnahme (WP-85).

## 7. Signatur und Vertrauen
- **Ed25519** über `node:crypto` (`generateKeyPairSync`, `sign`, `verify`), ohne Abhängigkeit.
- **Öffentlicher Schlüssel:** fest im Code, in `src/server/update/keys.ts` und im Installer.
- **Privater Schlüssel:**
  - einmal lokal erzeugt (`scripts/release-key.ts`) und als GitHub-Secret hinterlegt;
  - eine Offline-Kopie beim Nutzer (Passwort-Manager);
  - nie im Repo und nicht dauerhaft im Entwicklungs-Repo.
  - **Nie in einer Claude-Session:** Das Skript schreibt den Schlüssel in eine Datei außerhalb des Repos und setzt das
    Secret direkt per `gh secret set --env release` aus dieser Datei. Es gibt nur den öffentlichen Schlüssel und
    dessen Fingerabdruck aus. Der Nutzer führt es selbst aus, verschiebt die Datei in den Passwort-Manager und löscht
    sie. So landet der Schlüssel in keinem Terminal-Protokoll und keinem Transkript.
- **Signiert werden:**
  - `release.json` im Zip, mit dem SHA-256 jeder Datei und der `integrity` des Agent SDK. Jede Installation prüft die
    Signatur, jede Datei, dass keine fremde Datei dabei ist, und den Tarball des SDK.
  - `latest.json` mit Version, Asset-URL, Größe, SHA-256 des Zips, SHA-256 des `CHANGELOG.md` und den Notizen. Es ist
    damit schon vor dem Download vertrauenswürdig.
- **Wer prüft:** Die Prüfung ist nur etwas wert, wenn sie nicht vom geprüften Paket selbst kommt.
  - Update-Knopf und „Aus Datei installieren“: Es prüft der Code der **installierten** Version mit ihrem Schlüssel.
  - `install.cmd` auf einem Rechner mit Installation gibt an die installierte Version ab (`start.mjs --install
    <ordner>`), statt selbst zu prüfen.
  - Nur die allererste Installation vertraut dem Download (s. u.).
- **Nach dem Entpacken**, vor jeder Hashprüfung: Abbruch bei Links, Junctions und anderen Reparse-Punkten, Hardlinks,
  alternativen Datenströmen und Namen, die sich nur in Groß- und Kleinschreibung unterscheiden (Prüfung per `lstat`).
- **Schlüsselwechsel:** `release.json` kann einen Nachfolgeschlüssel tragen. Diese Version ist mit dem alten Schlüssel
  signiert, ab der nächsten gilt der neue. Geht der Schlüssel verloren, hilft nur eine Neuinstallation von Hand.
- **Erste Installation:** Sie vertraut dem Download wie bei jeder Software; ab dann prüft die installierte Version.

| Bedrohung | Gegenmaßnahme |
|---|---|
| Manipuliertes Asset auf GitHub oder unterwegs | Signatur und Hashes; HTTPS |
| Manipulierter SDK-Tarball (Registry, Mirror, unterwegs) | SHA-512 aus dem Lockfile, in der signierten `release.json` |
| Ein altes, signiertes `latest.json` wird erneut ausgeliefert (Downgrade) | Der Updater nimmt nur Versionen über der installierten; zurück geht es nur lokal |
| Präpariertes Zip mit `..`-Pfaden, Links oder Datenströmen | Entpacken in einen leeren Staging-Ordner (bsdtar lehnt `..` und absolute Pfade ab), `lstat`-Prüfung (oben), danach Hashprüfung gegen die signierte Liste; eine fremde Datei bricht ab |
| Code aus einem ungeprüften Paket läuft | Geprüft wird immer mit dem Code der installierten Version; nur die Erstinstallation führt `install.js` aus dem Download aus |
| Fremde URL in `latest.json` | Die URL muss mit `https://github.com/DerXHelp/parallax/releases/download/` beginnen. Weiterleitungen nur über HTTPS und höchstens fünf; keine feste Liste der Asset-Hosts, denn GitHub hat sie schon gewechselt. Hash und Signatur sichern den Inhalt |
| Test-Schalter im Release | URL, Registry und Schlüssel lassen sich nur in Builds mit einem Test-Flag zur Build-Zeit überschreiben, nicht über `isTestRun` (§12) |
| Übernahme des GitHub-Kontos | 2FA/Passkey. Restrisiko akzeptiert: Ein Angreifer könnte den Workflow mit dem Secret laufen lassen. Ausbaustufe: lokal signieren |
| Die Update-Prüfung verrät die Nutzung | GitHub sieht nur IP und Zeitpunkt; die Prüfung ist abschaltbar |


- **Arbeitsverzeichnis:** Launcher, Server und Chrome laufen mit dem Stammordner (oder dem Datenordner) als `cwd`,
  nie mit einem Versionsordner. Sonst sperrt ein langlebiges Chrome den Ordner gegen das Löschen.
- **Aufräumen** nach einem erfolgreichen Start:
  - Gelöscht werden Versionen, die weder `version` noch `previous` sind und nicht laufen. Die laufende Version steht
    im Lockfile des Datenordners. Ohne diese Ausnahme könnte eine zweite Installation ohne Neustart die laufende
    Version zur „älteren als die vorige“ machen, und ihr History-Worker lädt das SDK später noch aus ihrem Ordner.
  - Gelöscht wird in zwei Schritten: erst Umbenennen nach `versions\.trash-<zeit>`, dann Löschen mit Wiederholung.
    Reste räumt der nächste Start ab.
- **Stabile Dateien:** `start.mjs` und `parallax.cmd` ersetzt der Umschalter aus der neuen Version (atomar), wenn sie
  sich geändert haben.
- **Einträge:**
  - Autostart: `node.exe <root>\start.mjs --autostart`.
  - Protokoll: `node.exe <root>\start.mjs --open "%1"`.
  - Startmenü-Verknüpfung „Parallax“ auf `node.exe <root>\start.mjs`, mit Fensterstil „minimiert“ (7) und
    `parallax.ico`, sonst öffnet sich eine Konsole mit dem Node-Symbol.
  - `node.exe` ist der absolute Pfad des laufenden Node. Der Server schreibt die Einträge bei jedem Start neu (wie
    heute), ein Node-Update repariert sich damit selbst.
- **Marker:** Als „eigener Eintrag“ gilt zusätzlich ein Befehl mit `start.mjs` im Installationsordner. Alte Einträge
  mit `launcher\main.ts` bleiben „eigen“ und werden beim ersten Start aus der Installation umgebogen. Das Skript für
  die Verknüpfung (`AUTOSTART_ENV.marker`) kennt heute nur einen Marker und lernt mehrere.
- **Deinstallieren:** `install.cmd --uninstall` (bzw. `start.mjs --uninstall`) entfernt Autostart, Protokoll-Handler,
  Startmenü-Eintrag und den Stammordner. Die Daten in `%LOCALAPPDATA%\Parallax` bleiben; die Meldung nennt den Pfad.

### 8.2 Agent SDK aus der Registry
- **Gleiche Version wie zuvor** (gleiche `integrity`): Der geprüfte Tarball liegt in `<root>\cache\`. Er wird erneut
  gegen die `integrity` geprüft und entpackt, ohne Netzzugriff. Das ist der Normalfall, denn das SDK wechselt nur bei
  einem SDK-Upgrade. Kopiert wird kein Ordner, denn eine Kopie ließe die Prüfung aus.
- **Sonst wird der Tarball geholt**, gegen die `integrity` geprüft, im Cache abgelegt und mit
  `tar.exe -x -z --strip-components=1` nach `node_modules\@anthropic-ai\claude-agent-sdk` entpackt. Zwei Wege:
  1. **Bevorzugt npm neben Node:** `node.exe <node-ordner>\node_modules\npm\bin\npm-cli.js pack
     @anthropic-ai/claude-agent-sdk@<version> --pack-destination <temp> --json`.
     - npm wertet die ganze Konfiguration aus: Scope-Registries, `_auth`/`_authToken`, `${ENV}` in `.npmrc`, `cafile`,
       `strict-ssl`, Proxy, die globale npmrc und `NPM_CONFIG_*`. Gerade auf verwalteten Rechnern ist das robuster als
       ein eigener Nachbau.
     - Der Start folgt den Spawn-Regeln: absolutes `node.exe`, Argument-Array, ohne Shell, `windowsHide`.
  2. **Ohne npm:** eigener Download. Die Tarball-URL steht nicht im Lockfile (der kennt nur `integrity`). Sie kommt
     aus den Paket-Metadaten der Registry (`versions[<v>].dist.tarball`).
     - Registry: `--registry`, sonst `NPM_CONFIG_REGISTRY`, sonst `@anthropic-ai:registry=` bzw. `registry=` aus
       `%USERPROFILE%\.npmrc`, sonst `registry.npmjs.org`.
     - Dazu `_authToken` bzw. `_auth` für genau diesen Host, mit `${ENV}`-Ersetzung.
- Die Prüfung gegen die `integrity` macht jede Registry gleich vertrauenswürdig.
- **Fehlschlag** (keine Registry erreichbar): Die Installation bricht verständlich ab. Den Tarball kann der Nutzer
  dann selbst laden und per `--sdk-tarball <datei>` übergeben; geprüft wird er genauso.
- **TLS und Proxy:** `start.mjs` und `install.cmd` starten Node mit `--use-system-ca`, damit Zertifikate einer
  Firmen-Inspektion aus dem Windows-Speicher gelten. Für einen Proxy gibt es `--use-env-proxy` bzw.
  `NODE_USE_ENV_PROXY`. Beides kann Node 24; welche 24er-Version genau, legt WP-85 fest (§13).

### 8.3 `install.cmd`
- **Ablauf:**
  1. Node-Mindestversion prüfen (`release.json` `minNode`, genau mit Minor, §13).
  2. **Gibt es schon eine Installation**, gibt `install.cmd` an deren `start.mjs --install <ordner>` ab. Geprüft wird
     dann mit dem Code und dem Schlüssel der installierten Version (§7).
  3. Den entpackten Ordner nach `versions\.staging-<v>` kopieren, `lstat`-Prüfung, `release.json` prüfen (Signatur,
     Hashes), dann zu `versions\<v>` umbenennen.
  4. Das Agent SDK nach §8.2 einsetzen.
  5. `start.mjs`, `parallax.cmd` und `current.json` schreiben.
  6. Die Startmenü-Verknüpfung anlegen (PowerShell + `WScript.Shell` wie `autostart.ts`).
- **Parallax läuft schon** (Lockfile + Health im Datenordner): Es wird trotzdem installiert und umgeschaltet; die
  laufende Version liegt in ihrem eigenen Ordner und bleibt unberührt (Aufräumen, §8.1). Meldung: „Parallax neu
  starten (Zahnrad → Server beenden), um 1.4.0 zu nutzen.“
- **Optionen:** `--use <version>` schaltet auf eine installierte Version um; dazu kommen `--dir <ordner>`,
  `--registry <url>`, `--sdk-tarball <datei>` und `--uninstall`.
- **Gesperrte `.cmd`:** Ein aus dem Browser geladenes Zip trägt die Internet-Markierung. SmartScreen oder AppLocker
  können `install.cmd` dann warnen oder sperren, wie eine unsignierte `.exe` (§0). Das README nennt deshalb den
  gleichwertigen Weg `node dist\install.js` im entpackten Ordner. Updates über die App betrifft das nicht.

### 8.4 Sicherung beim ersten Start einer neuen Version (schon in Stufe 1)
- Der Launcher merkt sich die zuletzt gestartete Build-ID in `last-version.json` im Datenordner.
- Startet eine andere Build-ID als zuletzt, sichert er vor dem Serverstart nach
  `<home>\backups\<alt>-zu-<neu>-<zeit>\`. Gesichert wird nach einer **Liste**, nicht nach Ausschlüssen:
  - alle Dateien der JSON-Stores im Datenordner und je Eintrag (`entries/*/*.json`), samt `.bak`;
  - für die Transkripte (`*.transcript.jsonl`, nur angehängt) nur die Länge jeder Datei in `backup.json`; beim
    Einspielen werden sie auf diese Länge gekürzt, neuere Transkript-Dateien wandern in den Sicherungsordner. Das
    spart das Kopieren großer Dateien;
  - nicht: `processes.json` (beim Einspielen bleibt die aktuelle Datei, sonst gingen Einträge zu verwaisten Prozessen
    verloren), `auth-secret.json` (ändert sich nicht), `blobs/`, Anhänge, `ui/`, `chrome/`, `logs/`, `login/` und
    frühere Sicherungen.
  - Die drei jüngsten Sicherungen bleiben.
- Das gilt im Paket-Modus **und** im Klon (`parallax.cmd`). Ein Klon eines neueren `main` auf demselben Datenordner
  kann sonst migrieren, und das Release bricht danach mit Exit 3 ab, ohne dass es eine Sicherung gibt. Nur `pnpm dev`
  sichert nichts.
- Die Liste der Store-Dateien kommt aus dem Code (eine Stelle in `src/server/store`), nicht aus einer zweiten Liste im
  Launcher.

### 8.5 Umstieg vom Klon (einmal je Rechner)
1. Zip der ersten Version laden, entpacken, `install.cmd` starten.
2. In der alten Instanz „Server beenden“, dann Parallax über das Startmenü starten. Der Server biegt Autostart und
   Protokoll-Handler auf die Installation um, sofern sie eingeschaltet sind (wie heute).
3. Den alten Klon löschen oder nicht mehr starten. Daten und Chrome-Profil bleiben, wo sie sind.
   - Ein Klon ohne `git pull` hält die neuen `start.mjs`-Einträge für fremd und warnt nur.
   - Ab WP-86 erkennt ein Klon Einträge einer Installation, lässt sie in Ruhe (die Installation hat Vorrang) und zeigt
     nur einen Hinweis. So biegt auch ein aktualisierter Klon nichts zurück.

Das README bekommt die Abschnitte „Installieren“ und „Aktualisieren“; „Produktiv nutzen und weiterentwickeln“
verweist darauf.

## 9. Update in der App (Stufe 2)

### 9.1 Prüfen
- **Wann:** beim Start und alle 12 Stunden, per
  `GET https://github.com/DerXHelp/parallax/releases/latest/download/latest.json` und `.sig`. Download-Links zählen
  nicht gegen das API-Limit (ohne Anmeldung 60 Abfragen pro Stunde je IP, hinter einem Firmen-NAT womöglich geteilt).
- **Steuerung:** Einstellung `updates.check` (Standard an) und der Knopf „Jetzt prüfen“.
- **Nur im Paket-Modus.** Im Entwicklungs-Repo und im Klon zeigt der Abschnitt „Entwicklungsstand <Build-ID> – Updates
  über git“.
- **Proxy und TLS:** Laut Nutzer sollte das Netz durchgehen. Der CI-Probelauf und die Live-Prüfung bestätigen das.
  Falls nicht:
  - `HTTPS_PROXY` mit `NODE_USE_ENV_PROXY` bzw. `--use-system-ca` beim Serverstart;
  - sonst bleibt „Aus Datei installieren“.

### 9.2 Vorbereiten
1. „Update vorbereiten“ lädt das Zip nach `downloads\…partial`, mit Größenlimit und Fortschritt.
2. Der SHA-256 wird gegen `latest.json` geprüft.
3. `System32\tar.exe` entpackt nach `versions\.staging-<v>`.
4. `lstat`-Prüfung, dann wird `release.json` geprüft (§7), das Agent SDK eingesetzt (§8.2), und der Ordner wird zu
   `versions\<v>` umbenannt.

Das läuft im Hintergrund, die Sessions laufen weiter. Danach meldet die App: „Bereit – neu starten, um 1.4.0 zu
nutzen“.

### 9.3 Neu starten und umschalten
1. **Bestätigen:** „Neu starten“ zeigt wie „Server beenden“, was abbricht (`impact.ts`: laufende Sessions, offene
   Entscheidungen). Laufende `claude`-Prozesse werden wie beim Beenden gestoppt; die Sessions lassen sich danach
   fortsetzen.
2. **Übergabe:**
   - Der Server startet über `spawnHidden` (detached, ohne Fenster) den Launcher **der laufenden (alten) Version** mit
     `--apply-update=1.4.0`. So läuft die Orchestrierung in bewährtem Code.
   - Er gibt die eigenen Startargumente mit (`--home`, `--port`, `--backend`, `--system-integration`), damit die neue
     Version genauso startet.
   - Dann schließt er die WebSockets mit dem neuen Close-Code `SERVER_RESTARTING` (§9.7) und beendet sich. Anders als
     bei `4503` zeigt das Fenster „Parallax startet neu …“ und verbindet sich mit Backoff neu (bis zu 2 Minuten).
3. **Umschalten:**
   - Der Orchestrator nimmt die Start-Sperre des Datenordners. Ein Autostart, ein Klick auf eine Benachrichtigung oder
     ein `parallax:`-Link startet so keinen Server mitten im Wechsel.
   - Er wartet, bis der alte Serverprozess beendet und die Home-Sperre frei ist, nicht nur auf das Lockfile. Nach
     einer Frist beendet er den Prozessbaum mit `taskkill /T /F`.
   - Dann sichert er die Stores (§8.4), schaltet `current.json` um und startet die neue Version ohne Fenster.
4. **Erfolg:** Die neue Version ist innerhalb der Frist gesund (Health, gleiche Instanz-UUID wie im Lockfile). Die
   Frist beträgt 60 s und ist einstellbar, denn Virenscanner bremsen den ersten Start. Das offene Fenster verbindet
   sich neu, lädt wegen der neuen Build-ID neu und zeigt einmal „Aktualisiert auf 1.4.0 – Was ist neu“.
5. **Sonst automatisch zurück:**
   - den Prozessbaum der neuen Version beenden (`taskkill /T /F`) und warten, bis die Home-Sperre frei ist;
   - die Sicherung einspielen (§8.4: Stores zurück, Transkripte kürzen, `processes.json` bleibt), denn die neue
     Version könnte schon migriert haben;
   - `current.json` zurückstellen und die alte Version starten;
   - `update-failed.json` schreiben. Die App zeigt „Update auf 1.4.0 fehlgeschlagen, zurück auf 1.3.2“ mit dem Pfad
     zum Log.
6. **Sperre freigeben:** Der Orchestrator gibt die Start-Sperre erst frei, wenn eine Version läuft oder der Rückweg
   gescheitert ist (dann Meldung per Windows-Benachrichtigung mit Pfad zum Log).

### 9.4 Zurück zur vorigen Version
- In den Einstellungen gibt es „Zurück zu 1.3.2“, solange deren Ordner existiert.
- Die `schemaVersion` genügt als Vergleich nicht. Neue Felder kommen ohne Versionssprung, und eine ältere Version
  würde eine Datei mit unbekannten Werten in Quarantäne schieben oder Felder beim Schreiben verwerfen (§1).
- `release.json` nennt deshalb je Store einen **Schema-Hash**, dazu einen für das Item-Schema der Transkripte. Gebildet
  wird er aus dem JSON-Schema des zod-Schemas (`z.toJSONSchema`), beim Bau.
  - Sind alle Hashes bei beiden Versionen gleich, genügt das Umschalten.
  - Sonst geht es nur mit der Sicherung vom Update, mit klarer Warnung („Änderungen seit <Zeit> gehen verloren“) und
    Bestätigung.
- Der Ablauf ist derselbe wie in §9.3, mit `--apply-update=<vorige>`.

### 9.5 Oberfläche (`src/web/features/updates/**`, Namensraum `updates`)
- **Kopfzeile:** ein dezenter Hinweis „Parallax 1.4.0 verfügbar“, im Stil des Hinweises zu neuen `claude`-Versionen.
  Ein Klick öffnet den Abschnitt „Updates“.
- **Einstellungen, neuer Abschnitt „Updates“:**
  - installierte Version und Build-ID;
  - Status: aktuell, verfügbar, lädt (n %), bereit, fehlgeschlagen;
  - Knöpfe „Jetzt prüfen“, „Update vorbereiten“, „Neu starten“, „Zurück zu …“, „Aus Datei installieren…“;
  - Schalter „Automatisch nach Updates suchen“;
  - Links auf Lizenz und `THIRD_PARTY_NOTICES.md`.
- **„Was ist neu“:**
  - Vor dem Update zeigt es die Changelog-Abschnitte zwischen installierter und neuer Version, aus dem signierten
    `CHANGELOG.md` des Releases.
  - Sonst zeigt es den Abschnitt der installierten Version.
  - Gerendert wird mit dem vorhandenen Markdown, ohne Raw-HTML.

### 9.6 Aus Datei installieren
- Das Zip kommt per Dateiauswahl (Upload-Route wie bei Anhängen, mit Größenlimit). Es folgt dieselbe Prüfung wie in
  §9.2, durch den Code der installierten Version, dann „Neu starten“. Aus dem hochgeladenen Paket läuft vor der
  Prüfung kein Code.
- Das ist der Weg für Vorabversionen und für Rechner, auf denen die Prüfung nicht durchkommt.
- So lässt sich auch eine ältere Version installieren; dann gelten die Regeln aus §9.4.

### 9.7 Contracts (Überblick; Details in WP-87)
- **`HostState.app`** `{version, buildId, packaged}`.
- **`HostState.update`:** Status, Fortschritt, verfügbare Version mit Notizen, vorige Version mit `needsRestore`,
  `justUpdated`, `failedUpdate` und Fehler als `ErrorPayload`.
- **Befehle und Routen:** `update.check`, `update.prepare`, `update.apply`, `update.rollback`, `update.dismiss`; eine
  Route für den Datei-Upload; `GET /api/changelog`, `GET /api/notices`.
- **Fehlercodes:** `UPDATE_CHECK_FAILED`, `UPDATE_DOWNLOAD_FAILED`, `UPDATE_INVALID_SIGNATURE`, `UPDATE_INVALID_PACKAGE`,
  `UPDATE_SDK_FAILED`, `UPDATE_NOT_PACKAGED`, `UPDATE_BUSY`.
- **Neustart:** Close-Code `SERVER_RESTARTING` neben `SERVER_SHUTDOWN` (`4503`) in `@shared/protocol`. Der Client
  bekommt die Phase `restarting` (Anzeige „startet neu“, Reconnect mit Backoff, nach Ablauf `server-stopped`).
- **Einstellung** `updates.check`: Default `true`, kein Schema-Bump.
- **`PROTOCOL_VERSION`:** Die neue Version zählt hoch. WP-75 plant 3 → 4; wer zuerst umgesetzt wird, nimmt 4, der andere
  die nächste.

## 12. Teststrategie
- **Unit-Tests** mit Fakes (fetch, fs, tar, Uhr) für:
  - Changelog-Parser;
  - Neutralitätsprüfung (Regeln, Allowlist, lokale Begriffe);
  - Manifest und Signatur (mit Test-Schlüssel);
  - SDK-Bezug (`integrity`, `.npmrc`-Auswertung, Kopie aus der vorigen Version);
  - Versionsvergleich, Umschalter, Sicherung (Liste, Transkripte kürzen, `processes.json` bleibt);
  - `lstat`-Prüfung (Links, Junctions, Hardlinks, Datenströme, Groß-/Kleinschreibung);
  - Aufräumen mit Schutz der laufenden Version;
  - Orchestrierung samt Start-Sperre und Rückweg;
  - Schema-Hashes (ändern sich bei einem neuen Feld, nicht bei Kommentaren).
- **Isolation:** `test/setup` setzt heute nur ein eigenes `PARALLAX_HOME`, nicht `LOCALAPPDATA`/`APPDATA`.
  - Installer und Updater nehmen in Tests deshalb nie ihre Standard-Ordner: Stammordner und Startmenü kommen immer
    ausdrücklich aus dem Test.
  - Dazu kommt eine Sperre wie bei R6: Ein Testlauf, der den echten `%LOCALAPPDATA%\Programs\Parallax` oder das echte
    Startmenü treffen würde, bricht ab.
- **Paket:** Der Smoke-Job der CI (§6) prüft das fertige Zip unter Node 24 und Node 26. Lokal läuft `release-pack` nicht
  in Tests, denn es braucht das Netz und ist ein schwerer Lauf (ADR-154).
- **E2E:** Ein lokaler Release-Server und eine Fake-Registry auf 127.0.0.1 liefern `latest.json`, Zip und SDK-Tarball,
  signiert mit einem Test-Schlüssel.
  - Die Pakete sind klein und synthetisch (ein Mini-Server, der Health und Build-ID liefert), kein echtes
    `release-pack`.
  - URL, Registry und Schlüssel lassen sich nur in Builds mit einem Test-Flag zur Build-Zeit überschreiben. `isTestRun`
    (`VITEST`/`NODE_ENV=test`) genügt dafür nicht, das könnte jede Umgebung setzen.
  - Ablauf: Hinweis → Vorbereiten → Neustart (Fenster zeigt „startet neu“ und verbindet sich neu) → neue Version →
    Rückkehr.
  - Ein kaputtes Paket, ein Link im Zip oder ein falscher SDK-Hash löst den Abbruch bzw. Rückweg aus.
- **Live-Checkliste:**
  - Umstieg vom Klon; Autostart, Protokoll-Handler und Startmenü zeigen danach auf die Installation.
  - SDK-Bezug auf dem Firmenrechner (Firmen-Registry aus `.npmrc`).
  - 1.0.0 → 1.1.0 per `install.cmd`, danach 1.1.1 über den Update-Knopf und die Rückkehr.
  - Update-Prüfung auf allen drei Rechnern.
  - Deinstallieren und erneut installieren auf einem Rechner.
- Kein Live-`claude` nötig.

## 15. ADR-Entwürfe (ADR-212…221; angenommen erst mit der Freigabe von WP-84 bzw. WP-85)
- **ADR-212 – Öffentliches Repo ist neutral:** keine privaten Pfade, Namen, Firmen- oder Netzdetails; Prüfung in
  `pnpm check` mit allgemeinen Regeln im Repo und privaten Begriffen in einer nur lokal ausgeschlossenen Datei; der
  Verlauf wurde einmal bereinigt (Force-Push vor 1.0.0).
- **ADR-213 – Lizenz MIT:** Parallax steht unter MIT. README „Rechtliches“: unabhängig von Anthropic; steuert das
  installierte, unveränderte Claude Code; keine Zugangsdaten.
- **ADR-214 – Agent SDK wird nicht weitergegeben:** Es ist proprietär; Installer und Updater holen es aus der Registry
  und prüfen es gegen die `integrity` aus dem Lockfile; Hinweise zu Drittkomponenten liegen jedem Paket bei.
- **ADR-215 – Releases per Tag, bewusst ausgelöst:** SemVer aus `package.json`; ein Tag `vX.Y.Z` entsteht nur auf
  Wunsch des Nutzers; Release-Commit und Tag gehen direkt auf `main`.
- **ADR-216 – `CHANGELOG.md` als einzige Quelle der Release-Notizen:** Pflege beim Merge nach `main` unter
  „Unveröffentlicht“, Format geprüft in `pnpm check`; Release-Seite, `latest.json` und App lesen daraus.
- **ADR-217 – Paket = vorgebautes Zip, Node vorausgesetzt:** `dist/` mit gebündeltem Launcher, Laufzeit-Pakete flach;
  Paket-Modus über `release.json`; kein Build auf den Zielrechnern; Web-Pakete in `devDependencies`.
- **ADR-218 – Ed25519-Signatur für Releases:** Der öffentliche Schlüssel steht im Code; signiert sind `latest.json` und
  `release.json` (Hash jeder Datei, `integrity` des SDK); der private Schlüssel ist ein Secret der CI-Umgebung
  `release`, signiert wird in einem eigenen Job ohne Install; geprüft wird immer mit dem Code der installierten
  Version, nie mit dem des neuen Pakets.
- **ADR-219 – Installationsordner mit Versionsordnern:** `%LOCALAPPDATA%\Programs\Parallax`, `current.json`, stabiles
  `start.mjs`; Autostart, Protokoll und Startmenü zeigen darauf; Sicherung beim ersten Start einer neuen Version.
- **ADR-220 – Update in der App:** Prüfen über Download-URLs (kein API-Limit), Vorbereiten im Hintergrund, Neustart
  auf Klick mit eigenem Close-Code (`SERVER_RESTARTING`, das Fenster verbindet sich neu); die alte Version
  orchestriert unter der Start-Sperre; automatischer Rückweg mit Sicherung; Rückkehr ohne Datenverlust nur bei
  gleichen Schema-Hashes.
- **ADR-221 – Abhängigkeiten prüfen und aktualisieren:** `pnpm audit` wöchentlich und im Release (die
  Dependabot-Alerts sehen den Lockfile von pnpm 12 nicht vollständig); Dependabot version updates mit 14 Tagen
  Wartezeit, gebündelt, ohne Agent SDK, Übernahme nur über einen Feature-Branch; Sicherheits-Fixes vor Ablauf der
  14 Tage nur nach Entscheidung des Nutzers im Einzelfall.
