## 0. Ausgangslage (Code des CLI 2.1.322 und Live-Probe 12.11.2026)

- **Schnittstelle (intern, nicht typisiert):** `query.askSideQuestion(question, { history?, signal? })` →
  `{ response: string, synthetic: boolean, refusalFallback?: { originalModel, fallbackModel, content } } | null`
  (`null` = keine Antwort möglich, z. B. noch kein Gesprächsstand). Steuerbefehl `side_question`; `history` =
  frühere Fragen/Antworten desselben Seitenfadens (`[{ question, response }]`) für Nachfragen. Abbruch über
  `signal` → Fehler „Side question cancelled“. Fortschritt als Stream-Meldung
  `system/control_request_progress { request_id, status: 'started' | 'api_retry', attempt?, max_retries?,
  retry_delay_ms?, error_status? }` (die `request_id` kennt der Aufrufer nicht – Zuordnung nur, wenn genau eine
  Seitenfrage offen ist). Fehlercode `side_question_busy`: das CLI führt schon so viele Seitenfragen und
  Titel-Abfragen aus, wie es gleichzeitig darf.
- **Verhalten (CLI-Code):** zweigt den aktuellen Gesprächsstand ab, **auch mitten in einem laufenden Turn**
  (inkl. der bisherigen Teile dieses Turns), nutzt den Prompt-Cache der Session, schreibt nichts in den
  Gesprächsverlauf (`threadHistory: false`).
- **Probe live (Haiku, gesamt ≈ 0,0042 USD):**

  - **Keine Werkzeuge:** „Lies geheim.txt“ → „in dieser Nebenfrage sind keine Werkzeuge verfügbar“; kein
    `canUseTool`-Aufruf.
  - **Kosten** einer Seitenfrage im Leerlauf ≈ **0,0004 USD** (Nutzungsabfrage vorher/nachher). Sie zählen in das
    kumulierte `total_cost_usd` der Session (nächstes `result`) – Parallax zählt sie also schon mit, keine eigene
    Addition.
  - Hauptgespräch weiß nichts davon (Frage danach → „NEIN“); claude-Transkript enthält die Seitenfragen nicht.
  - Je Seitenfrage eine `control_request_progress`-Meldung `started`.

### 1.1 Backend und Engine
- Port-Methode `askSideQuestion(question, { history, signal })` mit **Laufzeitprüfung** (fehlt die Methode:
  `CLAUDE_CONTROL_FAILED`, kein Absturz) und tolerantem Parsen der Antwort (zod). `side_question_busy` →
  `SESSION_BUSY`; Abbruch → Status `cancelled`; sonst `CLAUDE_CONTROL_FAILED`.
- Befehl `session.askSideQuestion` legt sofort ein Item `side_question` (Status `pending`) in der **aktuellen
  Konversation** an und antwortet mit dessen ID; die Antwort kommt als Item-Update. Läuft kein Prozess (schläft,
  geschlossen): wie beim Senden eines Prompts starten/wecken (ohne Turn), dann fragen. Nicht für archivierte und
  externe Sessions (`SESSION_ARCHIVED`, `SESSION_EXTERNAL`).
- **Seitenfaden:** `threadId` = ID der ersten Frage; Nachfragen schicken die beantworteten Fragen/Antworten des
  Fadens als `history` mit (älteste zuerst, höchstens die letzten 10).
- **Abbrechen** (`session.cancelSideQuestion`) über `AbortSignal`; Prozessende/Neustart → offene Seitenfragen
  `failed` (nicht hängen lassen). **Löschen** (`session.deleteSideQuestion`, ganzer Faden) entfernt die Items aus
  Parallax.
- `control_request_progress` `api_retry` → am einzigen offenen Item „wiederholt (n/m)“ anzeigen; sonst ignorieren
  (zählen wie andere unbekannte Meldungen).
- Seitenfragen ändern weder `unread` noch Benachrichtigungen, Status oder Schlaf-Timer der Session (eine offene
  Seitenfrage hält den Prozess aber wach, bis sie beantwortet ist).
- Persistenz: im Transkript-Log von Parallax wie andere Items (überleben Neuladen und Server-Neustart). Kein Import
  aus dem claude-Transkript (dort stehen sie nicht).

### 1.2 Oberfläche (en/de, Tokens, Primitives aus `src/web/ui`)
- **Composer:** `/btw <frage>` wird abgefangen (nicht als Prompt gesendet, erscheint im `/`-Menü als Parallax-
  Befehl „Seitenfrage“) und ein Umschalter „Seitenfrage“ neben Senden (lucide, z. B. `MessageCircleQuestion`):
  an → Enter stellt eine Seitenfrage statt eines Prompts; der Zustand ist deutlich sichtbar (Rahmen/Platzhalter
  „Seitenfrage – geht nicht in den Kontext“). Geht auch, während Claude arbeitet. Anhänge/Pastes sind im
  Seitenfrage-Modus aus (die Schnittstelle nimmt nur Text).
- **Karte im Transkript** an der Stelle der Frage, sichtbar abgesetzt (eigener Hintergrund-Token, gestrichelter
  Rahmen o. ä.) mit dem Hinweis „Seitenfrage · nicht im Kontext“; Frage, Antwort als Markdown (gleiche
  Komponente wie Assistenten-Text), Nachfragen des Fadens darunter. Aktionen: „Nachfragen“ (kleines
  Eingabefeld in der Karte), „Kopieren“, „Löschen“; während `pending` „fragt…“ und „Abbrechen“.
  `synthetic: true` gedämpft darstellen („keine Antwort verfügbar“), `refusalFallback` als kleiner Hinweis
  („beantwortet von <Modell>“). Im kompakten Transkript (ADR-163) Rolle „sichtbar“, nie in eine Schrittgruppe.
- **Aus der Übersicht:** Kontextmenü der Session in der Seitenleiste „Kurz fragen…“ → Popover mit Eingabefeld;
  die Antwort erscheint im Popover (mit „Nachfragen“ und „Session öffnen“) und zusätzlich als Karte im Transkript.
  Schließt man das Popover vor der Antwort, kommt bei Eingang ein Toast mit dem Anfang der Antwort und
  „Öffnen“.
- Fehler lesbar (Toast bzw. in der Karte): „gerade zu viele Seitenfragen – gleich nochmal versuchen“
  (`SESSION_BUSY`), „Seitenfrage nicht verfügbar“ (`CLAUDE_CONTROL_FAILED`).
- **Keine Kostenanzeige je Karte** (nur über die Nutzungsabfrage messbar, während eines Turns ungenau); die
  Kosten stecken in den Session-Kosten.

### 1.5 Wartende Nachricht zurückholen (Punkt 11)
- **Schnittstelle (intern, nicht typisiert):** `query.cancelAsyncMessage(uuid)` → `cancelled: boolean` (Steuerbefehl
  `cancel_async_message`). `true`: aus der CLI-Warteschlange entfernt, das CLI schickt `command_lifecycle`
  `cancelled`. `false`: nicht mehr in der Warteschlange – schon übernommen (auch in den laufenden Turn gefaltet,
  `priority: 'next'` nach einem Werkzeugergebnis, `docs/sdk-findings.md` Punkt 9) oder noch vor der Warteschlange
  gehalten (dann setzt das CLI eine Abbruch-Marke). Laufzeitprüfung wie bei der Seitenfrage.
- Engine: Befehl `session.withdrawQueued` → `cancelAsyncMessage`; bei `true` den Queue-Eintrag und das graue
  User-Item entfernen (`command_lifecycle cancelled` nutzen, idempotent), Ergebnis `{ withdrawn: true, text }`;
  bei `false` nichts ändern, `{ withdrawn: false }`. Noch nicht an das CLI übergebene Einträge (`sending`) wie heute
  lokal entfernen.
- UI: in „Wartende Nachrichten“ (Composer) an jedem Eintrag „Zurückholen“ (lucide `Undo2` o. ä., Tooltip):
  `withdrawn: true` → Text (und Pastes/Anhänge, soweit Parallax sie noch hat) zurück ins Eingabefeld; ist dort
  schon Text, anhängen statt überschreiben. `withdrawn: false` → Toast „schon übernommen“.
- Fake: Hebel für `true`/`false`. `pnpm cli-check`: nur Existenz der Methode prüfen (kein Aufruf).
