### Tool-Status

`streaming_input` (Stream) → `pending` (finale Message) → `awaiting_decision` (`attachDecision`
offen) → `running` (erlaubt, `task_started`, `tool_progress`) → nach dem Result: `denied`
(Entscheidung verweigert, `tool_result_meta.permission_decision: reject`, `permission_denied`),
`interrupted` (`non_execution_kind: user-rejected` bzw. CLI-Text „The user doesn't want to proceed
…“, Abbruch/Ablauf einer Entscheidung, `finalizeOpen('process_exit')`), `error`, `background`
(`tool_use_result.isAsync`/`backgroundTaskId` oder gebackgroundeter Task; endet mit dem Task:
completed → `done`, failed → `error`, stopped/killed → `interrupted`), sonst `done`.

### Live vs. Verlauf

Getestet für alle Fixtures mit vollständigem `getSessionMessages` in `history.jsonl`
(`permissions`, `ask-user-question`, `plan-mode`, `subagent` inkl. `getSubagentMessages`): gleiche
Item-IDs in gleicher relativer Reihenfolge, Items gleich bis auf diese **dokumentierten und
explizit getesteten** Unterschiede (`history.test.ts`):

| Unterschied | Grund |
|---|---|
| keine `turn_result`-Items und keine System-Items wie `rate_limit`, `error`, `api_retry`, `conversation_reset` im Verlauf | `getSessionMessages` liefert nur user/assistant(/system) |
| absolute `order` verschieden (relative Reihenfolge gleich) | folgt aus der Zeile davor |
| `user_message.at`/`priority` | live = `PendingPrompt` (Sendezeit, Priorität), Verlauf = CLI-Timestamp, `priority: null` |
| `tool_call.result.structured = null` im Verlauf | kein `tool_use_result` (F.15); Diff-Fallback: `input.old_string/new_string` bleiben erhalten (getestet) |
| `tool_call.decision = null` im Verlauf | Entscheidungen setzt nur die Engine live |
| Status `denied` nur live; Verlauf `error` bzw. `interrupted` (Deny mit Interrupt) | Permission-Entscheidung/`tool_result_meta` fehlen im Verlauf |
| `tool_call.task`: im Verlauf ohne `isBackgrounded`/`startedAt`, `endedAt` = Zeit der Notification; `description`/`subagentType`/`taskType` aus dem Agent-Input | Verlauf kennt nur die `<task-notification>`-Usermessage |
| Agent-Tool zwischenzeitlich `background` nur live (Endzustand gleich `done`) | `isAsync` steht nur in `tool_use_result` |
| Subagent-Prompt (User-Message mit `parentToolUseId`) erzeugt kein Item | live kommt er nicht; er steht im Agent-Input |
| `user_message.origin` im Verlauf immer `human` | `HistoryMessage` hat kein `origin` (Contract-Wunsch) |
| Local-Command-Ausgabe: live `assistant_text` (`<synthetic>`, ID `${message.id}:0`), Verlauf `system/local_command_output` (ID = uuid) | Verlauf speichert sie als `<local-command-stdout>`-Usermessage (Format **angenommen**, nicht vollständig aufgezeichnet) |

Offene Tool-Calls im (ruhenden) Verlauf werden `interrupted`; `system`-Messages im Verlauf werden nur
gezählt (`unknownCounts['history/system']`).

### Statusmaschine – Regeln und Präzisierungen

Alle Pflichtregeln des Ports sind tabellengetestet (`status/machine.test.ts`). Präzisierungen:

- `session_state idle` ändert `runState` **nicht**, solange `runState = error` (ein Auth-/Setup-Fehler
  dieses Prozesses soll nicht von `idle` überschrieben werden); `running|requires_action` setzt
  `working` und löscht den Fehler (neuer Turn). `external` ignoriert `session_state`.
- `turn_result` mit Startfehler/Setup-Fehler setzt `error` **auch** bei `synthetic` (Startfehler
  haben `num_turns 0`); sonst ändert `synthetic` nichts. `interrupted` setzt nie einen Fehler.
- `init` ohne `sessionStateSeen` (alte CLI) → `working` aus `starting|idle` (Gegenstück zur Regel
  „`turn_result` zählt als `idle`“).
- `process_exit` behält `error` (erwartet oder nicht) und `external`; setzt `compacting`,
  `retrying`, `backgroundTasks` zurück (kein Prozess mehr). `process_starting` ebenso plus Fehler weg.
- `server_restart`: `starting|working` → `interrupted`; offene Entscheidungen → `interrupted`
  (außer `error`/`external`); `idle` → `sleeping`; Prozess-Flags zurück.
- `rate_limit`: `rejected` → `rateLimitedUntil = resetsAt`, `allowed`/`allowed_warning` → `null`.
- `external {active:false}` → `sleeping` (nur aus `external`).
- Keine Änderung → **dasselbe Objekt** zurück (Engine erkennt No-ops per Referenz).

Statusverläufe aller Fixtures und synthetischen Streams: `status/__snapshots__/`; erwartete
Sequenzen u. a. `auth-probe`: sleeping → starting → working → working+unread → done+unread →
sleeping+unread; `permissions`: working ↔ needs-permission … done+unread; `clear-rename` (mit
`viewed` nach jedem idle): `/rename` und `/clear` enden in `idle` ohne unread; `interrupt`: User-Stop
→ `idle` ohne unread; `subagent`: `done` erst nach dem zweiten Result + idle.

### Entscheidungen

1. **Reset-Marker:** Die Engine sendet `conversation.reset` (Diagramm f); der Normalizer liefert das
   Marker-Item `system/conversation_reset` mit der ersten Ausgabe nach `startConversation`
   (`order = nextOrder`, ID = `uuid` der Reset-Message = `new_conversation_id`).
2. **`px:`-IDs** = `px:${conversationId}:${order}` – über Prozess-Neustarts eindeutig, weil `order`
   pro Unterhaltung fortgeschrieben wird.
3. **`session_id`-Signal** für jede neue Session-ID (auch die erste); IDs einer durch Reset beendeten
   Unterhaltung lösen nie wieder eines aus (späte Frames der alten Unterhaltung).
4. **Finale Message ersetzt den Stream vollständig** – die CLI reichert Tool-Inputs an
   (`Edit.replace_all`, `ExitPlanMode.plan/planFilePath` werden erst in der finalen Message
   ergänzt; gestreamt war `{}`), daher gilt nur „gestreamte Keys ⊆ finale Keys“ (Fixture-Test).
5. **`costUsdTurn = null`** für das erste Result eines Normalizers (bei Resume enthält
   `total_cost_usd` die Vorkosten, F.14); danach Differenz (gerundet auf 1e-9).
6. **`structured` bleibt im Verlauf `null`** (architecture §6 vor dem Auftragstext); der Diff-Fallback
   ist Sache des Renderers (WP-15) über `input.old_string/new_string`.
7. **Plan-Text nie gekappt** (`ExitPlanMode.input.plan`), alle anderen Input-Strings > 48 Ki schon.
8. **Item-Budget:** `fitToolCall` lagert in der Reihenfolge structured → Result-Texte (16 Ki, 4 Ki,
   1 Ki, 256) → Input-Strings → Partial-Input aus; `memory_recall` teilt sich das Budget.

### Neue Befunde aus den Fixtures (für `docs/sdk-findings.md`, Koordinator)

- Die finale `assistant`-Message kann den gestreamten Tool-Input **erweitern** (s. Entscheidung 4).
- Zod 4: `z.unknown()`-Felder sind in Objekten Pflicht-Keys – tolerante SDK-Schemas brauchen
  `.optional()` (sonst fielen `init`/`status`/User-Messages ohne `tool_use_result` durch).
- Vordergrund-Bash erzeugt ebenfalls `task_started`/`task_notification` (`local_bash`,
  `is_backgrounded:false`) – vor dem `tool_result`.
- Nach „Jetzt senden“ (`now`) endet Turn C mit `subtype: success`, aber `terminal_reason:
  aborted_tools` → Outcome `interrupted` (kein unread).
- `getContextUsage` kommt in 4 Fixtures vor (nicht in `permissions-rules`).

- Nicht aufgezeichnete Typen sind nur synthetisch abgedeckt (Formen aus `sdk.d.ts`):

  Blob (der Rest wurde nie empfangen).
- Ohne `msg_lifecycle_v1` entsteht ein Prompt ohne `user_message_uuids` erst beim Result (Reihenfolge

### Gewünschte Contract-Änderungen (nicht umgesetzt, Workarounds aktiv)

1. `src/server/sessions/ports.ts`, `StatusSignal.context_estimate`: Feld `contextWindow: number |
   null` (aus dem letzten `result.modelUsage[model].contextWindow`). Grund: C.1 teilt durch dieses
   Fenster, die Engine soll keine Roh-Messages parsen. Workaround: `modelContextWindow(rawResult,
   model)` + `estimateContextGauge` aus `normalizer/index.ts`.
2. `src/server/backend/types.ts`, `HistoryMessage`: optional `origin: {kind: string} | null`
   (SessionMessage hat `origin`). Grund: `user_message.origin` im Verlauf (`human`/`other`).
   Workaround: immer `human`, Task-Notifications per Text erkannt.
3. `src/server/sessions/ports.ts`, Kommentar zu `session_id`: „für jede neue Session-ID (auch die
   erste), abgelöste IDs nie wieder“ statt nur „after a reset“ (Klarstellung, kein Typwechsel).
4. `docs/architecture.md` §6 Tabelle: `rate_limit_event rejected` → zusätzlich Signal
   `assistant_error` (`RATE_LIMIT_REJECTED`/`CLAUDE_BILLING`); `conversation_reset`-Marker kommt mit
   der ersten Ausgabe nach `startConversation` (Entscheidung 1); `system/model_refusal_no_fallback`
   → `system/error MODEL_REFUSAL`.

### Hinweise für WP-13 (Engine)

- `registerPrompt` **vor** `send()`; `user_message` entsteht bei `command_lifecycle started`.
- Nach dem Signal `conversation_reset`: neue `ConversationId`, Op `conversation.reset` selbst
  veröffentlichen, dann `startConversation(newId, 1)`; der Marker folgt in der nächsten Ausgabe.
- `session_id`-Signal → `conversations[last].sessionId` setzen (nach `/clear` nie
  `new_conversation_id`).
- Streaming-Upserts (`streaming:true`, `status:'streaming_input'`) **nicht** ins Transkript-Log;
  `conversation.lastOrder` aus den emittierten Upserts fortschreiben, neuer Normalizer je Prozess
  mit `nextOrder = lastOrder + 1`.
- Bei Prozessende `finalizeOpen('process_exit')`; `turn_end` ist meist unnötig (das Result schließt
  offene Streams).
- Context: nach jedem Turn `getContextUsage` → `normalizeContextUsage(raw, {contextWindow:
  profil.contextWindow}, now, 'summary')`; während des Turns `estimateContextGauge` mit
  `lastSdkMaxTokens` = letzte Breakdown-`maxTokens` und `modelContextWindow(letztesResult, model)`.
- `reduceStatus` erwartet `queue_changed`/`decisions_changed` von der Engine;
  `ctx.sessionStateSeen` je Prozess führen. Prompt gilt als übernommen, sobald sein
  `user_message`-Item kommt (auch ohne Lifecycle, R0-29).
- `assistant_error` kommt auch für `rate_limit_event rejected` → `lastError` setzen; nur
  Setup-Codes (z. B. `CLAUDE_BILLING`) machen den Status `error`.
- `readHistory` muss Haupt- und Subagent-Messages nach Zeit mischen (Beispiel: `mergeByTime` im
  Harness).
- Harness `testing/harness.ts` (`replayLive`/`replayStatus`) kann für FakeBackend-Tests dienen.
