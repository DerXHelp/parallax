### Bedienung

```powershell

.\parallax.cmd --port=4800         # Port (Default 4711; auch PARALLAX_PORT)
.\parallax.cmd --home=D:\px-data   # Datenverzeichnis (Default %LOCALAPPDATA%\Parallax; auch PARALLAX_HOME)
.\parallax.cmd --backend=fake      # FakeBackend (ohne Tokens)
.\parallax.cmd --no-build          # dist/ nicht prüfen/bauen
.\parallax.cmd --print-url         # Adresse mit Einmal-Code ausgeben statt Edge (60 s gültig)
.\parallax.cmd --help
```

| Situation | Verhalten | Exit-Code |
|---|---|---|
| Erster Start, `dist/` fehlt | „Building Parallax (first start …)“, `vite build` + `build-server.ts`, Server starten, Fenster | 0 |
| Checkout geändert (`git pull`, lokale Änderung an Build-Eingaben) | Build-ID passt nicht → neu bauen, dann wie oben | 0 |
| Parallax läuft (Lockfile + Health gleiche Instanz) | nur neues Fenster; Hinweis, falls `--port` abweicht oder der laufende Server ein älterer Build ist | 0 |
| Lockfile verwaist (Absturz, PID wiederverwendet, anderes Programm/andere Instanz auf dem Port) | „Found a stale lock file …“, neuer Server; das Lockfile überschreibt der neue Server | 0 |
| Zwei Starts gleichzeitig | der zweite Server endet mit Port belegt (4) bzw. „läuft schon“ (5) → der Launcher findet den ersten und öffnet dort ein Fenster | 0 |
| Port belegt (anderes Programm / anderer Parallax / hängender alter Server) | Meldung je Fall, bei hängendem Server mit PID und `taskkill`-Befehl; nichts gestartet | 1 |
| Port reserviert (EACCES, Hyper-V-Bereiche) | Hinweis auf `netsh interface ipv4 show excludedportrange protocol=tcp` | 1 |
| Server endet mit 3 (`STORE_VERSION_TOO_NEW`) | „written by a newer Parallax version – update Parallax“ + letzte Server-Zeile | 3 |
| Server endet sonst / Zeitüberschreitung (30 s) | Meldung mit Exit-Code bzw. PID und Pfaden `logs\server.out.log`, `logs\parallax.*.log` | 1 |
| Edge nicht gefunden / nicht startbar | Server läuft weiter (Port, PID genannt); Hinweis auf `--print-url` bzw. Firmen-Policies | 1 |
| Ungültige Option, `--dev` | Meldung + Usage | 2 |

`parallax.cmd` hält das Fenster bei einem Fehler mit `pause` offen (Doppelklick), außer
`PARALLAX_NO_PAUSE` ist gesetzt; bei Erfolg schließt es sich sofort. Es setzt
`NoDefaultCurrentDirectoryInExePath=1` (kein `node.exe` aus dem aktuellen Ordner) und ruft
`node node_modules\tsx\dist\cli.mjs --tsconfig src\server\tsconfig.json
src\server\launcher\main.ts %*` auf; `parallax.ps1` dasselbe über `Get-Command node
-CommandType Application`. Nach dem Start läuft nur noch `node.exe dist\server.js` (versteckt,
ohne Konsole); Fenster schließen beendet ihn nicht. Beenden: Zahnrad-Menü → „Server beenden…“.

### Verdrahtung für WP-20 (`src/server/main.ts`)

> **Historisch (Stand WP-21, vor WP-20a) – umgesetzt in `src/server/app/compose.ts`.** Maßgeblich
> sind der Code und `docs/architecture.md` §3.3 („Komposition und Start-Reihenfolge“); `main.ts`
> lädt nur Config und Logging, setzt die Exit-Codes und ruft `startServer()`. Abweichungen vom
> Beispiel unten:
> - Die Single-Instance-Vorprüfung (`findRunningServer`, Exit 5) ist nicht optional, sondern läuft
>   immer vor den Stores (WP-20a Entscheidung 3); der exklusive Home-Lock vor dem ersten Store
>   (`lib/homeLock.ts`, ADR-054) kommt mit WP-20c dazu.
> - `backend.dispose()` ruft `manager.shutdown()` selbst (R2-06); der Schritt `backend` in
>   `compose.ts` ist idempotent und deckt einen Fehlstart ab, bevor der Manager existiert.
>   Schrittfolge nach `manager.shutdown()`: `http` → `stores` → `lock` → `backend`.
> - Die Log-Datei schließt kein Schritt, sondern der `exit`-Wrapper (≤ 2 s, damit „shutdown: done“
>   noch in der Datei landet).

```ts
import { SERVER_EXIT_CODES } from './launcher/exitCodes';
import { writeServerLock } from './launcher/lockFile';
import { createServerShutdown } from './launcher/shutdown';

// optional vor dem Öffnen der Stores (zweiter Writer auf demselben Home):
//   if ((await findRunningServer({ home: config.home })).kind === 'running') → process.exit(SERVER_EXIT_CODES.alreadyRunning)
try {
  await app.listen({ host: config.host, port: config.port });
} catch (error) {
  // EADDRINUSE → Meldung auf stderr + Log, Exit 4 (der Launcher erkennt zusätzlich "EADDRINUSE" in der Ausgabe)
  process.exit(errnoCode(error) === 'EADDRINUSE' ? SERVER_EXIT_CODES.portInUse : SERVER_EXIT_CODES.failure);
}
const address = app.server.address();          // tatsächlicher Port, auch bei --port=0
const lock = await writeServerLock({ home: config.home, port: address.port, instance, launcherToken: auth.launcherToken });
const shutdown = createServerShutdown({
  stopSessions: () => manager.shutdown(),       // WP-13b: close() aller Queries, Stores flushen
  steps: [
    { name: 'http', run: () => app.close() },   // WS-Close 4503 an alle Fenster
    { name: 'stores', run: () => Promise.all([decisions.close(), blobs.close(), auth.close() /* … */]) },
    { name: 'backend', run: () => backend.dispose() },
    { name: 'lock', run: () => lock.release() },
    { name: 'logging', run: () => logging.close() },
  ],
});
shutdown.installSignalHandlers();               // SIGINT/SIGTERM/SIGBREAK/SIGHUP
// createSessionManager({ …, onShutdownRequested: () => void shutdown.stop('command') })
// StoreVersionTooNewError beim Laden → stderr + Log, process.exit(SERVER_EXIT_CODES.storeVersionTooNew)
```

- Einen Einmal-Code im Server-Prozess (`issueAuthCode()` beim ersten Start, ADR-015) braucht der
  Launcher **nicht**: Er holt auch beim ersten Start einen Code über `POST /api/launcher/code`
  (Entscheidung 2). Der Dev-Modus loggt seine URL weiter selbst (WP-10).
- `initLogging({ console })`: Wird der Server vom Launcher gestartet, landet stdout in
  `logs/server.out.log`; damit dort nicht der ganze pino-Log doppelt steht, empfiehlt sich
  `console: process.stdout.isTTY === true` (Datei-Log bleibt).
- Bundle: `lockFile.ts`, `shutdown.ts`, `exitCodes.ts` (und `client.ts` für den optionalen
  Pre-Check) sind bundle-tauglich; `build.ts` (dynamischer Import von `repo.config.ts`) und
  `main.ts` gehören nur zum Launcher.

### Umsetzung im Einzelnen

- **Single-Instance (C.8):** `findRunningServer` liest `server.lock.json` (`serverLockFileSchema`,
  EPERM/EBUSY-Retry) und pingt `GET /api/health` auf dem Port des Lockfiles; nur bei gleicher
  `serverInstanceId` gilt der Server als laufend. Kein PID-Vergleich, das Lockfile wird nie vom
  Launcher gelöscht. Nach dem Spawn wartet der Launcher, bis ein Lockfile mit der **PID des
  gestarteten Prozesses** erscheint und dessen Health dieselbe Instanz meldet (alte Lockfiles
  zählen dadurch nicht).
- **HTTP-Client:** `node:http` direkt auf `127.0.0.1` (`agent: false`, Timeout 2 s, Antwort ≤ 64 KiB):
  keine Proxy-Variablen, kein Keep-Alive, kein `Origin`/`Sec-Fetch-Site` – der Launcher-Endpunkt
  verlangt genau das (§5.1). Body `{}` mit `Content-Type: application/json` (WP-10.md Nr. 10).
  Der Test läuft gegen den echten WP-10-Server (`startTestServer`): Guard, Token, Einmal-Code.
- **Build (ADR-013/036):** Vergleich der ersten Zeile von `dist/server.js`
  (`// Parallax server, build <id>`) mit `resolveBuildId()` aus `repo.config.ts`, plus
  `dist/web/index.html` vorhanden. `repo.config.ts` liegt außerhalb des Server-Projekts (rootDir) und
  wird deshalb zur Laufzeit importiert (tsx) – eine einzige Build-ID-Implementierung. Gebaut wird
  mit `node <bin>` der lokalen `vite`/`tsx` (aus `package.json#bin`), also ohne pnpm und ohne Shell;
  ein Test hält `BUILD_STEPS` deckungsgleich mit `build:web`/`build:server` und den Banner mit
  `scripts/build-server.ts`. Geprüft gegen den echten Build: `upToDate`, Build-ID-Ermittlung ≈ 1 s.
- **Serverstart (C.2, C.8):** `spawnHidden(process.execPath, [<abs>\dist\server.js, --home=…,
  --port=…, --backend=…, --log-level=…], {detached, stdio: ['ignore', fd, fd], cwd: repo})`,
  `unref()`. Home und Port löst der Launcher mit `loadConfig` auf (dieselbe Rangfolge wie der
  Server) und übergibt die Werte explizit. Ausgabe nach `logs/server.out.log` (Rotation auf
  `.1.log` ab 1 MiB beim nächsten Start); bei einem Abbruch zeigt die Meldung die letzte Zeile **dieses**
  Starts (Offset vor dem Spawn).
- **Port:** Vorprüfung per Probe-`listen` auf `127.0.0.1:<port>` (nicht bei Port 0); belegt →
  Health auf dem Port unterscheidet „anderer Parallax“, „hängender alter Server (PID aus dem
  Lockfile)“ und „anderes Programm“. Ein Wettlauf nach der Probe wird über Exit-Code 4 bzw.
  `EADDRINUSE` in der Ausgabe erkannt.
- **Edge (C.9, A.8):** `findEdge` (App Paths HKCU/HKLM 64/32, Program Files (x86), Program Files,
  LocalAppData), Start über `spawnHidden` mit Argument-Array, `detached`, `stdio: 'ignore'`,
  `unref()`. Flags: `--user-data-dir=<home>\edge`, `--no-first-run`, `--no-default-browser-check`,
  `--app=<url>`. Der Code steht nur im `#`-Fragment und nie in einer Fehlermeldung.
- **Shutdown-Rahmen (C.8, R0-19):** Die Rückfrage im Fenster, dann `server.shutdown`; die Engine
  (13b) antwortet zuerst und ruft `onShutdownRequested` → `shutdown.stop('command')`. `stop()`
  wartet auf `stopSessions()` (Engine: `close()` aller Queries); läuft es nach 5 s noch, beendet
  `killChildProcessTrees` alle direkten Kindprozessbäume des Servers mit `taskkill /T /F` (ohne die
  eigene `powershell.exe`-CIM-Abfrage, nur Kinder jünger als der Server – PID-Wiederverwendung).
  Danach die Schritte in Reihenfolge, je mit Timeout, Fehler werden geloggt; am Ende immer
  `exit(code)`. Doppelte `stop()` liefern denselben Lauf; ein zweites Signal beendet sofort (130).
- **UI:** Menüpunkt „Server beenden…“ (destruktiv) im Zahnrad-Menü; Dialog (explizit bestätigt,
  Fokus startet auf „Abbrechen“) mit den Listen „Arbeitet (n)“ (starting/working/background) und
  „Wartet auf dich (n)“ (offene Freigabe/Frage/Plan) aus `deriveDisplayStatus` in Sidebar-Reihenfolge,
  Status als Icon + Text, Hinweis zu verfallenden Entscheidungen, Anzahl weiterer Sessions im
  Leerlauf; ohne Verbindung deaktiviert; ein abgelehnter Befehl zeigt den Fehler (`tError`) im Dialog.
  Nach dem `ack` schließt der Server alle Verbindungen (4503) und `HostGate` zeigt „Parallax-Server
  beendet“. Texte en/de in eigenen Wörterbüchern (Namespace `serverShutdown`).

### Entscheidungen

1. **Reihenfolge Single-Instance vor Build:** Abweichend von der Auftragsreihenfolge prüft der
   Launcher zuerst, ob Parallax läuft. `vite build` leert `dist/web`, während ein laufender Server
   daraus ausliefert – offene Fenster bekämen neue Assets zu einem alten Server (Reload-Schleife
   per `buildId`). Gebaut wird nur vor einem neuen Serverstart; bei laufendem älterem Build gibt es
   einen Hinweis („Server beenden“, neu starten).
2. **Einmal-Code auch beim ersten Start über den Launcher-Endpunkt** statt `issueAuthCode()` im
   Server-Prozess (ADR-015, Diagramm (h)): ein Codepfad für beide Fälle, der Server braucht weder
   Edge-Suche noch Edge-Start, Fehler (Edge fehlt) meldet die Konsole. Sicherheitlich gleichwertig:
   Der Launcher-Token steht ohnehin im Lockfile.
3. **Edge über `spawnHidden` (`windowsHide: true`):** Im einmaligen Smoke-Test war das App-Fenster
   trotz `SW_HIDE` in den Startinfos sichtbar (`MainWindowHandle` ≠ 0, Titel der Seite) – keine
   Ausnahme von „jeder Spawn mit `windowsHide`“ nötig.

### Stolpersteine

- In dieser (aus Claude Code gestarteten) Umgebung ist `NoDefaultCurrentDirectoryInExePath`
  gesetzt: `cmd /c parallax.cmd` findet das Skript dann nicht im aktuellen Ordner – `.\parallax.cmd`.
- Unter Last (parallele `pnpm check` anderer Worktrees, Virenscanner) dauern `startTestServer`,
  `git` und Prozessstarts ein Vielfaches; Standard-Timeouts (5 s Test, 10 s Hook) reichen dann nicht.
- Die Ausgabe eines gerade beendeten Servers kann kurz gesperrt sein (Scanner): `readServerOutput`
  wiederholt EBUSY/EPERM, der Launcher liest bei leerer Ausgabe nach 250 ms ein zweites Mal.
- Skripte im Scratch-Ordner (ohne `package.json` mit `"type": "module"`) brauchen `.mts`, und ESM-
  Importe absoluter Windows-Pfade müssen `file:///`-URLs sein.
