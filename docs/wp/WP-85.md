## 1. Umsetzung

### 1.1 Changelog (§4)
- `CHANGELOG.md` im Wurzelordner, Abschnitt „Unveröffentlicht“ mit den bisherigen Einträgen (Lizenz, Sicherheits-Update
  `hono`, Node 24.5). Beim Release 1.0.0 wird er zu `## [1.0.0] – <Datum>` (§4.4).
- `scripts/release/changelog.ts` parst und prüft das Format:
  - Überschriften, Gruppen in fester Reihenfolge, je Gruppe mindestens ein Eintrag;
  - ISO-Datum, Versionen absteigend, keine doppelte Version.
- `scripts/release-notes.ts`:
  - `--check`;
  - `--extract <version|unreleased>` für Release-Seite und `latest.json`;
  - `--check-tag <tag>` für die CI: Tag = `v` + `package.json` `version`, Abschnitt vorhanden und nicht leer.
- Der Test liest das echte `CHANGELOG.md`, Formatfehler fallen also in `pnpm check` auf.
- **Ergänzung:** Eine Vorabversion (`X.Y.Z-rc.N`) ohne eigenen Abschnitt nimmt die Notizen aus „Unveröffentlicht“. Ein
  Probelauf verbraucht den Abschnitt so nicht.

### 1.4 Launcher-Bundle und Paket-Modus (§5.2)
- **Abweichung:** `scripts/build-server.ts` bündelt neben `dist/server.js` auch `dist/launcher.js` (Banner
  `// Parallax launcher, build <id>`); ein eigenes `build-launcher.ts` gibt es nicht. Begründung:
  - dasselbe esbuild-Setup und derselbe Build-Lock;
  - keine neue Build-Stufe in `BUILD_STEPS`;
  - `pnpm build` und der Build des Launchers liefern beide Bundles.
- `launcher/main.ts` bestimmt `repoRoot` wie der Server (`dist` → `..`).
- `launcher/release.ts` (neu) enthält:
  - das Schema von `release.json` und `readReleaseInfo` (fehlt → Checkout, kaputt → `ReleaseInfoError`);
  - `verifyReleaseSignature` (Ed25519);
  - `RELEASE_PUBLIC_KEYS`, noch leer: Der Nutzer erzeugt den Schlüssel (§3).
- **Paket-Modus:** Liegt `release.json` neben `dist/`, gilt:
  - Die erwartete Build-ID kommt aus `release.json`; gebaut wird nie.
  - Ein unpassendes `dist/` meldet `package_damaged` („Install Parallax again“).
  - Die Meldung zu `STORE_VERSION_TOO_NEW` nennt „Update Parallax (or restore a backup)“ statt „git pull“.
  - Der Hinweis zu einem laufenden älteren Build nennt „installed“ statt „checkout“.
- `--install-root <ordner>` (absoluter lokaler Pfad, sonst Exit 2) ist das Arbeitsverzeichnis von Server und Chrome.
  Die Weitergabe an den Server sowie Autostart, Protokoll und Startmenü auf den Stammordner folgen mit WP-86
  (`system/**`).
- `launcher/packageFiles.ts` (neu) wird auch vom Installer (WP-86) genutzt:
  - `walkPackage` meldet Links, Junctions, Hardlinks, Datenströme und Namen, die sich nur in Groß- und
    Kleinschreibung unterscheiden;
  - dazu `hashFiles` und `comparePackageFiles` (fehlend, geändert, fremd).

### 1.5 Store-Schemas und Schema-Hashes (§9.4)
- `src/server/store/schemas.ts` ist die eine Liste der Stores in `PARALLAX_HOME`: neun JSON-Stores, `commands.json`
  und die Transkript-Zeilen.
- `schemaHash` = SHA-256 des kanonischen JSON Schema der Eingabeseite (`z.toJSONSchema`, `io: 'input'`), ohne Texte
  aus `description`/`title`.
- Der Test durchsucht `src/server` nach `new JsonStore` und verlangt jedes Schema in der Liste.
- WP-86 nimmt dieselbe Liste für die Sicherung (§8.4).

### 1.6 `scripts/release-pack.ts` (§5.2)
- **Voraussetzungen:**
  - `pnpm build` desselben Commits: Server, Launcher und Web mit derselben Build-ID `<version>+…`;
  - ohne `.dirty`, außer mit `--allow-dirty` für einen lokalen Probelauf;
  - `--out` außerhalb des Repos.
- **Ablauf:**
  1. Im Staging `parallax-<v>` läuft `pnpm install --prod --frozen-lockfile --ignore-scripts`
     `--config.node-linker=hoisted --config.package-import-method=copy`: flach, ohne Junctions und ohne Hardlinks in
     den pnpm-Store.
  2. **Import-Wächter:** esbuild parst `dist/server.js`, `dist/launcher.js` und alle `.js`/`.mjs`/`.cjs` des SDK
     (Metadatei, nichts wird geschrieben). Jeder nackte Import muss in einem Wegwerf-Modul im Staging per
     `import.meta.resolve` auflösen.
     - Zusätzlich geprüft wird `pino-roll` (Import über eine Variable).
     - Ausgenommen sind `pino-pretty` (nur `--dev`) und die Plattform-Pakete des SDK.
  3. Das SDK wird entfernt; ebenso die Verwaltung von pnpm (`.modules.yaml`, `.bin`).
  4. **Ergänzung:** Dateien ohne Laufzeit-Nutzen werden entfernt: Typdeklarationen, TS-Quellen, Source-Maps und
     Markdown in `node_modules`. Lizenz- und NOTICE-Dateien bleiben. Das spart 7 800 Dateien (75 → 45 MB).
  5. Dazu kommen ein gekürztes `package.json` (`name`, `version`, `type`, `engines`), `CHANGELOG.md`, `LICENSE` und
     `THIRD_PARTY_NOTICES.md`.
  6. Nur normale Dateien (`walkPackage`), dann `release.json` mit:
     - Version, Commit, Build-ID und `minNode`;
     - Schema-Hashes;
     - SDK (Version und `integrity` aus dem Lockfile);
     - dem SHA-256 jeder Datei.
- **`THIRD_PARTY_NOTICES.md`** (`scripts/release/notices.ts`, Text deutsch):
  - Inhalt: alle Pakete im Staging (Server) und alle Pakete, die die Source-Maps von `dist/web` nennen (Web). Dazu
    kommen CSS und Schriften, die dort fehlen (`WEB_ASSET_PACKAGES`).
  - Je Paket: Lizenz und Lizenz-/NOTICE-Dateien.
  - Ein eigener Abschnitt erklärt, dass das Agent SDK nicht enthalten ist, mit dessen `LICENSE.md`.
  - **Allowlist** der Lizenzen: MIT, ISC, BSD-2/3, Apache-2.0, BlueOak-1.0.0, 0BSD, CC0-1.0, OFL-1.1, Python-2.0 und
    Unlicense. Alles andere bricht das Release ab.
- Vorlagen (`start.mjs`, `parallax.cmd`, `install.cmd`, `parallax.ico`) kommen mit WP-86.

### 1.7 Signatur (§7)
- `scripts/release/sign.ts` läuft mit reinem `node` (Node 26 entfernt die Typen) und nutzt nur `node:`-Module, ohne
  Projektcode. Befehle:
  - `sign <datei>…` schreibt `<datei>.sig` (Ed25519 über die genauen Bytes, base64);
  - `latest` schreibt `latest.json` (Version, `prerelease`, URL, Größe, SHA-256 des Zips und des `CHANGELOG.md`,
    Notizen).
  - Den Schlüssel liest es aus dem Secret `RELEASE_SIGNING_KEY` und gibt ihn nie aus.
- `scripts/release-key.ts` führt nur der Nutzer selbst aus:
  - erzeugt das Schlüsselpaar und schreibt den privaten Schlüssel (PKCS#8) in eine neue Datei außerhalb des Repos;
  - setzt das Secret der Umgebung `release` per `gh secret set` über stdin;
  - gibt nur den öffentlichen Schlüssel (JWK `x`) und den Fingerabdruck aus.

### 1.8 Smoke (§6)
`scripts/release/smoke.ts` macht nacheinander:
1. Signatur von `latest.json`, dann Größe und SHA-256 des Zips.
2. Entpacken mit `System32\tar.exe`.
3. Signatur von `release.json`, `minNode` und jede Datei (fehlend, geändert, fremd).
4. Das Agent SDK per `npm pack` (npm neben Node) holen, gegen die `integrity` prüfen und entpacken.
5. Start wie das spätere `start.mjs`: `node --use-system-ca --use-env-proxy dist\launcher.js --install-root …`, mit
   FakeBackend, Temp-Home und Port 0.
6. Health mit der Build-ID aus `release.json`, dann `taskkill /T /F`.

**Abweichung:** Plan §6 sah für WP-85 das SDK aus dem Build-Arbeitsbereich vor. `npm pack` mit Prüfung der
`integrity` testet den späteren Weg 1 aus §8.2 schon jetzt. `--dir <ordner>` prüft ein unsigniertes Staging lokal.

### 1.9 CI (§6, §6.1)
- **`.github/workflows/release.yml`** wird von Tags `v*` ausgelöst und hat vier Jobs nacheinander:
  1. **build** (`contents: read`): Tag/Changelog prüfen, `pnpm audit --prod --audit-level high`, `pnpm check`,
     `pnpm build`, `pnpm e2e`, `release-pack` und Notizen. Das Artefakt wird mit `include-hidden-files` hochgeladen,
     sonst fehlten Dateien, die `release.json` listet.
  2. **sign** (Umgebung `release`, `contents: write`): Sparse-Checkout nur mit `sign.ts`, signieren, mit `tar.exe`
     zippen, `latest.json` erzeugen und signieren, dann Entwurf mit `gh release create --draft --verify-tag`
     (bei `-rc` als Pre-release).
  3. **smoke** (`contents: read`): Matrix Node 24.5.0 und 26.
  4. **publish** (ubuntu): `gh release edit --draft=false`.
- **Actions** per SHA gepinnt, alle älter als 14 Tage:

  | Action | Version | Datum |
  |---|---|---|
  | `actions/checkout` | v7.0.1 | 20.07.2026 |
  | `actions/setup-node` | v7.1.0 | 08.10.2026 |
  | `pnpm/action-setup` | v6.1.0 | 05.09.2026 |
  | `actions/upload-artifact` | v7.0.2 | 07.10.2026 |
  | `actions/download-artifact` | v8.0.2 | 07.10.2026 |

  `pnpm/action-setup` v6.1.1 (03.11.) war am 17.11. erst genau 14 Tage alt.
- **`.github/workflows/audit.yml`:** montags 05:17 UTC und von Hand, `pnpm audit` über alles.
  - Heute meldet es zwei mittlere Lücken (`glob`, `minimatch`, DEPS-2026-11 §6).
  - Bis zu deren Update (ab 18.11. bzw. 30.11.) schlägt der Lauf erwartungsgemäß fehl. Der Release-Job prüft nur
    hoch/kritisch zur Laufzeit und läuft durch.
- **`.github/dependabot.yml`:**
  - npm und github-actions, monatlich, je ein gebündelter PR;
  - `cooldown` 14 Tage, Ziel `main`, Agent SDK ausgenommen.
