### Anforderungen (normativ)
1. **Store (ADR-102):** `JsonStore` mit `profilesFileSchema` (v1), `backup`, Warnungen; fehlt die
   Datei → nur `STANDARD_PROFILE` im Speicher, geschrieben erst beim ersten `save`/`setDefault`.
   Fehlt „Standard“ in der Datei → ergänzt. Genau ein `isDefault` (mehrere/keiner → erster bzw.
   „Standard“, Warnung ins Log). `save`: neue ID `pf_` + 32 Hex (`lib/ids.newId`), `createdAt`/
   `updatedAt` vom Server, `builtin` nur für `standard`; Fehler-Issues → `PROFILE_INVALID{count}`.
   `remove`: `builtin` → `PROFILE_NOT_DELETABLE`; war Default → „Standard“ wird Default.
   Profil-Env-Werte mit geheimen Schlüsselnamen (`*_KEY`, `*_TOKEN`, `*_SECRET`, `*PASSWORD*`,
   case-insensitiv) beim Laden/Speichern per `registerSecret` maskieren (R9).
2. **Issues (`ProfileIssue = {level, issue}`, WP-30 §4.5):** `profileIssues` liefert
   - `level 'error'`: die `errors` von `parseProfileArgs(args, passRawArgs)` (`PROFILE_ARG_BLOCKED`,
     `PROFILE_ARG_NOT_ALLOWED`, `PROFILE_ARG_INVALID` mit `ProfileArgIssueParams`);
     `executable.path` nicht absolut / kein `.exe` / `windowsPathIssue` ≠ null / Datei fehlt →
     `PROFILE_INVALID{field:'executable', reason:'not_absolute'|'not_exe'|'unsafe'|'not_found'}`;
     `configDir` mit `windowsPathIssue` ≠ null → `PROFILE_INVALID{field:'configDir', reason:'unsafe'}`;
   - `level 'warning'`: die `warnings` von `parseProfileArgs` mit Schweregrad warning
     (`PROFILE_ARG_BROAD_ALLOWED_TOOLS`, `PROFILE_BYPASS_ENABLED`, `PROFILE_ARG_RESUME_NO_EFFECT`) und
     unaufgelöste `${env:NAME}` (`PROFILE_ENV_REF_UNRESOLVED{name,key}`);
   - `level 'info'`: `PROFILE_ARG_PASSED_RAW`.
   Ein fehlender `configDir`-Ordner ist kein Befund (die CLI legt ihn beim Login an).
3. **Summaries:** `ProfileSummary.{defaults, configDir, issues}`; `entryCount` bleibt 0 (füllt die

5. **Integration:** nutzt den übergebenen Store; bei `onChange` je Profil die Auflösungs-Caches

### Umsetzung (Kurzfassung)

- **Store (ADR-102):** `JsonStore` (`profilesFileSchema` v1, `backup: true`, Quarantäne, Warnungen,
  `StoreVersionTooNewError` wie die übrigen Stores). Ohne Datei nur `STANDARD_PROFILE` im Speicher;
  geschrieben wird erst bei `save`/`setDefault` (auch `setDefault('standard')` schreibt). Invarianten
  in `normalizeProfiles`: „Standard“ fehlt → vorn ergänzt (nicht Default), doppelte IDs → erste gewinnt,
  `builtin` genau für `standard`, mehrere Defaults → erster, keiner → „Standard“. Reparaturen werden
  geloggt (`warn`, nur Codes) und sofort zurückgeschrieben. `save` vergibt `pf_` + 32 Hex
  (`newId('pf')`), setzt `createdAt`/`updatedAt` vom Server, behält bei Änderungen `id`, `createdAt`,
  `isDefault`; vom Client mitgeschickte `isDefault`/`builtin` werden ignoriert. Secrets
  (`*_KEY`, `*_TOKEN`, `*_SECRET`, `*PASSWORD*`, case-insensitiv) beim Laden und Speichern per
  `registerSecret`. `onChange`-Listener laufen nach `save`/`remove`/`setDefault`/`setClaudeStatus`;
  ein werfender Listener wird geloggt und bricht die Änderung nicht ab.
- **Issues:** Reihenfolge Fehler → Warnungen → Infos. `executable`: `windowsPathIssue` `not_absolute`/
  `empty` → `not_absolute`, jedes andere Problem → `unsafe`, keine `.exe`-Endung → `not_exe`,
  `exists` false → `not_found` (`exists` wird nur mit sicheren absoluten `.exe`-Pfaden gerufen).
  `${env:NAME}` wird exakt wie in `buildEnvReport` aufgelöst (dieselbe Funktion, `configDir` dort
  ausgeblendet). `summaries()` cacht die Befunde je Profil bis zur nächsten Änderung (auch „Profil
  testen“); `profile.get`/`profile.validate` rechnen frisch (`issuesOf`).
- **Befehle:** `profile.delete` prüft `builtin` vor `entryCount` (also `PROFILE_NOT_DELETABLE` vor
  `PROFILE_IN_USE {count}`), unbekannte ID → `PROFILE_NOT_FOUND`. `profile.test` ruft
  `integration.checkProfile` (schreibt über `setClaudeStatus` in den Store → `onChange`); liest die
  Integration einen anderen Store (Fake, Tests), schreibt der Handler das Ergebnis zusätzlich selbst
  in den Store. `fs.listDirectory` → `NOT_IMPLEMENTED` (gehört WP-33). Ergebnisse gegen
  `commandResultSchemas` getestet.
- **`consoleLaunchFor`:** Profil laden → unsicherer `cwd` → `PATH_REJECTED {reason, field:'cwd'}` →
  Fehler-Issues → `PROFILE_INVALID {count}` → `buildEnv(target 'terminal', entryId)` (wirft
  `PROFILE_ENV_REF_UNRESOLVED` …) → `.exe` wie `launchSpecFor` (Cache, `CLAUDE_NOT_FOUND`).
  `explicitEnv` = Profil-Env-Namen mit ihrem endgültigen Wert aus dem gebauten Env (aufgelöste
  `${env:…}`) + `CLAUDE_CONFIG_DIR`; Secret-Werte daraus werden registriert. `args` = `profile.args`
  unverändert + `--resume <id>` + `--model`/`--permission-mode`, wenn gesetzt und nicht schon in den
  Args (per `parseProfileArgs`) + `--settings {"autoCompactWindow":N}` bei `contextWindow` ohne
  eigenes `--settings` (sonst `warn` ins Log). `cwd` exakt.
- **Cache-Invalidierung:** Cache-Eintrag trägt `resolutionKey` = `[executable, env, configDir]`;
  `onChange` verwirft Einträge, deren Profil fehlt oder deren Schlüssel sich geändert hat (eine
  reine Umbenennung behält den Cache); der Schlüssel wird zusätzlich beim Lesen geprüft, laufende
  Auflösungen sind je Profil+Schlüssel getrennt.
- **Preflight:** Zeile `profiles` (ok: „N from profiles.json“; info: ohne Datei/ohne Datenordner;
  warn: Reparaturbedarf, neuere Version, unlesbar – dann nur „Standard“), je Profil vor
  `claude`/`login` eine Zeile `config:<id>` (Fehler → `fail`, nur Warnungen → `warn`, nur Infos →
  keine Zeile; nie Env-Werte). `readProfilesFile` liest nur (keine Quarantäne, keine `.bak`, keine
  Reparatur auf Platte).

### Entscheidungen und Abweichungen

1. **`openProfileStore({warnings})` ist `StoreWarningSink`** (aus `store/jsonStore.ts`) statt
   `StoreWarnings` (`sync/ports.ts`, nur `list()`): der Store muss Warnungen *hinzufügen*.
   `createStoreWarnings()` erfüllt beides – die Verdrahtung in WP-40 ändert sich nicht. Weitere
   optionale Felder (additiv): `issueContext`, `debounceMs`, `retryDelaysMs`, `logger`.
   `PersistentProfileStore` hat zusätzlich `issuesOf(profile | input)` (frische Befunde).
2. **`launchSpecFor` prüft jetzt alle Fehler-Issues** (ADR-102: „verhindern Start“), nicht nur die
   Arg-Fehler. Folge: unsicherer `configDir` → `PROFILE_INVALID {count}` statt `PATH_REJECTED`;
   ein `executable.path` auf `.cmd`/`.ps1` → `PROFILE_INVALID` (WP-30 §4.12 verlangt `.exe`). Die
   Existenz der Datei prüft weiterhin die Auflösung (`CLAUDE_NOT_FOUND` mit Grund). Test angepasst.
3. **`VALIDATION_FAILED {path:'profile.env', key}` ist ein Fehler-Issue** (NUL im Wert, nur durch
   Handbearbeitung möglich): `buildEnv` würde den Start sonst ohnehin verweigern.
4. **Konsolenbefehl:** Die Form `& '<exe>' '<arg>'` allein ist in Windows PowerShell 5.1 falsch
   (leere Args fallen weg, `"` im Arg – z. B. das erzeugte `--settings {"autoCompactWindow":N}` –
   kommt ohne Anführungszeichen an), in 7.3+ dagegen richtig. Daher:
   `…; & { $PSNativeCommandArgumentPassing='Legacy'; & '<exe>' <args> }` (in 5.1 eine harmlose
   Variable, in 7.3+ nur im Skriptblock wirksam) und jedes Arg vorab nach MSVC-Regeln gequotet
   (`nativeCommandArg`), danach als PowerShell-Literal. Werte mit Zeilenumbruch werden zu
   doppelt-gequoteten Literalen mit Backtick-Escapes (der Befehl bleibt eine Zeile);
   Env-Namen außerhalb `[A-Za-z_][A-Za-z0-9_]*` als `${env:…}`. **Empirisch geprüft** (Scratch-Skript,
   nicht im Repo) mit Windows PowerShell 5.1 und `node.exe` als argv-Echo: Leerzeichen, `'`, `$`,
   `` ` ``, Umlaute, leere Args, JSON, abschließende Backslashes, Tabs, Zeilenumbrüche, typografische
   Anführungszeichen, `%PATH%`, `--%`, Env-Namen mit `(`/`{`/`` ` ``, `cwd` mit `'`/`$`/Leerzeichen –
   alles exakt. Bekannte Grenze (nur 5.1): ein Arg, in dem *jedes* Leerzeichen hinter einer
   ungeraden Zahl `"` steht (z. B. `"a b"` samt Anführungszeichen), kommt geteilt an. pwsh 7 ist auf
   diesem Rechner nicht installiert; dessen Verhalten folgt der Doku (`Legacy` = Verhalten von 5.1,
   maskierte `\"` zählen dort nicht).

### Stolpersteine

- Windows PowerShell 5.1 (Legacy-Übergabe an native Programme): zählt **jedes** `"` (auch `\"`) bei
  der Entscheidung, ein Arg mit Leerzeichen erneut in `"…"` zu setzen; leere Strings werden nicht
  übergeben; ein Arg `--%` wird selbst gequotet als Stop-Parsing-Token verschluckt
  (`nativeCommandArg` quotet es deshalb als `"--%"`). Typografische `“”„` zählen dort nicht.
- Hohe Last durch parallele WPs: `pnpm install --frozen-lockfile` brauchte ~18 min, das Grep-Werkzeug
  lief mehrfach in Timeouts (PowerShell `Select-String` als Ausweg).
