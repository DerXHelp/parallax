## 1. 86a – Sicherung (`src/server/store/backup.ts`)

Plan §8.4. Die Liste der Dateien kommt aus `STORE_SCHEMAS` (eine Stelle).

- `StoreSchema` bekommt `backup: boolean` (Default `true`); `false` für `processes.json` (beim Einspielen bleibt die
  aktuelle Datei, sonst gingen Einträge zu verwaisten Prozessen verloren) und `auth-secret.json` (ändert sich nicht,
  enthält ein Geheimnis). Der Schema-Hash ändert sich dadurch nicht (`schemaHash` sieht nur `schema`).
- Exporte (Namen verbindlich, der Launcher und WP-87 nutzen sie):
  - `BACKUPS_DIR = 'backups'`, `BACKUP_MANIFEST = 'backup.json'`, `BACKUPS_KEPT = 3`,
    `LAST_VERSION_FILE = 'last-version.json'`.
  - `readLastBuildId(home): Promise<string | null>` – fehlend oder kaputt → `null` (nie werfen).
  - `writeLastBuildId(home, buildId, now?): Promise<void>` – atomar (`writeFileAtomic`), `{schemaVersion: 1, buildId,
    at}`.
  - `createBackup(home, { from: string | null, to: string, now?: Date }): Promise<BackupResult>` –
    Ordner `<home>\backups\<from|unbekannt>-zu-<to>-<YYYYMMDD-HHmmss>` (Build-IDs enthalten `+` und `.`, das ist unter
    Windows erlaubt; `:` nie). Kopiert jede vorhandene Datei aller `kind: 'json'`-Stores mit `backup: true`, je
    Eintrag (`entries/<id>/…`), samt `<datei>.bak`, mit relativem Pfad. Für `kind: 'jsonl'` (Transkripte) nur die
    Länge in Bytes in `backup.json`. `backup.json`: `{schemaVersion: 1, from, to, createdAt, files: string[],
    transcripts: Record<string, number>}` (Pfade `/`-getrennt, relativ zu `home`). Erst in
    `backups\.partial-<…>` schreiben, dann umbenennen: ein abgebrochener Lauf hinterlässt keine halbe Sicherung.
    `BackupResult = { dir, files, transcripts }`.
  - `restoreBackup(home, dir): Promise<RestoreResult>` – für WP-87 (Rückweg); hier schon mit Tests:
    - jede gesicherte Datei zurück (atomar);
    - eine Store-Datei (Liste wie oben), die es jetzt gibt, aber nicht in der Sicherung, wandert nach
      `<dir>\newer\<relativer Pfad>`;
    - Transkripte auf die gesicherte Länge kürzen; Transkripte, die in der Sicherung fehlen, wandern nach
      `<dir>\newer\…`; ein Transkript, das kürzer ist als gesichert, bleibt (und wird in `RestoreResult.warnings`
      gemeldet);
    - `processes.json` und `auth-secret.json` bleiben unberührt.
    - Vorher prüft sie `backup.json` (zod); kaputt → Fehler, nichts geändert.
  - `pruneBackups(home, keep = BACKUPS_KEPT): Promise<string[]>` – löscht die ältesten fertigen Sicherungen über
    `keep` (Sortierung nach `createdAt` aus `backup.json`, unlesbare zählen als älteste) und `.partial-*` älter als eine
    Stunde; gibt die gelöschten Ordner zurück.
- Tests (Temp-Home mit `entries/<id>/…`, `.bak`, Transkripten): Liste ohne `processes.json`/`auth-secret.json`,
  Kürzen, `newer\`, kaputtes Manifest, `prune` behält drei, abgebrochener Lauf (`.partial`).
- Nicht in 86a: der Aufruf im Launcher (86d).

## 2. 86b – Agent SDK (`src/server/install/sdk.ts`, `npmrc.ts`)

Plan §8.2.

```ts
export interface SdkSpec { name: string; version: string; integrity: string } // release.json `sdk`
export interface ProvideSdkOptions {
  spec: SdkSpec;
  target: string;      // <versionsordner>\node_modules\@anthropic-ai\claude-agent-sdk (fehlt oder leer)
  cacheDir: string;    // <root>\cache
  tempDir: string;     // <root>\downloads
  tarball?: string;    // --sdk-tarball <datei>
  registry?: string;   // --registry <url>
  nodeExe?: string;    // Default process.execPath
  env?: NodeJS.ProcessEnv;
  run?: RunFileFn;     // Default runFile
  fetch?: typeof fetch;
  log?: (line: string) => void;
}
export type SdkSource = 'cache' | 'tarball' | 'npm' | 'download';
export async function provideSdk(opts: ProvideSdkOptions): Promise<{ source: SdkSource }>;
export class SdkError extends Error {}
```

- Reihenfolge: (1) Cache `<cacheDir>\<name ohne @, / → ->-<version>.tgz` – erneut gegen die `integrity` prüfen; passt
  er nicht, löschen und weiter. (2) `tarball` (nur wenn angegeben, dann ohne Rückfall: ein falscher Hash ist ein
  Fehler). (3) npm neben Node: `<dirname(nodeExe)>\node_modules\npm\bin\npm-cli.js pack <name>@<version>
  --pack-destination <tempDir>\<neu> --json [--registry <url>]` per `run` (absolutes `node.exe`, Argument-Array,
  `windowsHide`, Timeout 5 min); fehlt `npm-cli.js` oder scheitert npm, weiter mit (4). (4) eigener Download:
  Registry = `registry` > `NPM_CONFIG_REGISTRY`/`npm_config_registry` > `.npmrc` (`@anthropic-ai:registry`, dann
  `registry`) > `https://registry.npmjs.org/`; Metadaten `GET <registry>/<name mit %2F>` (Header `accept:
  application/json`), Tarball-URL aus `versions[<v>].dist.tarball`; Token/Basic-Auth für genau diesen Host aus
  `.npmrc`. Nur `https:`, `http:` nur für `127.0.0.1`/`localhost` (Tests). Größenlimit 200 MB, Timeout.
- Jeder Weg endet gleich: SHA-512 der Datei = `integrity` (`sha512-<base64>`), sonst `SdkError` (Datei löschen).
  Danach in den Cache legen (atomar) und mit `System32\tar.exe -x -z -f <tgz> --strip-components=1 -C <target>`
  entpacken; danach muss `<target>\package.json` `name`/`version` der Spec tragen.
- `npmrc.ts`: `readNpmrc(env, readFile?)` liest `NPM_CONFIG_USERCONFIG` bzw. `%USERPROFILE%\.npmrc` (fehlend = leer);
  Zeilen `key=value`, Kommentare `;`/`#`, `${VAR}` aus `env`; `registryFor(scope, npmrc, env)`,
  `authFor(url, npmrc)` → `Authorization`-Header oder `null` (`//host[/pfad]/:_authToken`, `:_auth`,
  `:username` + `:_password` base64). Längster passender Präfix gewinnt.
- Fehlermeldungen für den Nutzer (Englisch, wie Logs): was versucht wurde, und der Hinweis auf `--sdk-tarball`.
- Tests mit Fakes (`run`, `fetch`, Temp-Ordner, kleiner echter `.tgz` im Test erzeugt – `tar.exe -c -z` im Temp-Ordner
  ist erlaubt): Cache-Treffer ohne Netz, kaputter Cache, Tarball mit falschem Hash, npm-Weg (Fake-`run` legt die Datei
  ab und gibt das JSON aus), Download mit `.npmrc`-Registry und Token, `http:` außerhalb von Loopback abgelehnt,
  Größenlimit.

## 86a – Ergebnis

Umgesetzt nach §1 in `src/server/store/backup.ts` (+ Test), `store/schemas.ts` (Feld `backup`), `store/README.md`.
Exportnamen wie verlangt; zusätzlich exportiert: `BACKUP_NEWER_DIR`, `readBackupManifest`, `backupManifestSchema`
(`BackupManifest`), `BackupError`, `RestoreWarning` und die Options-Typen. Keine Contract-Änderung.

Ergänzungen und Entscheidungen:

- **Signaturen:** `createBackup` nimmt zusätzlich `fs?`, `retryDelaysMs?`, `logger?` (Test-Naht wie bei den Stores),
  `restoreBackup(home, dir, options?)` ebenso. `pruneBackups(home, keep, { now? })`: der optionale dritte Parameter
  gibt die Bezugszeit für das Alter der `.partial-*` (gemessen an der `mtime` des Ordners).
- **`RestoreResult`** = `{ restored, movedToNewer, truncated, warnings }`. `warnings` ist strukturiert
  (`{ file, reason: 'shorter' | 'missing', savedBytes, currentBytes }`), damit WP-87 sie übersetzen kann. Ein
  gesichertes Transkript, das jetzt fehlt, meldet `missing` (§1 nennt nur „kürzer“).
- **Ordnername:** Zeit in UTC (deterministisch, passt zu `createdAt`). In Build-IDs wird jedes Zeichen außer
  `A-Z a-z 0-9 . _ + -` zu `_`, ein führender Punkt bekommt `_` davor (sonst Verwechslung mit `.partial-`), je
  Build-ID höchstens 80 Zeichen. Zweite Sicherung in derselben Sekunde → Endung `-2`. `backup.json` behält die
  Build-IDs unverändert.
- **Prüfung vor dem Einspielen:** außer dem Schema muss jeder Pfad zur Liste passen (Platzhalter `*` = ein Segment
  aus `A-Z a-z 0-9 _ . -`, nie `.`/`..`), der Zielpfad muss `windowsPathIssue` bestehen (z. B. kein reservierter
  Gerätename) und jede gesicherte Datei muss vorhanden sein. Sonst `BackupError`, nichts geändert.
- **Einspielen:** Dateien atomar ohne `.bak` zurück (sonst würde die neuere Fassung zur `.bak`). `.bak` zählt als
  Store-Datei: eine `.bak`, die es nur jetzt gibt, wandert nach `newer\` (eine `.bak` mit neuerer `schemaVersion`
  würde den Store sperren, sobald die Hauptdatei fehlt). Liegt in `newer\` schon eine Datei (zweiter Rückweg aus
  derselben Sicherung), bekommt die neue die Endung `.1`, `.2`, …
- **Abbruch:** Wirft `createBackup` (z. B. Platte voll), löscht es den `.partial-…`-Ordner selbst und wirft weiter;
  nur ein beendeter Prozess hinterlässt ihn, `pruneBackups` räumt ihn nach einer Stunde.
- **`last-version.json`** steht nicht in `STORE_SCHEMAS` (kein JsonStore, gehört dem Launcher, wird nicht gesichert);
  `readLastBuildId` liefert nur für `schemaVersion: 1` eine Build-ID, sonst `null`.

Hinweise für 86d: `createBackup` ruft `pruneBackups` nicht selbst auf. `backup.ts` importiert `schemas.ts` und damit
die Module der Stores (u. a. `http/auth.ts`, `sessions/*`) – im Launcher-Bundle mitgezählt.

Tests: `backup.test.ts` 27 Fälle (Layout der Liste, Kopie samt `.bak` je Eintrag und Transkript-Längen, `.partial`
und Umbenennen, abgebrochener Lauf, Ordnernamen, leerer Datenordner, Rückweg mit Kürzen, `newer\` und Warnungen,
unberührte `processes.json`/`auth-secret.json`, kaputte Manifeste ohne Änderung, `prune` behält drei, unlesbare zuerst,
alte und frische `.partial-*`, `last-version.json`); `schemas.test.ts` +1 (`backup: false` nur für `processes.json` und
`auth-secret.json`).

## 86b – Ergebnis

Umgesetzt wie §2: `src/server/install/sdk.ts`, `npmrc.ts`, Tests daneben, `src/server/install/README.md`
(Abschnitt SDK). Schnittstelle `provideSdk`/`SdkSpec`/`ProvideSdkOptions`/`SdkSource`/`SdkError` unverändert.

- **Prüfung im Cache-Ordner:** Jede Quelle wird erst in eine Temp-Datei neben dem Cache-Eintrag kopiert, dort gegen
  die `integrity` geprüft, dann umbenannt; entpackt wird immer die Cache-Datei. So sind die entpackten Bytes genau die
  geprüften. `lib/fs.ts` hat nur `writeFileAtomic` für Daten im Speicher; das Kopieren mit Umbenennen (mit
  `withFsRetry`) steht lokal im Modul.
- **`--sdk-tarball` mit falschem Hash:** `SdkError`, aber die Datei des Nutzers wird nicht gelöscht (§2 „Datei
  löschen“ gilt für geholte Dateien aus npm und Download).
- **Ein falscher Hash aus npm** ist wie beim Download ein Fehler ohne Rückfall auf den Download (§2 „jeder Weg endet
  gleich“); nur ein fehlendes oder scheiterndes npm (Exit, Timeout, unlesbare Ausgabe, fehlende Datei) führt weiter
  zu Schritt 4.
- **Weiterleitungen** folgt der Download selbst (`redirect: 'manual'`, höchstens 5): jede Station muss `https:` sein
  (bzw. Loopback-`http:`), die Anmeldung kommt je Station aus `.npmrc` für genau deren Host. Ein Wechsel von `https:`
  auf `http:` wird abgelehnt.
- **Zusätzliche Exporte** (für Tests und den Installer): `sdkCacheFileName`, `sha512Integrity`, `packedFileName`,
  `readBodyLimited`, `isAllowedDownloadUrl`, Konstanten `SDK_MAX_BYTES` (200 MB), `SDK_METADATA_MAX_BYTES` (64 MB),
  `NPM_TIMEOUT_MS`, `TAR_TIMEOUT_MS`, `DOWNLOAD_TIMEOUT_MS` (je 5 min). `npmrc.ts`: `parseNpmrc`, `replaceEnv`,
  `userNpmrcPath`, `DEFAULT_REGISTRY`.
- **Vorbedingungen:** `target` muss fehlen oder leer sein (sonst `SdkError`); scheitert das Entpacken oder passt
  `package.json` nicht, wird `target` wieder entfernt. `target`, `cacheDir`, `tempDir` und `--sdk-tarball` laufen vor
  jedem Zugriff durch `windowsPathIssue`. Die Spec wird per zod geprüft (Paketname, SemVer, genau ein SHA-512).
- **`.npmrc`:** gelesen nach den Regeln von npm (`ini` + `@npmcli/config`): Kommentare auch hinter einem Wert ohne
  Anführungszeichen, `${VAR?}`, Abschnitte und `key[]` werden übergangen. Ein unlesbares `.npmrc` (außer fehlend) lässt
  den Download mit Meldung scheitern. Ohne `log` gehen die Zeilen an den Server-Logger (`module: install/sdk`).
- Tests: 29 (npmrc 9, sdk 20), darunter ein Lauf mit echtem `fetch` gegen einen Loopback-Server (Weiterleitung,
  Token je Host).

## 86c – Ergebnis

Umgesetzt in `src/server/system/**` (Details: `src/server/system/README.md`). Keine Änderung an `ports.ts`, keine neuen
Fehlercodes.

- **Neue Dateien:** `markers.ts` (Marker-Regeln, `entryMarkers`, `installationOnlyMarkers`, `entryOwner`,
  `INSTALL_START_SCRIPT = 'start.mjs'`, `INSTALL_ICON = 'parallax.ico'`, `installStartScript`, `installIconPath`) und
  `installation.ts` (`ensureStartMenuEntry`, `removeInstallationEntries` → `{ autostart, protocol, startMenu }`).
  86d kann die Dateinamen aus `markers.ts` übernehmen oder `install/layout.ts` als Quelle nehmen und `markers.ts`
  darauf umstellen.
- **`SystemOpResult`** (`run.ts`, nicht eingefroren) bekommt `deferred?: true` im Erfolgsfall; Skript-Ausgabe
  `deferred` und der Protokoll-Handler liefern `{ ok: true, deferred: true }`. `index.ts` loggt das als `info`
  („entry belongs to an installation - left alone“) und setzt keine Warnung.
- **Standard ohne `markers`:** `createAutostartShortcut`/`removeAutostartShortcut`, `isOwnCommand` und
  `ProtocolRegistryDeps` nehmen ohne Angabe `LAUNCHER_ONLY_MARKERS` (nur `launcher\main.ts`, nichts zurückgestellt –
  das Verhalten vor WP-86, fremde Einträge bleiben ohnehin unangetastet). `createSystemIntegration` übergibt immer
  `entryMarkers(installRoot)`. `PARALLAX_LNK_DEFER` wird nur gesetzt, wenn es zurückgestellte Marker gibt.

**Entscheidungen**

1. **Andere Installation:** Mit `installRoot` ist der Eintrag einer *anderen* Installation (`\start.mjs` außerhalb des
   eigenen Stammordners) fremd (Warnung `foreign`, nie ersetzt), nicht zurückgestellt – zurückgestellt wird nur im
   Klon (§3). Der Deinstaller nimmt nur `<installRoot>\start.mjs` als eigen; Einträge eines Klons
   (`launcher\main.ts`) bleiben, denn ein Klon, der sie nach dem Umstieg wieder angelegt hat, wird offenbar genutzt.
2. **Startmenü:** einmal je Serverstart (erstes `apply`, nur `available`, Windows und `installRoot`), auch bei Fehler
   kein zweiter Versuch bis zum nächsten Start (kein PowerShell je Einstellungsänderung). Der Befehl trägt nie
   `--home`, auch nicht, wenn der Server mit `--system-integration=on` auf einem anderen Datenordner läuft: das
   Startmenü startet wie die Verknüpfung des Installers immer den Standard-Datenordner.
3. **Toast im Klon:** Ist der Protokoll-Handler einer Installation zurückgestellt, gilt er für den Klon nicht als
   registriert (`toastLaunchUri` = null); ein Klick auf den Toast startet also nicht den Launcher der Installation.

**Abweichung/Zusatz:** `reg.exe` gibt in der OEM-Codepage aus (`lib/registry.ts`). Der Marker `<installRoot>\start.mjs`
enthält – anders als `launcher\main.ts` – den Benutzerordner; bei einem Umlaut im Benutzernamen hätte der Handler der
Installation ab dem zweiten Start als fremd gegolten. `entryOwner` faltet deshalb auf beiden Seiten jede Folge von
Nicht-ASCII-Zeichen und `?` (in Windows-Pfaden unzulässig) zu einem Platzhalter. DBCS-Codepages (z. B. Japanisch)
können darüber hinaus verfälschen; dann bleibt es beim sicheren „fremd“. Die Verknüpfungen liest `WScript.Shell`
in Unicode, dort gibt es das Problem nicht.

**Prüfung:** Tests nur mit Fake-`run` und Temp-`APPDATA` (92 Tests in `src/server/system`, davon 34 neu). Das
Skript wurde einmal von Hand mit der echten Windows PowerShell gegen einen Scratch-Ordner (nicht im Repo, nicht das
Startmenü) geprüft: Klon legt an, Installation biegt um und setzt das Symbol, Klon meldet `deferred` beim Anlegen
und Entfernen, alter Klon (`LAUNCHER_ONLY_MARKERS`) `foreign`, andere Installation `foreign`, Deinstaller entfernt
(auch bei anderer Groß-/Kleinschreibung), fehlende Verknüpfung `removed`.

- **Ablauf von `dist/install.js`** (`cli.ts`): Argumente → eigene `release.json` → Node-Mindestversion → Neustart mit
  `PACKAGE_NODE_FLAGS`, falls sie fehlen → Stammordner (`--dir` oder `%LOCALAPPDATA%\Programs\Parallax`) → Paket im
  Stammordner abgelehnt → Übergabe an `<root>\start.mjs --install <paket>` (nur aus einem Paket und nur mit vorhandener
  Installation) → Sperre `install` je Stammordner → Aktion. Exit-Codes 0 / 1 / 2 (falsche Option).
- **Einsetzen** (`install.ts`): Signatur (Schlüssel der laufenden Version), Node-Version, `walkPackage` +
  `comparePackageFiles` auf der Quelle, Kopie nur der gelisteten Dateien (nur Inhalt – kein ADS, kein
  Mark-of-the-Web), erneute Prüfung der Kopie im Staging, SDK (86b), Umbenennen, Stammdateien nur bei Änderung,

- **Laufende Version:** über den Server des Standard-Datenordners (`findRunningServer`), dessen Build-ID gegen die

- **Launcher:** `backupStep.ts` sichert vor dem Start eines neuen Servers, wenn die Build-ID von `last-version.json`

  Server mit `PACKAGE_NODE_FLAGS`; `--install-root` geht bis in `createSystemIntegration`.

**Entscheidungen**

1. **`install.cmd` ohne Node-Flags** (Abweichung von §4): Ein Node vor 24.5 bricht bei unbekannten Flags ab, bevor
   der Installer seine verständliche Meldung zur Mindestversion zeigen kann. `install.js` prüft die Version zuerst
   und startet sich dann selbst mit den Flags neu. `parallax.cmd` und alle Einträge tragen die Flags direkt (die
   Version wurde bei der Installation geprüft; `start.mjs` prüft sie bei jedem Start noch einmal).
2. **Ein leerer Stammordner bleibt nicht zurück:** Die Sperre legt den Ordner an; scheitert die erste Installation
   (z. B. Signatur), entfernt `cli.ts` ihn wieder, wenn er leer ist.
3. **Namen einmal:** `system/markers.ts` und `install/layout.ts` nennen `start.mjs` und `parallax.ico` je für ihre
   Seite; ein Test in `templates.test.ts` hält sie gleich. Die Node-Flags der Einträge kommen aus
   `PACKAGE_NODE_FLAGS` (`launcher/release.ts`).

**Prüfung:** 60 Tests in `src/server/install` (darunter ein echter Start von `start.mjs` mit `node.exe`),
`backupStep.test.ts`, neue Tests in `launcher.test.ts`, `cli.test.ts` und `config.test.ts`; `pnpm check` grün
