## 2. Grundentscheidungen (gelten für alle Dateien)

### 2.1 Was auf dem Draht steht (Multi-Host, B „Vereinfachungen“) [ABW zu A.2]
- Der Server ist **host-agnostisch**: Auf dem Draht gibt es nur `entryId`, **nie** `hostId` oder
  `sessionKey`. A.2 schreibt `subscribe{sessionKey, …}`; nach B lebt `hostId` nur in der
  Connection-Map des Clients → auf dem Draht `subscribe{entryId, sinceSeq?}`.
- Der Client bildet `sessionKey = \`${hostId}:${entryId}\`` (Helfer `makeSessionKey`/`parseSessionKey`
  in `common.ts`, damit Server-Toasts später dasselbe Format bauen können). `hostId` Phase 1 = `local`.
- Alles, was ein Host liefert (Profile, Settings, Ordner, Blobs), ist **pro Verbindung** gültig.

### 2.2 IDs

| ID | Erzeuger | Format (zod) | Bemerkung |
|---|---|---|---|
| `EntryId` | Server | `en_` + 32 Hex (`/^en_[0-9a-f]{32}$/`) | Sidebar-Eintrag; Ordnername unter `entries/` |
| `ConversationId` | Server | `cv_` + 32 Hex | Parallax-Unterhaltung; entsteht vor der Claude-Session-ID |
| `DecisionId` | Server | `dc_` + 32 Hex | Server-ID je Entscheidung (A.2) |
| `ProfileId` | Server | `standard` oder `pf_` + 32 Hex | eingebaut: `standard` |
| `ClientId` | Client | `cl_` + 32 Hex | pro Fenster, in `sessionStorage` |
| `CmdId` | Client | UUID (`z.uuid()`) | Idempotenzschlüssel |
| `BlobId` | Server | 64 Hex (SHA-256) | inhaltsadressiert, `/api/blob/<id>` |
| `ClaudeSessionId` | CLI | nicht-leerer String ≤ 100 (kein UUID-Zwang) | aus `init.session_id` |
| `MessageUuid` | Server | UUID | `SDKUserMessage.uuid` gesendeter Prompts |
| `ItemId` | Normalizer | String 1–200 | Schema §5.6 |
| `HostId` | Client | `/^[a-z0-9][a-z0-9-]{0,31}$/` (kein `:`) | nur Client |

Begründung Präfixe: Entry-, Conversation- und Claude-Session-IDs wären sonst alle UUIDs und
verwechselbar. Erzeugung **nicht** in `src/shared` (kein `crypto` im Lib-Set): Server-Helfer
`src/server/lib/ids.ts` (WP-10, `newId(prefix)` mit `node:crypto`), Web-Helfer `src/web/lib/ids.ts`
(WP-14, `crypto.randomUUID()`).

### 2.3 zod-Konventionen
- Jedes Schema heißt `xxxSchema`, der Typ `Xxx = z.infer<typeof xxxSchema>` (exportiert, gleicher
  Name ohne `Schema`). Unions mit `z.discriminatedUnion`. Diskriminator auf dem Draht: `type`; in
  Items: `kind`; in System-Items: `event`.
- Objekte: **`z.object`** (unbekannte Schlüssel werden entfernt) für Draht und Dateien.
  `z.strictObject` nur in Tests. Begründung: tolerant gegenüber Zusatzfeldern (Multi-Host,
  Downgrade), kein Fehler durch harmlose Extras.
- Dateien/Persistenz: neue Felder immer mit `.default(...)` bzw. `.nullable().default(null)`, damit
  alte Dateien ohne Migration laden (B „Fehlende Entry-Felder werden ergänzt“).
- Zeit: `IsoDateTime = z.iso.datetime({ offset: true })` (UTC-Strings aus `toISOString()`), Dauern in
  ms als `z.number().int().nonnegative()`.
- Beliebige JSON-Daten (Tool-Input, `tool_use_result`): `JsonValue = z.json()`.
- Rohe SDK-Strings, deren Wertemenge wächst (Modell-IDs, `task_type`, `decisionReasonType`), sind
  `z.string()`, nicht `z.enum` (F „unbekannte Typen tolerant“). Echte Enums nur, wo Parallax selbst
  entscheidet oder das SDK sie typisiert und wir sie **senden** (`PermissionMode`, `EffortLevel`).
- Eingehende Server→Client-Nachrichten mit unbekanntem `type` verwirft der Client still und zählt
  sie (`safeParseServerMessage`, §7.6). Client→Server ist strikt (unbekannt → `INVALID_MESSAGE`).

### 2.4 Rohdaten vs. normalisierte Items
- `src/shared` kennt **keine SDK-Typen** (ESLint verbietet `@anthropic-ai/*` in Shared). Rohe
  SDK-Messages existieren nur im Server (`AgentBackend` → `BackendEvent.message: unknown`).
- **Normalisiert wird ausschließlich im Server** (WP-12, zwei Adapter live/Verlauf, A.3). Der Client
  bekommt nur `TranscriptItem`s und `SessionOp`s. Der Normalizer parst SDK-Messages selbst tolerant
  mit eigenen zod-Schemas (`src/server/sessions/normalizer/sdk-schemas.ts`, WP-12).

Begründungen:
- 48 KiB liegt mitten im Plan-Korridor 32–64 KB; Zeichen statt Bytes, weil Shared kein
  `TextEncoder` typisiert hat und JS-Strings in UTF-16 gezählt werden (Kappung muss nur grob sein).
- `promptPrioritySchema` ohne `'later'`: die UI kennt nur Queue (`next`) und „Jetzt senden“ (`now`).
- `dontAsk` gehört zu `PERMISSION_MODES`, weil die CLI ihn in `init`/`status` melden kann; die UI
  bietet ihn nicht an (WP-16).

### 5.6 Transkript-Items (A.2, A.3, B „Message-Routing“, F.4, F.6, F.9–F.13)

**Item-ID-Schema (normativ, live und Verlauf identisch):**

| Quelle | `id` | Beleg |
|---|---|---|
| Assistant-Content-Block (text/thinking/tool_use) | `` `${message.id}:${blockIndex}` `` | F.13; geprüft: in allen Fixtures liefert jede `assistant`-Message genau einen Block, `content_block_start.index` = Ordinalzahl der Blöcke derselben `message.id`; im Verlauf (`getSessionMessages`) sind `message.id` und Reihenfolge identisch |
| User-Prompt | `` `${uuid}` `` (= unsere `MessageUuid`) | geprüft: Verlaufs-`uuid` = gesendete `uuid` |
| andere SDK-Message mit `uuid` (System-Events, Result, Interrupt-Marker) | `` `${uuid}` `` | |
| von Parallax erzeugt (Fehler ohne SDK-Message, Reset-Marker) | `` `px:${conversationId}:${n}` `` | |

`blockIndex` = `content_block_start.index` (live mit Stream) bzw. laufende Blockzahl je
`message.id` (ohne Stream: Subagent, Verlauf). `tool_result` erzeugt kein Item, sondern wird in das
`tool_call`-Item mit derselben `toolUseId` gemischt.

**Reihenfolge:** Jedes Item hat `order` (Ganzzahl ≥ 1, pro Unterhaltung streng steigend, bei
Erzeugung vergeben, nie geändert). Clients und Snapshots sortieren **nur** nach `order`; ein
`upsert` ersetzt am Platz. Damit fügen sich Snapshot, `loadEarlier` und spätere Updates alter Items
(z. B. Hintergrund-Task-Ergebnis) deterministisch zusammen.

Bedeutung von `runState` (Übergänge implementiert WP-12, hier nur Semantik):

| runState | Bedeutung |
|---|---|
| `starting` | Prozess gestartet/Query erzeugt, noch kein `init`/`running` |
| `working` | `session_state_changed` = `running` oder `requires_action` |
| `idle` | `session_state_changed` = `idle` (C.5: „fertig“ nur hieraus; `result` ändert `runState` nicht – F.10: `result` kommt vor `idle`, mit Hintergrundarbeit mehrere `result`s) |

| `external` | an externe Konsole/Terminal übergeben (Phase 2/4) |

Ein User-Stop (`result error_during_execution`, `terminal_reason aborted_*`) führt **nicht** zu
`interrupted` oder `error`, sondern über `idle` zu `lastTurn.outcome = 'interrupted'` (F.3, F.10).

|---|---|---|---|---|
| 1 | `runState = external` | `external` | nein | 4 |
| 2 | offene Entscheidungen > 0 (`permission+question+plan`) und `runState ∉ {sleeping, interrupted, error}` | nach `oldestKind`: permission→`needs-permission`, question→`needs-answer`, plan→`needs-review` | ja | 0 |
| 3 | `runState = error` | `error` | nein | 1 |

| 5 | `rateLimitedUntil > now` und `runState ∈ {idle, sleeping}` | `rate-limited` | nein | 1 |
| 6 | `runState = starting` | `starting` | nein | 2 |
| 7 | `runState = working` | `working` | nein | 2 |
| 8 | `runState = idle` und (`backgroundTasks > 0` oder `queuedPrompts > 0` oder `wakeupAt > now`) | `background` | nein | 2 |
| 9 | `runState = idle` und `unread` | `done` | nein | 3 |

| 11 | `runState = sleeping` | `sleeping` | nein | 4 (3 wenn `unread`) |

- **Seq** pro Eintrag, startet je `serverInstanceId` bei 1, jede `SessionOp` bekommt genau eine.

- Live-Bündelung: Der Server-Hub puffert `item.delta` je `(itemId, field)` und flusht alle

  mehrere Ops tragen. Der Client wendet Ops pro Animation-Frame an (WP-14).
- `conversation.reset` leert im Client Items und Entscheidungen der alten Unterhaltung; danach
  folgt `item.upsert` des `system/conversation_reset`-Markers.
- `detail.patch` ersetzt die genannten Felder komplett (Arrays nicht mergen).
- Mehrere Abos pro Client erlaubt (neues Fenster, Split-View später).

## 8. `src/shared/sync.ts` – gemeinsame reine Reducer [Ergänzung zum Plan]

Server-Hub (WP-10, materialisierter Zustand für Snapshots) und Web-Store (WP-14) wenden **dieselben**
Ops an. Ein gemeinsamer, getesteter Reducer verhindert, dass beide Seiten auseinanderlaufen.

```ts
export interface SessionViewState {
  entryId: EntryId;
  seq: number;
  conversationId: ConversationId;
  items: TranscriptItem[];            // aufsteigend nach order, ohne Duplikate
  hasEarlier: boolean;
  decisions: Decision[];              // offen + abgelaufen, nach createdAt
  detail: SessionDetail;
}

export function viewStateFromSnapshot(s: z.infer<typeof sessionSnapshotSchema>): SessionViewState;
/** Applies one op. Pure, returns a new object (structural sharing ok); never throws on unknown ids. */
export function applySessionOp(state: SessionViewState, op: SessionOp): SessionViewState;
/** Applies seq ops; returns { state, gap: true } without changes if ops[0].seq !== state.seq + 1. */
export function applySeqOps(state: SessionViewState, ops: SeqOp[]): { state: SessionViewState; gap: boolean };
/** Merges loadEarlier items (by order, de-duplicated by id). */
export function mergeItems(items: TranscriptItem[], incoming: TranscriptItem[]): TranscriptItem[];
/** Keeps only the newest `limit` items (snapshot / cache trimming); sets hasEarlier if trimmed. */
export function trimItems(state: SessionViewState, limit: number): SessionViewState;
```
Op-Semantik (tabellengetestet):

| Op | Wirkung |
|---|---|
| `item.upsert` | ID vorhanden → ersetzen (Position bleibt); sonst einsortieren nach `order` (binäre Suche; Ende ist der Normalfall) |
| `item.delta` | Item mit `id` suchen: `text` → `assistant_text.text` bzw. `thinking.text.text`; `thinking` → `thinking.text.text`; `inputPartial` → `tool_call.inputPartial` (null → ''); unbekannte ID/passt nicht → ignorieren |
| `item.remove` | entfernen, falls vorhanden |
| `conversation.reset` | `items = []`, `decisions = []`, `hasEarlier = false`, `conversationId` neu |
| `decision.upsert` | ersetzen oder anhängen (nach `createdAt`) |
| `decision.resolved` | Entscheidung entfernen (das Outcome steht im `tool_call.decision`, das der Server per `item.upsert` nachzieht) |
| `detail.patch` | flaches Überschreiben der genannten Felder |

`seq` wird nur von `applySeqOps` gesetzt. Der Server-Hub benutzt `applySessionOp` + `trimItems`
(`LIMITS.snapshotItems`) und baut daraus `session.snapshot`.

## 13. Versionierung und Regeln für Contract-Änderungen

| Größe | Startwert | Erhöhen, wenn … |
|---|---|---|
| `PROTOCOL_VERSION` | `1` | ein Peer mit der alten Version eine Nachricht der neuen nicht mehr korrekt versteht: Feld entfernt/umbenannt, Semantik geändert, neues **Pflicht**feld, Enum-Wert in Client→Server-Richtung entfernt. **Nicht** bei: neuen optionalen Feldern, neuen Server-Nachrichtentypen (Client ignoriert), neuen Befehlen (alter Server → `VALIDATION_FAILED`). |
| `buildId` | `dev` im Dev-Modus; sonst `<package.version>+<Build-Zeitstempel bzw. git-Kurzhash>` | jeder Build (Client-Reload nach `git pull`, A.2) |
| `REGISTRY_SCHEMA_VERSION`, `PROFILES_SCHEMA_VERSION`, `SETTINGS_SCHEMA_VERSION`, `decisions.json` | `1` | Migration nötig (Umbenennung, Strukturwechsel). Neue Felder mit `.default()` → **kein** Bump (B „fehlende Felder ergänzen“). Migrationen: `JsonStore` (WP-10) mit `migrations[from] = (raw) => raw'`. |
| Transkript-Log-Zeile `v` | `1` | wie oben; alte Zeilen bleiben lesbar (Reader kennt alle `v`) |
| `fixtureVersion` | `1` (ADR-010) | unverändert |

Ablauf jeder Contract-Änderung (nach dem Einfrieren): Anfrage im WP-Bericht unter
„SCHNITTSTELLEN/CONTRACT-ABWEICHUNGEN“ → Freigabe Koordinator → Änderung + Tests + Zeile im
Contract-Changelog (`docs/progress.md`) → Bump nach Tabelle. Die Build-ID-Injektion (Vite `define`
`__PARALLAX_BUILD_ID__` + esbuild `define` mit demselben Wert) braucht Root-Configs → WP-20 mit
Koordinator-Freigabe; bis dahin liefern Server und Web `'dev'`.

### Abweichungen vom Design (mit Begründung)
1. **Patch-Schemas ohne Defaults** (Bugfix): zod 4 wendet Defaults auch in `.partial()` an
   (geprüft). `settingsSchema.partial()` hätte bei `{theme}` die Sprache auf `en` zurückgesetzt,
   `detail.patch` hätte `unknownCounts` geleert. Neu: `settingsPatchSchema`, `sessionDetailPatchSchema`
   (gleiche Felder, keine Defaults; Test prüft Schlüsselgleichheit); `settings.update.patch`,
   `detail.patch` und `SettingsStore.update(patch: SettingsPatch)` nutzen sie.
2. **`applySeqOps`:** Ops mit `seq ≤ state.seq` werden übersprungen (idempotentes Replay-Überlappen)
   statt als Lücke gewertet; Lücken werden über den ganzen Batch geprüft. Der Namenskonflikt
   `applySessionOps` (Besitz-Tabelle) vs. `applySeqOps` (§8) ist gelöst, indem es beide gibt
   (`applySessionOps` = Ops ohne Seq falten).
3. **`conversation.reset`** setzt zusätzlich `detail.conversationId` (sonst zwei verschiedene
   Wahrheiten im View). **`detail.patch`** ignoriert Schlüssel mit `undefined`, damit Server-View
   (Ops aus TS) und Client-View (Ops nach JSON) nicht auseinanderlaufen.
4. **Unions:** `transcriptItemSchema` ist eine verschachtelte `z.discriminatedUnion('kind')` statt
   `z.union` (gleicher Typ, schneller); `ack` als verschachtelte Union funktioniert (kein Fallback).
   Die Helfer `sys(...)`/`c(...)` sind ausgeschrieben (ESLint `no-unnecessary-type-parameters`).
5. **`truncationSchema`** vereinheitlicht (`totalChars` positiv) für `cappedText.truncated`,
   `inputTruncated`, `structuredTruncated`.
6. **`TranscriptLogLine`** ist `z.infer<typeof transcriptLogLineSchema>` (zod als Quelle) statt
   handgeschriebenem Typ; `CommandError` mit explizitem Feld statt Parameter-Property, `name` gesetzt.
7. **Fixture-Format** (Koordinator): `src/server/backend/fixture.ts` ist die einzige Quelle,
   `scripts/record/format.ts` re-exportiert (statt Kopie + Follow-up).
8. **Build-ID** (Koordinator, statt WP-20): `resolveBuildId()` liegt in **`repo.config.ts`**, weil Vite-
   und esbuild-Build denselben Wert brauchen und beide diese Datei schon importieren (nicht wörtlich in
   der Besitz-Liste; bewusst, siehe ADR-013). Vite setzt `define` nur bei `vite build`. Weil noch kein
   Server-Code `BUILD_ID` liest (das `hello` kommt in WP-10), stempelt esbuild die ID zusätzlich als
   erste Zeile (`banner`). Die Ersetzung über `define` ist für Vite und esbuild im Scratch-Build geprüft.
9. **`docs/progress.md` nicht geändert** (nicht in der Besitz-Liste des Koordinators); der
   Changelog-Eintrag steht unten. Commit-Betreff nach Koordinator: „WP-02: Contracts, Ports und Architektur“.
10. **Ergänzungen** (additiv, getestet): `errorCodeForRateLimitError` + `CREDITS_REQUIRED_ERROR`
    (§4 „`credits_required` → `CLAUDE_BILLING`“ als Funktion), `DECISIONS_SCHEMA_VERSION`,
    `TRANSCRIPT_LOG_VERSION`, `CommandOf<N>`, `openDecisionCount`, `ITEM_DELTA_FIELDS`, `CANCEL_REASONS`,
