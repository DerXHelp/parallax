# WP-100 – Parallax unter Ubuntu: Bestandsaufnahme und Plan (WP-100…109)

Koordinator, Branch `feature/linux`. Auftrag des Nutzers am 20.11.2026. Stand: **Plan, Entscheidungen E1–E4 und E8
getroffen** (§4.1, 20.11.2026). WP-101 (Spikes) fertig: `docs/wp/WP-101.md` – E1 für Ubuntu 24.04 ohne Desktop neu
vorgelegt (WP-101 §3).

## 1. Auftrag

„ist parallax auch auf ubuntu lauffähig? das wäre wichtig“ – nach der Bestandsaufnahme (§2):

> „Es soll sowohl Ubuntu mit desktop, als auch ohne unterstützt werden. Ohne desktop natürlich dann nur im ‚server
> mode‘, sodass ich das von anderem Rechner aus steuere. […] Alle feature brauche ich dort. Kann aber akzeptieren, wenn
> beim Bau zwei Artefakte rauskommen: eins für windows, eins für ubuntu“

**Feststehend (Nutzer, 20.11.2026):**
- **Ubuntu mit Desktop:** alle Features lokal, wie unter Windows.
- **Ubuntu ohne Desktop („Server-Modus“):** kein eigenes Fenster; gesteuert von einem anderen Rechner über „Mehrere
  Rechner“ (WP-76…82).
- **Alle Features** auf beiden Wegen, soweit sie im jeweiligen Modus einen Sinn ergeben (§3.3).
- **Zwei Release-Artefakte** sind in Ordnung (Windows, Linux).
- **WSL ist kein eigenes Ziel.** Ein Ubuntu unter WSL hat keinen eigenen Desktop und verhält sich wie der
  Server-Modus; der Windows-Teil desselben Rechners steuert es über „Mehrere Rechner“.

Bisher war Linux ausdrücklich ausgeschlossen (`docs/wp/WP-83.md` §1, „Nicht im Umfang“). Dieser Plan hebt das auf.

## 2. Bestandsaufnahme (20.11.2026, nur gelesen, nichts auf Linux ausgeführt)

**Ergebnis: Parallax startet unter Ubuntu heute nicht.** Server, Web-UI, Agent SDK, Normalizer und Sync-Protokoll
sind portabel; was fehlt, ist die Systemschicht – vor allem die Pfadregeln.

## 3. Zielbild

### 3.1 Grundsätze
- **Eine Codebasis, Plattform zur Laufzeit** (`process.platform`). Je Plattform ein Adapter hinter den bestehenden
  Ports; die Windows-Implementierungen bleiben unverändert und werden nur umgehängt.
- **Pfade je Host, nicht je Browser:** Ein Windows-Fenster zeigt Sessions eines Linux-Servers. Die Web-UI wählt die
  Pfadregeln nach `HostState.platform` des jeweiligen Hosts (das Feld gibt es schon, `shared/model.ts:1083`).
- **Zwei Artefakte aus einem Build:** `parallax-<v>-win.zip` und `parallax-<v>-linux-x64.tar.gz`. Sie unterscheiden
  sich nur in Startskripten, Installer-Vorlagen und Archivformat.
- **Kein Rückschritt für Windows:** Jedes WP hält `pnpm check`, `pnpm build` und `pnpm e2e` unter Windows grün.
- **Sicherheitsniveau wie unter Windows:** Jede Windows-Regel (UNC/NTLM, Geräte-Pfade, nur absolute Programme, keine
  Shell, Prozessbaum beenden, neutrale Umgebung) bekommt ein POSIX-Gegenstück (§5.1, §5.2) und ein Review (WP-109).

### 3.2 Modi unter Linux
- **Desktop:** wie unter Windows – Launcher startet den Server unsichtbar und Chrome im App-Modus; alle
  Integrationen über freedesktop-Standards (XDG, D-Bus, `.desktop`).
- **Server (`parallax --server`):** kein Browser, Server im Vordergrund für systemd, Fernzugang („Freigeben“) an.
  Verwaltet wird er von einem gekoppelten Rechner mit der Stufe „Verwalten“ (E2); die erste Kopplung startet die
  Kommandozeile. Unter Windows nicht nötig, aber nicht verboten.

### 3.3 Feature-Matrix

| Feature | Windows | Ubuntu Desktop | Ubuntu Server (bedient vom steuernden Rechner) |
|---|---|---|---|
| Sessions, Chat, Entscheidungen, Pläne, Status, Remote Control, Limits | ✓ | ✓ | ✓ |

| Editor, Standardprogramm, „Im Ordner zeigen“ | ✓ | `xdg-open`, Editor-Vorgaben, `FileManager1` | – (remote gesperrt; Follow-up: VS-Code-Remote-Link) |

## 4. Entscheidungen

### 4.1 Entscheidungen des Nutzers (20.11.2026)

**E1 – Schlüsselspeicher: wie empfohlen.** Mit Desktop der **Secret Service** (GNOME Keyring, libsecret). Ohne
Desktop **`systemd-creds`** (verschlüsselt an den Rechner gebunden, mit TPM wenn vorhanden). Eine Datei mit Rechten
0600 nur als ausdrückliches Opt-in (`--key-store=file`), mit Warnung in Einstellungen und Preflight.
- *Vorbehalt (WP-101):* `systemd-creds` für Benutzerdienste gibt es laut Doku erst ab systemd 256; Ubuntu 24.04 hat 255.
  Fällt das durch, bleibt für 24.04 ohne Desktop nur die Datei – dann E1 noch einmal vorlegen.

**E2 – Verwaltung: über „Mehrere Rechner“** (statt SSH-Tunnel und Kommandozeile). Heute sind Einstellungen, Profile
(inkl. `claude`-Login), Updates, „Server beenden“ und die Kopplung für andere Rechner gesperrt
(`REMOTE_DENIED_COMMANDS`, `shared/protocol.ts:842`); das Kopplungsfenster öffnet nur ein lokales Fenster
(`remote/pairingWindow.ts`). Entwurf (Ergänzung der Sicherheitsspezifikation WP-76 §B, Review in WP-109):
- **Stufe je gekoppeltem Rechner:** „Steuern“ (wie heute) oder „Verwalten“, gespeichert beim freigebenden Rechner
  (Peer-Liste, neues Feld mit Default „Steuern“ – bestehende Kopplungen bleiben unverändert).
- **„Verwalten“ hebt die Sperre auf** für `settings.update`, `server.shutdown`, `profile.*`, `update.*`,
  `multiHost.configure` und `remoteAccess.*` (Kopplung, Schlüssel, Ereignisse). **Gesperrt bleiben** die Befehle für
  sichtbare Programme auf dem fremden Desktop (`session.openExternal`, `session.consoleCommand`, `file.open`,
  `editor.detect`, `link.open`, `session.openShell`) und `hosts.*` (die eigene Rechnerliste des Servers).
- **Vergabe:** beim Koppeln (Wahl im Kopplungsfenster bzw. `parallax remote pair --manage`); ändern lokal oder von
  einem Rechner mit „Verwalten“. Ein Befehl, der den eigenen Zugang abschneidet (Freigeben aus, eigene Kopplung
  aufheben), fragt nach.
- **Erste Kopplung ohne Desktop** braucht trotzdem eine kleine Kommandozeile: `parallax remote enable`,
  `parallax remote pair --manage` (zeigt den Code im Terminal), `parallax remote status`, `parallax remote unpair
  [--all]`, `parallax service install|uninstall|status`. Sie spricht mit dem laufenden Server über den Launcher-Kanal
  (Bearer-Token aus dem Lockfile, `launcher/client.ts`). Danach geht alles über den steuernden Rechner. Notweg bei
  verlorenem Zugang: SSH-Tunnel (`ssh -L <port>:127.0.0.1:<port>`, gleicher Port, weil der Host-Wächter nur
  `127.0.0.1:<port>` annimmt, `shared/http.ts:160`) und `parallax --print-url`.
- **Web:** Einstellungen, Profile und Updates eines anderen Rechners in dessen Kontext (Rechnerwahl in den
  Einstellungen); der Anmeldeablauf von `claude` mit Code-Eingabe (`profile.loginCode`) öffnet den Browser auf dem
  steuernden Rechner.
- **Risiko:** Ein übernommener steuernder Rechner mit „Verwalten“ beherrscht den Server vollständig – praktisch geht
  das über Sessions und mit E3 über das Terminal ohnehin.

**E3 – Terminal: für gekoppelte Rechner immer erlaubt,** ohne eigenen Schalter. Hebt in ADR-239 „nie für andere
Rechner“ auf und gilt plattformübergreifend, also auch für freigebende Windows-Rechner (cmd, PowerShell, Git Bash).
Das Shell-_Fenster_ (WP-97) bleibt lokal, weil es ein sichtbares Programm auf dem fremden Desktop wäre.

**E4 – Zielplattformen: Empfehlung gilt** (ohne Widerspruch, 20.11.2026): **Ubuntu 24.04 LTS und 26.04 LTS, x64.**
arm64 nur bei Bedarf (der Code wäre derselbe; Kosten: ein weiteres Artefakt und ein CI-Runner). Andere Distributionen
„sollte gehen“, ohne Zusage.

**E8 – Testumgebung: Docker-Container** (Nutzer: „Kannst du nicht docker Container dafür hochfahren?“). Docker Desktop
mit Linux-Containern ist vorhanden.
- **Image:** `ubuntu:24.04` und `ubuntu:26.04` mit offiziellem Node 26, pnpm, git und Google Chrome; Dockerfile im Repo
  (WP-101), dasselbe Image später in CI.
- **Quelle:** Der Arbeitsbaum ohne `node_modules`, `dist` und `.worktrees` wird in ein Container-Volume kopiert; der
  Container hat eigene `node_modules` mit Linux-Binaries (die Windows-`node_modules` nie einbinden), der pnpm-Store
  liegt in einem Volume.
- **Ressourcen (ADR-154):** Container mit `--cpus` und `--memory` auf höchstens die Hälfte begrenzt; ein schwerer Lauf
  zur Zeit – auch nicht parallel zu einem schweren Lauf unter Windows; Container nach dem Lauf beenden.
- **Abgedeckt:** Unit-Tests, Server, E2E (Chrome headless), Server-Modus, „Mehrere Rechner“ (zwei Container bzw.
  Container und Windows), Spikes (PTY, libsecret mit D-Bus und `gnome-keyring`, `systemd-creds`; systemd als PID 1 nur
  in einem eigenen Spike-Container).
- **Nicht abgedeckt:** echter Desktop (Chrome-App-Fenster, Benachrichtigung mit Klick, Autostart beim Login, Keyring
  der Anmeldung) → Live-Abnahme auf einem echten Ubuntu mit Desktop (WP-109, mit dem Nutzer); Xvfb im Container nur für
  automatisierte Teilprüfungen.
- **Live-`claude`** im Container (Meilenstein 1) nur nach Freigabe des Nutzers; die Anmeldung liegt dann im
  Container-Volume.
- **CI** auf `ubuntu-latest` (neuer Workflow `ci.yml`: `pnpm check`, `build`, `e2e`) als Gate vor dem Merge nach
  `main`; dafür `feature/linux` einmal pushen (Freigabe des Nutzers wie üblich).

### 4.2 Vorschläge des Koordinators (ADR mit dem jeweiligen WP; Einspruch jederzeit)

- **E5 – PTY-Anbindung:** eigene über `node:ffi` und `/dev/ptmx` (§5.4) statt `node-pty`. Grund: keine neue
  Abhängigkeit, kein natives Build-Skript (`strictDepBuilds`), gleiche Struktur wie ConPTY (ADR-239). Rückweg, falls der
  Spike scheitert: `node-pty` als Abhängigkeit vorlegen.
- **E6 – POSIX-Pfadregeln** (§5.1): absolut, ohne Steuerzeichen und Punkt-Segmente, groß/klein unterscheidend, absolute
  Symlink-Ziele erlaubt; Sperrliste für Pseudo-Dateisysteme (`/proc`, `/sys`, `/dev`, `/run`) als Wurzel oder Ziel von
  Dateizugriffen; gelesen werden nur reguläre Dateien (FIFOs und Geräte würden den Server blockieren).
- **E7 – Ablage nach XDG:** Daten `$XDG_DATA_HOME/parallax` (Standard `~/.local/share/parallax`), Programm
  `~/.local/lib/parallax/versions/<v>`, Startskript `~/.local/bin/parallax`. Logs wie unter Windows im Datenordner;
  im Server-Modus zusätzlich ins Journal (stdout).

## 5. Technischer Entwurf

### 5.1 Pfade (Contract, Kern von WP-102/103/104)
- `@shared/paths` bekommt Pfad-Regelsätze: `type PathFlavor = 'win32' | 'posix'`, `pathRules(flavor)` mit `issue`,
  `isSafe`, `key`, `equal`, `isInside`, `resolve`, `baseName`, `extension`, `join`, `separator`, `nameIssue`.
  `pathFlavorOf(platform: string)`: `win32` → `win32`, sonst `posix`.
- Die heutigen `windows*`-Funktionen bleiben unverändert als Implementierung von `win32`; neue `posix*`-Funktionen
  daneben. Gespeicherte `cwd`-Strings bleiben exakt (keine Migration, Windows-Daten unberührt).
- **POSIX-Regeln (E6):** `empty`, `too_long` (4096 Bytes UTF-8), `control_char`, `not_absolute` (nicht `/…`),
  `dot_segment`, `name_too_long` (255 Bytes je Segment), `pseudo_fs` (Sperrliste). Schlüssel = Pfad mit
  zusammengefassten `/` ohne abschließenden `/`, **groß/klein unterscheidend**.
- **Server:** `lib/paths.ts` wählt einmal `SERVER_PATHS = pathRules(pathFlavorOf(process.platform))`; alle Aufrufer
  gehen über diese Instanz statt direkt über `windows*`. Symlink-Prüfung (`resolveLinkTarget`) je Regelsatz.
- **Web:** `useHostPaths(hostId)` aus `HostState.platform`; `features/files/lib/paths.ts`, `lib/file-refs.ts`
  (POSIX-Pfade und `~/…` im Transkript erkennen, `fromGitBashPath` nur für Windows-Hosts), Gruppierungen
  (`session-order.ts`, `since.ts`, `recent-projects.ts`), Ordner-Browser, Formulare.
- **Schemas mit `.exe`-Pflicht** (`shared/model.ts:479,539`, Profil-Programm): im Schema nur noch Länge und
  Steuerzeichen; die plattformgenaue Prüfung macht der Server beim Speichern (`PATH_REJECTED` wie heute).

### 5.2 Prozesse, Programme, Umgebung (WP-103)
- `resolveExecutable` je Plattform: POSIX trennt `PATH` an `:`, ohne `PATHEXT`, verlangt eine ausführbare reguläre
  Datei (`X_OK`), löst Symlinks auf (`realpath`) und prüft das Ziel mit den POSIX-Pfadregeln.
- `resolveClaude` unter Linux: Einstellung → `~/.local/bin/claude` (nativer Installer) → `PATH`. Ziel nach `realpath`
  muss die native Binary sein (ELF); die alte JS-Variante wird wie unter Windows mit Hinweis abgelehnt.
- `systemTool` je Plattform (`/usr/bin/<tool>`, Existenz geprüft); `assertSpawnableFile` unter POSIX: absolut, keine
  Shell, ausführbar.
- **Prozessgruppen:** `spawnHidden` startet unter POSIX mit `detached: true` (eigene Gruppe, kein Terminal).
  `killProcessTree`: `SIGTERM` an `-pgid`, nach Frist `SIGKILL`; zusätzlich Nachfahren aus `/proc`, die eine eigene
  Gruppe aufgemacht haben.
- **Prozessliste aus `/proc`:** Startzeit (`stat` Feld 22 + Bootzeit), Kommandozeile, Eltern-PID; `environ` eigener
  Prozesse für `PARALLAX_ENTRY_ID`. Damit gehen Waisen-Suche, Heartbeat, Shutdown-Sweep, `applyUpdate` und der
  E2E-Teardown.
- **Umgebung:** unter POSIX groß/klein unterscheidend (`getEnvVar`, `setEnvVar`, `buildEnv`); `buildEnv` entfernt
  dieselben Variablen wie heute. `guiEnvironment` entsprechend.
- `spawnGui` unter POSIX: absolutes Programm, Sperrliste (Shells, Interpreter, Terminal-Emulatoren nur über §5.5),
  `detached`, `setsid`, stdio `ignore`; die PE-Prüfung entfällt dort (unter Linux gibt es kein GUI-Subsystem-Flag).

### 5.3 Start, Daten, Lock, Launcher (WP-103, WP-106)
- `config.ts`: Datenordner nach E7, Label `~/.local/share/parallax`.
- **Home-Lock unter Linux:** abstrakter Unix-Socket `\0parallax-<kind>-<sha256(realpath)>` – exklusiv gebunden, beim
  Prozessende automatisch frei (wie die Named Pipe unter Windows). B1-Fix: Pfadprüfung nach Regelsatz.
- **Chrome-Suche unter Linux:** Einstellung → `google-chrome-stable`, `google-chrome`, `chromium`, `chromium-browser`
  auf `PATH` → `/snap/bin/chromium`. Chromium als Snap darf keine versteckten Ordner in `$HOME` beschreiben – das
  Chrome-Profil (README „Chrome-Profil“) muss dann woanders liegen (WP-101 prüft das).
- **`--server`:** kein Chrome, Vordergrund (`Type=simple`), Log zusätzlich auf stdout; `--print-url` zeigt die Adresse
  mit Einmal-Code für den SSH-Tunnel.
- Meldungen mit `taskkill`, `netsh`, Task-Manager, `icacls` je Plattform.

### 5.4 Terminal (WP-105)
- **Linux-PTY** `terminal/unixPty.ts` als zweite `PtyFactory` neben `conpty.ts` (Port `terminal/ports.ts` bleibt bis
  auf den Kommentar „Absolute `.exe`“):
  1. `/dev/ptmx` mit `O_RDWR | O_NOCTTY | O_NONBLOCK` öffnen (`fs.openSync`), `unlockpt` und `ptsname_r` aus der libc
     über `node:ffi`, Slave öffnen.
  2. Shell starten: `child_process.spawn('/usr/bin/setsid', ['-c', shell, ...args], {stdio: [slave, slave, slave],
     cwd, env})` – `setsid -c` macht den Slave zum steuernden Terminal (Strg+C, Job-Control). Danach den Slave im
     Server schließen.
  3. `read`: `fs.readSync` auf den Master, `EAGAIN` → null, `EIO` → Ende. `write`: nicht blockierend mit Warteschlange
     wie ConPTY. `resize`: `ioctl(TIOCSWINSZ)` über `node:ffi` (variadisch – WP-101 prüft das; Rückweg `stty`).
     `exitCode`: aus dem `exit`-Ereignis. `close`: Master schließen (SIGHUP an die Sitzung), Rückfall `kill(-pid)`.
  4. Umgebung: neutral wie unter Windows (`shellEnvironment`), dazu `TERM=xterm-256color`, `COLORTERM=truecolor`.
- `ffi.ts` lädt `node:ffi` auch unter Linux x64 (und arm64, falls E4).
- **Shells (Contract):** `SHELL_KINDS` um `login` (Login-Shell des Nutzers aus `$SHELL` bzw. `getent passwd`), `bash`,
  `zsh`, `fish`, `pwsh` erweitern. `shell.detect` liefert zusätzlich die verfügbaren Shells; die UI zeigt nur diese.
  Standard je Plattform: Windows `cmd` (wie heute), Linux `login`. `gitBashWindow`/`gitDir` nur unter Windows sichtbar.
- **Shell im Ordner als Fenster (WP-97) auf dem Desktop:** Terminal-Emulator aus Einstellung → `xdg-terminal-exec` →
  `x-terminal-emulator` → bekannte Programme (Ptyxis, GNOME Terminal, Konsole, Xfce Terminal, kitty, Alacritty, WezTerm,
  foot, xterm), je mit eigener Syntax für Arbeitsordner und Befehl. Im Server-Modus ausgeblendet.
- Web: `windowsPty` nur für Windows-Hosts (`engine.ts:82`).
- **E3 (für gekoppelte Rechner immer erlaubt):** Weiterleitung der Route `API_PATHS.terminalWs` über den Vermittler
  (neuer Eintrag in `HOST_API_PATHS`, Contract), `shell.detect` remote erlaubt, `session.openShell` (Fenster) bleibt
  gesperrt; Wächter, Grenzen und Gegendruck wie lokal, Eingaben werden auch dort nie geloggt. ADR-239 bekommt einen
  Nachtrag. Ersatz für die externe Konsole auf einem Server: „In Terminal fortsetzen“ (`claude --resume` im
  eingebetteten Terminal, auch lokal nutzbar).

### 5.5 Externe Konsole (WP-106)
- Gleiche Terminal-Erkennung wie §5.4, Befehl `claude --resume …` mit `buildEnv`-Umgebung.
- PID-Verfolgung über `/proc` (Prozess mit `PARALLAX_ENTRY_ID`), weil Terminal-Emulatoren sofort zurückkehren.
- `consoleCommand.ts` je Plattform des Hosts: POSIX-Quoting (`PARALLAX=1 PARALLAX_ENTRY_ID=… claude --resume …`).
- **Fix für alle Plattformen:** Ohne nutzbaren Starter ist `launcher` null (`sessions/external.ts:135`), damit die
  Session nicht erst beendet wird; die UI blendet die Aktion über eine Host-Fähigkeit aus.

### 5.6 Dateien, Editor, „Im Ordner zeigen“ (WP-106)
- Editor-Vorgaben Linux: VS Code (`code`), VSCodium, Zed, Sublime Text, Kate, GNOME Text Editor, gedit, eigenes
  Programm; Erkennung über `PATH`.
- Standardprogramm: `xdg-open`. „Im Ordner zeigen“: D-Bus `org.freedesktop.FileManager1.ShowItems` über
  `/usr/bin/gdbus`, Rückfall `xdg-open <ordner>`.
- Ordner-Browser-Wurzeln: `/`, `~`, `/media/<user>`, `/mnt`.

### 5.7 Benachrichtigungen (WP-106)
- `notify-send` (libnotify ≥ 0.8, Standard auf Ubuntu Desktop) mit `--app-name=Parallax`, `--replace-id` statt `tag`,
  `--action` und `--wait`; ein Klick öffnet die Session wie der Toast-Klick unter Windows. Rückfall: D-Bus
  `org.freedesktop.Notifications` über `gdbus`.
- Server-Modus: native Benachrichtigungen aus; die Weiterleitung an den steuernden Rechner gibt es schon (WP-81).

### 5.8 Systemintegration (WP-106, WP-107)
- Desktop: Programmeintrag `~/.local/share/applications/parallax.desktop` (Icon als PNG/SVG statt `.ico`,
  `StartupWMClass` für das Chrome-App-Fenster – WP-101 prüft das), XDG-Autostart `~/.config/autostart/parallax.desktop`,
  `parallax:` über `MimeType=x-scheme-handler/parallax` und `xdg-mime default`.
- Server: systemd-Benutzerdienst `~/.config/systemd/user/parallax.service` (`parallax --server`), `systemctl --user
  enable --now`, `loginctl enable-linger` (ob das ohne Admin-Rechte geht, prüft WP-101; sonst Hinweis in README).
  Die Einstellung „Autostart“ steuert im Server-Modus diesen Dienst.

### 5.9 Mehrere Rechner und Server-Modus (WP-107)
- Schlüsselspeicher nach E1: `secure/secretServiceKeyStore.ts` (libsecret, synchrone API über `node:ffi`),
  `secure/systemdCredsKeyStore.ts`, optional `secure/fileKeyStore.ts` (0600, Opt-in). Auswahl und Fehlertexte in
  `remote/checks.ts` und Preflight.
- Preflight-Texte je Plattform (Firewall: `ufw` statt Windows-Firewall), Node-Prüfung auf OpenSSL ≥ 3.5.
- **Stufe „Verwalten“ (E2):** Feld in der Peer-Liste (`remote/peerStore.ts`, Default „Steuern“), Prüfung im Hub
  (`sync/hub.ts`, heute `isRemoteAllowedCommand`) je Stufe, Wahl im Kopplungsfenster und beim steuernden Rechner;
  Web: Einstellungen, Profile und Updates eines anderen Rechners (Rechnerwahl in den Einstellungen).
- **Kommandozeile (E2, erste Kopplung und Notweg):** `parallax remote …` und `parallax service …` über neue
  Launcher-Endpunkte (`@shared/http`, Contract); der Kopplungscode erscheint nur im aufrufenden Terminal.
- Terminal über den Vermittler (E3, §5.4).
- Voraussetzung für „Windows steuert Linux“: Pfade je Host (§5.1).

### 5.10 Paket, Installer, Update, Release (WP-108)
- Artefakt `parallax-<v>-linux-x64.tar.gz`; Installer `node dist/install.js` plus `install.sh`. Ablage nach E7;
  Deinstallation entfernt `.desktop`-Dateien, Autostart, systemd-Dienst und `parallax:`-Eintrag, die Daten bleiben.
- Agent SDK wie unter Windows aus der npm-Registry; `npm-cli.js` unter Linux in `<prefix>/lib/node_modules/npm`.
  Entpacken mit `/usr/bin/tar`.
- Update in der App: Asset je Plattform (`release.json` und Endpunkte, Contract), Archiv je Plattform (`update/zip.ts`),
  `applyUpdate` mit `/proc`-Startzeiten und Prozessgruppen.
- `release.yml`: ein Build (JavaScript), Paketierung und Smoke je Plattform (`windows-latest`, `ubuntu-latest`).
  Signaturverfahren unverändert.
- Voraussetzung in README: **Node ≥ 26.9 als offizieller Build** (nicht aus den Ubuntu-Paketquellen: zu alt, OpenSSL
  3.0), `claude` über den nativen Installer, Google Chrome oder Chromium (Desktop).

### 5.11 Tests, CI, Tooling (alle WPs, Abschluss WP-108/109)

  `runIf(win32)`; neue POSIX-Tests entsprechend. Echte Pfade in Tests über `os.tmpdir()` statt `C:\…`.

- CLI-Profil (`claude/cli-profile.json`): einmal live unter Linux prüfen (WP-109, Freigabe des Nutzers).

## 7. Risiken
- **`node:ffi` unter Linux** ist experimentell und hier noch nie benutzt (Terminal, Schlüsselspeicher). Rückwege:
  `node-pty` (E5, neue Abhängigkeit), `secret-tool` als Programm statt libsecret direkt.
- **Regressionen unter Windows** durch den Pfad-Umbau (85 Dateien): mechanisch, Windows-Funktionen bleiben unverändert,
  Tests pinnen den Regelsatz; Windows-`pnpm check`/`e2e` nach jedem Merge.
- **Sicherheit der POSIX-Regeln** (Groß/klein, Symlinks, Pseudo-Dateisysteme, Prozessgruppen) ist neu entworfen →
  eigenes Review in WP-109.
- **Mehr Rechte für gekoppelte Rechner** (E2 „Verwalten“, E3 Terminal immer): Ergänzung der Spezifikation WP-76 §B
  vor der Umsetzung (WP-102), Review in WP-109; bestehende Kopplungen bekommen nichts automatisch dazu außer dem
  Terminal (E3).
- **Snap-Chromium** und Wayland-Fensterverhalten (Spike WP-101).
- **Testumgebung:** Container decken keinen echten Desktop ab (E8) → Live-Abnahme auf echtem Ubuntu mit Desktop.
  Docker Desktop läuft in einer eigenen VM; ihre Last zählt zu ADR-154 (Grenzen je Container).
- **Verschiedene Terminal-Emulatoren** mit eigener Syntax – auf eine Liste begrenzt, Rest über die Einstellung.

## 8. Nicht im Umfang
- macOS; andere Distributionen ohne Zusage; arm64 ohne E4.
- WSL als eigenes Ziel (geht als Server-Modus).
- Datenordner zwischen Windows und Linux umziehen.
- `.deb`, Snap, Flatpak – nur Archiv mit Installer, wie unter Windows.
- VS-Code-Remote-Link für Dateien eines Servers (Follow-up).
